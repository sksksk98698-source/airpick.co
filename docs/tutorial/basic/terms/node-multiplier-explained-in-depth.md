# 节点倍率（Multiplier）彻底搞懂：1倍、0.1倍与5倍率的扣费账单计算

## 一、导言：先把结论拍在桌面上（TL;DR）

如果你只有 30 秒，请记住下面这五条：

1. **节点倍率（Multiplier）是计费乘数，不是速度乘数。** 5 倍率节点不代表快 5 倍，它只代表你走这条路要付 5 倍流量钱。
2. **计费口径通常是「上行 + 下行」双向叠加后乘倍率。** 只统计下行是少数面板的配置，不能默认。
3. **0.1 倍率节点不是免费，是打一折。** 你在 0.1x 节点上跑 40GB，账单只扣 4GB。
4. **核心公式：`实际扣除 = (上行字节 + 下行字节) × 倍率 × 时段系数`。** 时段系数是隐藏变量，很多机场在晚高峰时段对特定节点组做 2x 叠加，这是最大的账单黑洞。
5. **5 倍率专线该不该买，取决于你的痛点是「账单」还是「稳定性」。** 跨境会议、SSH 长连接、券商行情推流这类对丢包敏感的场景，5x 是合理溢价；纯刷视频，5x 是纯浪费。

本文不讲空话，我们把面板计费口径、IEPL/IPLC 的成本结构、三档倍率的账单复盘、抓包排障命令、避坑矩阵一次性讲完。新手按顺序读，老手直接跳到第二节和第七节。

## 二、底层机理：倍率这个数字，到底乘在什么上？

要理解倍率，先要理解机场的成本结构。机场向运营商或上游 IDC 采购的是「带宽容量 + 流量池」，不同承载介质的单位成本差 10 倍以上，倍率本质上是**成本转嫁的定价标签**。

### 2.1 三种承载介质，三档成本

**公网 BGP 中转**：数据包从入口服务器出发，经过公共互联网出口抵达落地。成本最低，也最容易被晚高峰国际出口拥塞影响。特征是「延迟随时间段波动大」，典型倍率 `0.1x ~ 0.5x`。

**IEPL（International Ethernet Private Line）**：运营商提供的二层点对点专线，数据不过公网出口，相当于在两地之间拉了一根「虚拟网线」。因为没有公网排队，晚高峰几乎不掉速，成本通常是公网中转的 5–20 倍。典型倍率 `2x ~ 4x`。

**IPLC（International Private Leased Circuit）**：三层专线，独享带宽，通常带 SLA 承诺。成本和 IEPL 同量级甚至更高，典型倍率 `3x ~ 6x`。

这就解释了为什么「同样的落地 IP、同样的协议，一个卖 0.1x 一个卖 5x」——**你付的不是协议钱，你付的是那根线的钱。**

### 2.2 几个常被拿来忽悠人的技术名词

**BBRv3**：Google 的拥塞控制算法。它的价值在于高丢包长肥管道（Long Fat Network）下把吞吐拉回来——当链路丢包在 1%–3% 时，BBRv3 相比 CUBIC 能显著改善有效吞吐。但请注意：**BBRv3 是 TCP 层的软件优化，它无法抵消物理专线的排队延迟。** 很多机场把「已启用 BBRv3」写进高倍率节点的卖点，这是偷换概念——公网中转节点同样可以开 BBRv3。

**TLS Reality / XTLS-Reality**：VLESS 的传输伪装方案，通过借用真实网站的 TLS 握手特征抵抗主动探测。它影响的是**节点存活率**，不影响倍率。但这里有个关键推论：如果一个 5x 专线节点因为协议配置粗糙被封，你的溢价就打了水漂。所以看高倍率节点，协议实现质量必须和线路质量一起评估。

**双 ISP / 双入口**：入口同时接入两家一级运营商（例如电信 + 联通），通过 BGP 宣告或 DNS 调度让不同省份用户走更近的一跳。这是「最后一公里绕路」的主要来源，也是高倍率合理性的重要支撑之一。

**QoS 与承诺速率（CIR/PIR）**：专线厂商会给出承诺信息速率和峰值信息速率。**倍率真正应该锚定的是 CIR 和超售比，而不是节点名字里写了「IPLC」。** 一个超售比 1:50 的 IPLC，晚高峰体验可能不如一个超售比 1:5 的优质 BGP 中转。这一点，在第七节的��障里会给出可验证的方法。

| 节点类型 | 典型倍率 | 承载介质 | 单线实测带宽 | 平均 RTT | 晚高峰丢包 | 估计超售比 | 等效单价（元/GB） | 最佳适配场景 |

| 双 ISP 精品入口 | `3x ~ 6x` | 专线 + 多线接入 | 300–800 Mbps | 120–145 ms | `低于 0.5%` | 1:5 | `0.80 ~ 1.50` | 游戏加速、低抖动 |

## 四、倍率计算公式与三档账单复盘

### 4.1 完整公式

```
实际扣除流量 = (上行字节数 + 下行字节数) × 节点倍率 × 时段系数 × 协议开销修正
剩余流量 = 套餐总量 − Σ(实际扣除流量)
```

四个变量逐个拆：

- **上行 + 下行**：面板（SSPanel-Uim / V2board / Xboard 系）一般在节点侧代理层统计收发的字节数。**上传同样计费**——这是 PT 用户和网盘同步用户最容易翻车的地方。
- **节点倍率**：就是你看到的那一栏数字。
- **时段系数**：部分机场对「高倍率节点组」在晚高峰 20:00–24:00 设置额外乘数（常见 `×2`）。这个参数通常写在订阅页的折叠说明里，极容易被忽略。
- **协议开销修正**：多数面板统计的是代理层载荷，底层 TCP 重传放大不计入，但 TLS/传输头开销可能计入。不同实现有差异，**不要假设 1GB 下载只扣 1GB**。

### 4.2 三档账单复盘

假设本月你在各节点上产生的**原始流量总量为 40GB**（其中下行 36GB、上行 4GB），套餐为 100GB：

| 场景 | 走什么节点 | 计算过程 | 实际扣除 | 账单剩余 |
| --- | --- | --- | --- | --- |
| A | 全走 `0.1x` 低倍率 | `40 × 0.1` | **4 GB** | 96 GB |
| B | 全走 `1x` 标准 | `40 × 1` | **40 GB** | 60 GB |
| C | 全走 `5x` 高倍率专线 | `40 × 5` | **200 GB** | 严重超支，需叠加流量包 |

**结论非常直白**：在场景 C 下，你一个月的实际可用流量只有 20GB（100 ÷ 5），而场景 A 下你理论上有 1000GB 额度。

### 4.3 混合策略：把倍率当「路由权重」用

真正会玩的人，是把倍率当成**分流规则的权重参数**来用：

- **大流量、可容忍抖动**（视频、系统更新、大文件下载、PT）→ 强制路由到 `0.1x` 节点组
- **中等流量、要稳定**（网页、社交、代码仓库拉取）→ `1x` 主力节点
- **小流量、绝不能断**（WebRTC 会议、SSH、券商行情推流）→ `3x ~ 5x` 专线

这样一个月下来，账单通常能压到「全走 1x」的 40%–60%，而关键场景的体验反而更好。具体的分流配置在第六节展开。

## 六、分客户端 / 分平台实操配置与深度避坑

### 6.1 通用原则：让路由规则承担省钱职责

倍率是写在订阅里的静态属性，客户端不会帮你省钱——**省钱靠的是分流规则**。核心思路是把节点按倍率分组，再用规则把流量类型映射到节点组。

### 6.2 各平台落地要点

**Clash Verge Rev / Mihomo（桌面端主力）**

- 用 `proxy-groups` 建三个组：`低倍率-大流量`、`1x-主力`、`专线-关键业务`。
- 用 `GEOSITE` / `RULE-SET` 做分流：`geosite:category-ads-all` 拒绝，`geosite:youtube`��`geosite:netflix` 指向低倍率组，`geosite:github`、`geosite:openai` 指向主力组，`DOMAIN-SUFFIX` 命中会议域名（如 zoom、teams）指向专线组。
- 开启 `profile.store-selected` 保存手动选择，避免每次订阅更新被打回默认。

**Shadowrocket（iOS）**

- 节点名里直接标注倍率（`🇺🇸 美西 0.1x`），减少切错。
- 打开「流量统计」，按节点查看当日消耗，和机场面板对账。
- **重点**：关闭 iCloud 照片同步走代理、关闭 App Store 自动更新走代理。这两个是 iOS 上最大的隐形流量黑洞。

**Surge（macOS / iOS）**

- `[Policy Group]` 做策略组，`[Rule]` 里用 `PROCESS-NAME` 精确控制单个 App 的出站策略，例如把 `Transmission` 强制走低倍率组。
- 配合 `requests` 面板观察每个策略组的实时速率。

**sing-box / OpenWrt（路由器全局）**

- 路由器全局代理是偷跑流量最严重的场景：智能电视开机自动更新、NAS 后台同步、IoT 设备心跳都可能走代理。
- 必须用 `nftables` 或 sing-box 的 `route.rules` 做**设备级白名单**，只放行明确需要代理的设备和网段。
- 定期用 `vnstat -m` 对照路由器 WAN 口月度用量和机场面板用量。

### 6.3 三个高频踩坑点

1. **订阅更新后节点顺序变化**：很多客户端按顺序选第一个节点，订阅一更新就从 `0.1x` 跳到 `5x`。解决方式是用策略组固定，不用「自动选择」。
2. **双倍计费时段未察觉**：把机场公告页加入 RSS 或定期查看，确认是否有晚高峰加价。
3. **上传流量被忽略**：网盘同步、PT 做种、Docker push 都会产生可观的上行。如果机场上传计费，务必在客户端限制这些进程。

## 七、抓包排障诊断手册：用命令验证「值不值」

当你怀疑高倍率节点名不副实，或者账单对不上时，按下面的流程走。

### 7.1 常用命令

```bash
# 1. 链路逐跳丢包定位（TCP 模式，避免 ICMP 被限速误判）
mtr -rwzc 100 -T -P 443 node.example.com

# 2. TCP 握手延迟（比 ping 更贴近真实代理体验）
tcping -p 443 -c 20 node.example.com

# 3. 端到端吞吐实测（下载 100MB 样本）
curl -o /dev/null -s -w "connect=%{time_connect}s ttfb=%{time_starttransfer}s speed=%{speed_download}B/s\n" \
  https://speed.cloudflare.com/__down?bytes=104857600

# 4. 本机实时流量观察
nload -u M            # 界面化上下行
iftop -i eth0 -n -P   # 按连接看谁在跑流量

# 5. 本机月度流量统计（Linux 路由器常用）
vnstat -m

# 6. 当前活跃连接数（排查异常长连接）
ss -tn state established | wc -l
```

### 7.2 结果判定表

| 观察到的现象 | 最可能的原因 | 处置建议 |
| --- | --- | --- |
| `mtr` 从第 3 跳开始持续丢包，末跳丢包率 `大于 3%` | 公网
