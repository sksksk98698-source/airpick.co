# iOS 双雄对决：Shadowrocket（小火箭）与 Quantumult X（圈X）深度较量

## 一、TL;DR：先给结论，再讲道理

如果你只想要一句话答案：

- **只想“装完能用、订阅一导就上网、顺手买断不折腾”** → 选 **Shadowrocket（小火箭）**。它的核心价值是**极低的上手门槛 + 极宽的资源兼容性**，在“小火箭简单易用优势”这一维度上，至今没有 iOS 客户端能真正撼动它。
- **愿意花 2~3 天读懂配置、想要**规则分流 + 脚本改写 + 去广告 + 自动化任务**一步到位** → 选 **Quantumult X（圈X）**。它的核心价值是**脚本引擎 + MITM 深度改写能力**，在“圈X脚本去广告实力”这个赛道上，小火箭只能算半个对手。

关键提醒：**客户端只决定「你怎么管流量」，不决定「流量跑得稳不稳」。** 两者都跑在 iOS 的 NetworkExtension 沙盒里，最终体验的 70% 由你背后的节点质量决定——协议效率、线路类型（公网中转 vs IPLC/IEPL 专线）、晚高峰拥塞程度。客户端选错，最多难受；节点选错，天天难受。

## 二、底层机理：两个 App 到底在抢什么

### 2.1 同一条用户态转发链路

iOS 不允许 App 直接改内核路由表。所有代理客户端都必须走 **NetworkExtension → NEPacketTunnelProvider** 这条唯一合法通道：系统把符合条件的 IP 包交给 App 创建的虚拟网卡（utun），App 在**用户态**完成解析、规则匹配、加密、再通过真实 socket 发出去。

这意味着：

1. **两者都不存在“内核加速”的魔法**，性能差距来自用户态实现的精细度。
2. 单条 TCP 握手要经历「系统 → utun → App → 远端」四跳，**首包 RTT 天然比裸连多 1~3ms**，这是架构税，不是谁的锅。
3. 高并发场景（比如同时开 200 个 DNS 查询 + 30 条连接）时，**调度器实现质量决定掉速率**，这里圈X 的多核调度略占优。

### 2.2 规则引擎：线性表 vs 集合树

小火箭默认使用「域名后缀 + IP-CIDR + GEOIP + 正则」的**有序线性规则表**，命中即停。规则条目一旦膨胀到 8 万行以上（某些去广告合集就是这个量级），冷启动会看到明显白屏等待。

圈X 采用**规则集 + 域名集合树**的混合结构，支持把大规则拆成多个 `filter_remote` 远程集并增量更新，冷启动更快，但代价是——你得先搞懂 `[filter_local]`、`[filter_remote]`、`[rewrite_local]` 各写在哪一段。

### 2.3 脚本与 MITM：圈X 真正的护城河

圈X 的脚本引擎基于 **JavaScriptCore**，暴露 `$http-request`、`$http-response`、`$task`、`$done`、`$notify` 等 API，能在 TLS 解密后对报文做**真实改写**——改 JSON 字段、删广告位、伪造会员状态、给请求加签名。这就是「圈X脚本去广告实力」强于小火箭的根本原因：不是多几个规则，而是**能从数据层把广告从响应体里抠出去**。

小火箭也支持脚本，语法与 Quantumult X 部分兼容，但 API 覆盖面窄，社区里大量 `.js` 在圈X 能跑、在小火箭报错。**如果你最在意的是 App 内广告、开屏广告、信息流推广位的清除，圈X 是唯一解。**

注意：MITM 需要 **安装并手动完全信任根证书**（设置 → 通用 → 关于本机 → 证书信任设置）。这一步是安全红线——**只对你信任的脚本开启 MITM 域名，不要开 `*.` 全局**，否则等于把明文流量交给脚本作者。

### 2.4 协议覆盖 vs 协议效率

截至 2026 年初，小火箭的协议覆盖更“野”，对新协议跟得飞快（Hysteria2、TUIC、WireGuard 都能吃）；圈X 相对保守，但对已支持协议的实现更稳。

真正影响体验的是**传输层参数**：BBRv3 拥塞控制、TLS Reality 伪装、UDP 转发质量。这些取决于**服务端**，客户端只负责正确握手。所以当你发现“换了客户端还是卡”，问题八成在节点侧。

## 四、细分人群与场景选型

- **纯小白 / 只求翻墙可用**：小火箭。买断、导入订阅、点连接，三步结束。别碰脚本。
- **重度去广告用户**：圈X。开屏广告、App 内信息流、网页浮窗，靠 `rewrite` + 脚本一套带走。
- **多机场多节点管理党**：圈X。它的策略组 + 脚本选路能做到「延迟最低自动切、故障自动降级」，小火箭的分组逻辑相对朴素。
- **手游玩家**：小火箭。UDP 转发实现更直接，配合专线（如 IEPL）在 40~70ms 区间比较稳；圈X 开一堆脚本反而增加抖动。
- **开发者 / 抓包党**：圈X。MITM + 脚本日志能当日志分析器用。
- **双设备用户（iPhone + Mac）**：小火箭有 Mac 版可共用生态，配置迁移成本低。

## 五、分平台实操配置与深度避坑

### 5.1 小火箭：正确姿势

1. **添加订阅**：首页右上角 `+` → 类型选 `Subscribe` → 粘贴链接 → 保存。不要用「扫码导入配置文件」的老路子，容易带进别人的分流。
2. **全局路由**：新手先用「配置」模式，别选「代理」全局，否则国内 App 也会绕路。
3. **开启连接日志**：设置 → 打开「连接」页面，排障时这是唯一有效证据。
4. **避坑**：任何声称「一键脚本自动订阅」的 `.conf`，导入前先文本看一眼有没有 `[Proxy]` 硬编码节点——那是在拿你的流量给别人做中转。

### 5.2 圈X：正确姿势

1. **先备份再改**：`资源 → 配置文件` 导出一次，改坏了能回滚。
2. **规则分层**：`[filter_local]` 放自己的直连/拦截，`[filter_remote]` 引用公开规则集，不要全塞本地。
3. **MITM 域名白名单**：只填真正需要改写的域名，例如 `api.xxx.com`。
4. **脚本**：`[rewrite_local]` 里挂 `script-response-body`，路径用本地 `Scripts/` 目录，别直接用远程 URL——远程脚本可变，等于给对方留了后门。
5. **避坑**：网上流传的「去广告全家桶配置」动辄开 30 多个 MITM 域名，**默认信任 = 默认裸奔**。

### 5.3 与节点侧的配合

客户端的策略组要能吃到节点标签。买机场时优先选**支持标准 Clash/V2Ray 订阅、明确标注线路类型**的服务商。比如极连云这类标注专线、支持主流订阅格式的服务，导入小火箭/圈X 都能一次成功，减少大量格式转换的折腾——具体测速数据可参考 [极连云深度评测](/reviews/jiliancloud/)。

## 六、抓包排障诊断手册（含命令与判定表）

iOS 本身不给你 `mtr`，但你可以**用同一网络下的 Mac/Linux** 做诊断，或者用 iSH 装轻量工具。以下命令在 macOS / Linux / WSL 直接可跑：

```bash
# 1) 链路逐跳质量：看哪一跳开始丢包/暴涨
mtr -rwzc 50 1.1.1.1

# 2) 分层耗时拆解：DNS / TCP / TLS / TTFB 各自花了多久
curl -o /dev/null -s -w "DNS:%{time_namelookup} TCP:%{time_connect} TLS:%{time_appconnect} TTFB:%{time_starttransfer} Total:%{time_total}\n" https://www.google.com

# 3) 端口连通性与抖动：判断节点是否假活
tcping -c 10 -i 0.2 1.1.1.1 443

# 4) UDP 质量（游戏/语音场景）
# 用 mtr 的 UDP 模式或 iperf3 -u 做背靠背测试
```

**判定表：**

| 现象 | 高概率根因 | 处置 |
|---|---|---|
| DNS 耗时 `> 800ms` | 走错 DNS 或被劫持 | 改客户端 DNS 为 DoH/远端解析 |
| TCP 正常但 TLS 卡 | 中间设备干扰 / 协议被干扰 | 换 Reality / 换端口 |
| TTFB 大、Total 更大 | 出口带宽被超售 | 换节点或换服务商 |
| mtr 第 3~5 跳开始丢包 | 跨境段拥塞 | 换专线入口 |
| tcping 全丢 | 节点假活 / 被封 | 立即切节点 |
| 单 App 慢、系统整体正常 | 分流规则误判 | 检查规则命中顺序 |

**圈X / 小火箭内建排查**：开启连接日志，看目标域名走了 `DIRECT` 还是 `PROXY`；如果是 `DIRECT` 却该走代理，八成是规则顺序写反了。

## 七、行业常见避坑矩阵

| 宣传话术 | 真实情况 | 识别方法 |
|---|---|---|
| 「永久免费不限量」 | 要么超售到没速度，要么在卖你的流量 | 看是否要求装证书 / 改 DNS |
| 「全网最低延迟 10ms」 | 大概率是本地环回测速或到入口的延迟 | 要求看**跨境落地**实测 |
| 「全解锁 Netflix/Disney+」 | 伪解锁：只改 DNS 骗过首页 | 播 1 分钟其实会报错 |
| 「IPLC 专线」 | 实为公网中转伪装 | 看晚高峰是否掉速 |
| 「一键脚本自动配置」 | 可能夹带节点或 MITM 域名 | 导入前审文本 |
| 「小火箭也能跑全套广告脚本」 | API 兼容性有限 | 跑不通别怪工具 |

## 八、常见问题排障 FAQ

**Q1：小火箭和圈X 能同时装吗？会不会打架？**
能装，但**同时只能有一个开启隧道**（iOS 会抢占 NEProvider），否则规则互相覆盖，出现诡异的间歇性断流。

**Q2：圈X 脚本跑不通，报 `$done is not defined`��**
八成是脚本按 Surge 写的，Surge 用 `$done()` 的语义略有差异，需要改成圈X 的 `$done({body})` 形式，或者用社区里标注 QX 专用的版本。

**Q3：小火箭导入订阅后节点名字乱码？**
机场用了 UTF-8 BOM 或特殊分隔符，属于订阅格式问题。可以让服务商换标准 Clash YAML，或手动改 `#` 注释行。

**Q4：开了 MITM 之后部分 App 打不开？**
MITM 域名开太野，把带证书校验（SSL Pinning）的 App 流量也拦了。把该 App 域名从 MITM 列表移除即可。

**Q5：两个客户端谁更省电？**
纯代理场景差别不大（都在 `1%/小时` 量级）。圈X 挂 10 个以上常驻脚本时，后台耗电会明显抬头，实测可差 2~3 倍。

**Q6：为什么我换了客户端速度没变？**
因为瓶颈在**服务端与线路**。客户端的差异主要体现在首包和调度，跨境吞吐量上限由节点侧决定。

**Q7：圈X 买了之后能退款吗？**
App Store 买断制，可通过苹果官方渠道申请退款，但次数有限，别拿这个当试用。
