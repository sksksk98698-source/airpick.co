# 套餐参数全解读：周期流量、重置日期、同时在线设备数与限速规则

## TL;DR · 三分钟结论先行

如果你只想带走三句话：

1. **流量不是越多越好，而是「重置方式 + 倍率 + 计费方向」的组合。** 一个「500G/月、自然月 1 号重置、全节点 x1、上下行双向计费」的套餐，实际可用价值可能低于一个「300G/30天滚动重置、核心节点 x1、仅计下行」的套餐。
2. **同时在线设备数限制的本质是 IP 并发 + 连接数配额，不是「你有几台手机」。** 大多数家庭会在路由器侧就撞上限制，而不是在手机上。
3. **限速条款里最坑的不是「限速到多少」，而是「什么时间段限速」「哪些节点限速」「是否共享限速池」。** 这三项没写清楚的，一律按最坏情况估算。

## 一、为什么同一份套餐，有人用得爽有人骂街？

在讨论参数之前，必须先建立一个认知：**机场卖的不是「流量」，而是「单位时间内的可用带宽资源」。** 流量只是计费单位，带宽才是真实成本。

### 1.1 物理层：光速延迟地板与线路等级

从上海到洛杉矶的直线距离约 10,400 公里，光纤中的信号传播速度约为真空光速的 2/3，单程理论延迟就约 52ms，往返（RTT）理论下限约 104ms。**这就是「光速地板」——任何宣称「上海到美西 80ms」的商家，要么在测内网中转段，要么在说谎。**

于是行业演化出几种线路分层：

| 线路类型 | 典型 RTT（沪→洛杉矶） | 成本量级 | 高峰期稳定性 |
|---|---|---|---|
| 普通公网 BGP 直连 | 160–260ms | 基准 1x | 抖动大，晚高峰易丢包 |
| CN2 GIA（电信精品网） | 130–160ms | 3–5x | 中等，仍受公网拥塞影响 |
| IEPL 国际以太网专线 | 110–135ms | 8–15x | 高，独立通道不受公网 QoS 影响 |
| IPLC 国际私有专线 | 105–130ms | 10–20x | 极高，点对点独占 |

**IEPL 与 IPLC 的核心差异**在于：IEPL 走的是二层以太网封装、可灵活组网、多用于多点互联；IPLC 是传统点对点专线，延迟更可控但扩容慢。高端机场通常是「入口 BGP 多线 + 中段 IEPL/IPLC + 出口多地区落地」的混合架构。

理解这一点后，你就能明白：**一个标注「500G」的 IEPL 套餐，其成本可能是同流量公网套餐的 5–10 倍。** 价格异常便宜又宣称全专线的，基本可以判定为虚假宣传或严重超售。

### 1.2 传输层：QoS 令牌桶与「限速」到底怎么实现的

机场的限速绝大多数通过 **Linux tc（traffic control）+ HTB 分层令牌桶** 实现。其机制是：为每个账号或每个连接分配一个令牌桶，桶以固定速率（如 100Mbps）补充令牌，数据包发送需消耗令牌，桶空了就排队或被丢弃。

这带来三个关键推论：

- **限速是「平均值」不是「瞬时值」。** 短时间突发可能超过限速值（因为桶里有余量），但持续下载会被压回均值。
- **限速通常作用在「账号维度」而非「设备维度」。** 也就是说，你 5 台设备同时跑，共享同一个 100Mbps 桶。
- **部分商家用 `tbf` 而非 `htb` 做简单限速**，会导致 TCP 重传率飙升、单线程速度崩坏——这类节点表现为「测速能上 200M，但下载文件只有 3MB/s」。

### 1.3 拥塞控制：BBRv3 / Cubic / 锐速的真实差异

很多人以为换内核算法能「突破限速」，这是误解，但算法确实影响**丢包环境下的实际吞吐**。

- **Cubic（Linux 默认）**：丢包即大幅降速，对跨境高丢包链路极不友好。
- **BBRv2 / BBRv3**：基于带宽时延积建模，丢包 5% 时仍能维持较高吞吐，是目前主流选择。
- **锐速 / LotServer**：老牌单边加速，对极端丢包场景有效，但 2026 年已基本被 BBRv3 取代。

**结论：如果商家服务端跑的是 BBRv3，你客户端用默认 Cubic 也能拿到不错的速度；但如果服务端是 Cubic，你在晚高峰就会比较难受。** 这一点在你选购前很难验证，只能通过实测判断。

### 1.4 伪装层：TLS Reality 与 uTLS 指纹

2026 年，主流协议已基本收敛到 **VLESS + Vision + Reality** 和 **Hysteria2 / TUIC** 两条路线：

- **Reality**：借用真实网站的 TLS 握手，服务端无需证书，抗主动探测能力强。缺点是依赖目标站点 SNI 的可用性。
- **Hysteria2**：基于 QUIC/UDP，拥塞控制用 Brutal，**在高丢包链路上表现极佳**，但对运营商 UDP QoS 敏感，部分场景会被限速。
- **uTLS 指纹伪装**：让 ClientHello 与 Chrome/Firefox 一致，对抗基于 JA3/JA4 的识别。

这些都会间接影响你「实际能跑多少」，但它不是套餐参数——**你要警惕的是那些把协议先进性当作「速度承诺」的营销话术。**

### 1.5 IP 资源层：广播 IP、原生 IP 与双 ISP 住宅 IP

这直接决定了「解锁能力」这个隐性参数：

- **广播 IP（Datacenter）**：机房 IP，Netflix 大概率只能看自制剧，ChatGPT 可能触发风控。
- **原生 IP**：注册地与实际落地一致的机房 IP，解锁能力中等偏上。
- **双 ISP 住宅 IP（Residential）**：由本地宽带运营商分配，解锁能力最强，成本也最高。

**避坑要点**：所谓「DNS 解锁」只是把流媒体请求重定向到解锁服务器，**你的出口 IP 并没有变**。这类解锁在 Netflix 风控升级后极易失效，且不适用于需要真实 IP 的服务（如银行、部分 AI 平台）。

## 二、核心参数对比矩阵：10 项量化指标一次说清

下表把套餐页面上最容易被忽略的参数拉出来横向对比。请对照你手上的套餐逐项核对。

| 参数项 | 常见写法 | 真实含义 | 你需要确认的问题 |
|---|---|---|---|
| 周期流量 | 100G / 500G / 1T | 一个计费周期内可用的总流量额度 | 是否区分上下行？内网中转段是否计费？ |
| 重置方式 | 自然月 / 滚动 30 天 / 购买日 | 额度刷新时间点 | 未用完是否结转？结转几期？ |
| 重置日期 | 每月 1 日 / 每月 15 日 | 具体刷新日 | 时区按 UTC 还是 UTC+8？ |
| 流量倍率 | x1 / x0.5 / x2 / x5 | 消耗倍率，实际可用 = 额度 ÷ 倍率 | 哪些节点是 x1？低价节点是否 x3 起？ |
| 计费方向 | 双向 / 仅下行 | 上行是否扣流量 | 上传备份、视频会议场景差异巨大 |
| 同时在线设备 | 3 台 / 5 台 / 不限 | 并发 IP 数或连接数 | 是 IP 数还是连接数？路由器算几台？ |
| 限速阈值 | 100Mbps / 500Mbps | 账号级速率上限 | 是单节点还是全账号共享？ |
| 高峰限速 | 20:00–24:00 降速 | 时段性 QoS | 高峰期限到多少？是否打折式降速？ |
| 到期策略 | 到期清零 / 冻结 30 天 | 流量与账号的处理 | 未用完流量是否可保留？ |
| 退款与试用 | 3 天无理由 / 不支持 | 售后条款 | 按已用流量折算还是全额？ |

**重点关注「流量倍率 × 计费方向 × 高峰限速」这个三重乘积。** 举例：

- 套餐 A：500G，全节点 x1，双向计费，晚高峰限速 100Mbps
- 套餐 B：300G，主力节点 x1 / 冷门节点 x3，仅下行计费，全时段不限速

如果你的使用场景是「白天办公 + 晚上看 4K」，**B 的实际体验大概率优于 A**，因为 4K 流媒体一小时约消耗 7GB，且以下行为主；而 A 的双向计费会在视频会议、云盘同步时快速吃掉额度。

## 三、细分人群与使用场景选型推荐

### 3.1 轻量办公 / 学术检索（月流量 `50G` 以内）

- **重点参数**：稳定性 > 流量 > 速度。ChatGPT、Claude、Google Scholar 对 IP 纯净度敏感。
- **建议**：选主力节点 x1、仅下行计费、设备数 ≥ 5 的中小套餐。不要贪便宜选大流量低质节点。

### 3.2 流媒体重度用户（月流量 300G–1T）

- **重点参数**：解锁能力、单节点带宽、是否限速。
- **建议**：确认 Netflix / Disney+ 是「原生解锁」还是「DNS 解锁」。4K 播放需要稳定 25Mbps 以上，**高峰限速若低于 50Mbps 会明显卡顿**。

### 3.3 远程开发 / 容器镜像拉取（月流量 1T+）

- **重点参数**：流量额度、是否双向计费、连接数限制。
- **建议**：`docker pull`、`npm install`、Git 大仓库克隆会产生大量下行流量。优先选「仅下行计费」+「高流量额度」。同时注意连接数限制——`npm` 并发请求会瞬间拉起几百个连接。

### 3.4 多设备家庭 / 小型团队（5 台以上设备）

- **重点参数**：同时在线设备数、账号级限速机制。
- **建议**：**路由器级代理会占用设备数配额**，这��最常见的踩坑点。若商家按「并发 IP」计数，一个路由器 + 两三个终端可能就直接顶到上限。选「设备数 ≥ 10」或明确写「不限设备但限速」的套餐。

### 3.5 极客 / 自建混合方案

- **重点参数**：协议支持度、是否有开放 API、是否允许中转自建。
- **建议**：优先选支持 Hysteria2 / TUIC 且提供订阅链接标准化的商家，便于对接 Clash Meta、sing-box 等内核。

## 四、分客户端 / 分平台实操配置与深度避坑

### 4.1 Clash Verge Rev（Windows / macOS）

- **订阅转换**：优先使用商家原生 Clash 订阅，避免第三方转换站的规则污染。
- **策略组设置**：把「AI 服务」「流媒体」「Telegram」分成独立策略组，避免全局走同一节点导致 IP 频繁切换触发风控。
- **`tun` 模式 vs 系统代理**：`tun` 模式能接管所有流量（含终端命令），但会占用更多连接数；系统代理更轻量但不接管 CLI。

```yaml
# 关键配置片段
dns:
  enable: true
  enhanced-mode: fake-ip
  fake-ip-range: 198.18.0.1/16
  nameserver:
    - https://223.5.5.5/dns-query
```

**避坑**：`fake-ip` 模式下，某些需要真实 IP 的应用（如部分游戏、局域网发现）会异常，可加 `fake-ip-filter` 白名单。

### 4.2 sing-box（iOS / Android / 路由器）

- iOS 端推荐 Shadowrocket 或 sing-box 官方客户端；Android 端推荐 NekoBox / sing-box。
- **路由器（OpenWrt）**：`tproxy` 模式对 TCP/UDP 都友好，但注意 `nftables` 与 `iptables` 规则冲突。
- **连接数陷阱**：BT 下载、P2P 会瞬间拉起数千连接，**极易触发商家的连接数限制被临时封禁**。路由器侧务必配置 `BT` 直连或限速规则。

### 4.3 移动端高铁 / 弱网场景

- 优先开启 Hysteria2 节点（QUIC 抗丢包）。
- iOS 上关闭「低数据模式」，否则系统会限制后台连接。
- 高铁场景下频繁切换基站，建议开启「节点自动测速切换」，阈值设为 200ms 以上再切换，避免抖动。

## 五、抓包排障诊断手册

当速度不达预期时，按以下顺序排查，不要盲目换节点。

### 5.1 链路质量检测

```bash
# 1. 路由追踪（100 个包，带 ASN 显示）
mtr -rwzbc 100 your-node-domain.com

# 2. TCP 层延迟与丢包（需安装 tcping）
tcping -t 20 -i 0.5 your-node-domain.com 443

# 3. 分阶段耗时拆解
curl -o /dev/null -s -w "DNS: %{time_namelookup}s | 连接: %{time_connect}s | TLS: %{time_appconnect}s | 首字节: %{time_starttransfer}s | 总计: %{time_total}s\n" https://www.google.com

# 4. 单线程下载测速（避免多线程掩盖问题）
curl -o /dev/null --limit-rate 0 -w "速度: %{speed_download} B/s\n" https://speed.cloudflare.com/__down?bytes=104857600
```

### 5.2 判定表

| 现象 | 可能的根因 | 处置建议 |
|---|---|---|
| `mtr` 第一跳就丢包 | 本地网络 / 路由器问题 | 检查网线、Wi-Fi 信道、路由器负载 |
| 中间跳丢包但末跳正常 | 运营商 QoS 或 ICMP 限速 | 属正常现象，无需处理 |
| 末跳丢包 `> 3%` | 服务端链路拥塞或超售 | 换节点，或联系商家 |
| `time_connect` 正常但 `time_starttransfer` 高 | 服务端处理慢 / 落地拥塞 | 换落地节点 |
| `time_appconnect` 异常高 | TLS 握手被干扰 | 检查是否被 SNI 阻断 |
| 测速快但实际下载慢 | 单线程被限速 / 令牌桶过小 | 测试单线程速度，参考 5.3 |

### 5.3 验证「是否被限速」

```bash
# 同时跑 4 个单线程下载，观察总带宽是否被压在某个整数附近
for i in 1 2 3 4; do
  curl -o /dev/null -w "线程$i: %{speed_download}\n" \
    https://speed.cloudflare.com/__down?bytes=52428800 &
done
wait
```

**判定逻辑**：若 4 线程总和 ≈ 100Mbps（12.5MB/s），说明触发了账号级限速；若总和远小于单线程 ×4，说明连接数或 CPU 存在瓶颈。

### 5.4 UDP / QUIC 可用性检测

```bash
# Hysteria2 依赖 UDP，若被运营商 QoS，速度会断崖式下跌
nslookup -type=HTTPS cloudflare.com
# 或直接用客户端内置的延迟测试，观察 UDP 端口是否可通
```

## 六、行业常见避坑矩阵

| 宣传话术 | 真实情况 | 识别方法 |
|---|---|---|
| 「全网不限速」 | 小字里写着「高峰期公平调度」 | 晚 20:00–23:00 实测单线程速度 |
| 「无限流量」 | 通常有「合理使用条款」，超量降速至 1Mbps | 查 ToS 中的 Fair Use 条款 |
| 「不限设备」 | 可能限制并发连接数或 IP 数 | 用 5 台设备同时测速，观察是否掉线 |
| 「全节点 IEPL」 | 大概率只有 1–2 个主力节点是专线 | 用 `mtr` 看中转段 ASN 是否一致 |
| 「原生 IP 解锁 Netflix」 | 可能是 DNS 解锁或共享 IP | 查 `ipinfo.io` 的 `type` 字段 |
| 「不限流量不限速不限设备」 | 典型超售，晚高峰必崩 | 试用期内做高峰压力测试 |
| 「终身套餐」 | 多为一次性流量包，用完即止 | 确认是「包月续费」还是「买断流量」 |

**超售识别技巧**：连续三天在同一时段测速，若速度方差极大（如 300Mbps → 20Mbps），说明该节点用户密度过高，带宽被严重争抢。

## 七、常见问题排障 FAQ

**Q1：流量每月几号重置？为什么我 1 号还是显示老额度？**
重置时间取决于商���的时区设定。部分商家按 UTC 0 点重置，对应北京时间 8:00；也有商家按购买日滚动重置。若 1 号上午未刷新，等到北京时间 8:00–9:00 再看。仍不刷新就提工单。

**Q2：我用路由器代理，为什么设备数限制很快就满了？**
因为大多数商家按「并发出口 IP」计数，你的路由器对外只有一个出口 IP，理论上只算一台。但若商家按「连接数」或「协议握手次数」计数，路由器下所有设备的请求会累加。**解决办法：优先选明确写「按 IP 计数」的商家。**

**Q3：套餐还剩 200G，为什么速度突然变成 2Mbps？**
三种可能：① 触发高峰限速；② 单节点被限速，换节点即可；③ 你的套餐有「高速流量额度」，超过后就进入低速通道。查套餐详情中的「高速流量」字段。

**Q4：为什么测速 300Mbps，下载文件只有 5MB/s？**
典型的多线程测速幻觉。Speedtest 类工具会开多个 TCP 连接，而单线程下载受 BDP（带宽时延积）和丢包影响。用 `curl` 单线程测试才是真实体验。跨境链路单线程速度通常只有多线程的 20%–40%。

**Q5：未用完的流量能结转到下个月吗？**
绝大多数机场不支持结转。少数支持「流量包叠加」的商家允许余额保留，但周期流量到期清零是行业默认规则。

**Q6：设备数超限会怎样？**
通常是新设备无法连接，已有连接不受影响；部分商家会临时封禁账号 5–30 分钟。**注意：频繁切换节点也会被误判为多设备。**

**Q7：为什么流媒体白天能解锁，晚上就失效？**
解锁能力与落地 IP 池的纯净度相关。晚高峰有大量用户使用同一 IP 池，被流媒体风控标记的概率大幅上升。**原生住宅 IP 的抗风险能力显著优于机房广播 IP。**
