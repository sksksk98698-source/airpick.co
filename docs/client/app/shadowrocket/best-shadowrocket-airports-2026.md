## 二、底层技术：iOS 上的"快"到底由什么决定

### 2.1 NEPacketTunnelProvider：小火箭跑在一个被严格限制的沙盒里

Shadowrocket 基于 iOS 的 Network Extension 框架，通过 `NEPacketTunnelProvider` 创建虚拟网卡接管流量。这意味着三件事：

1. **它拿不到系统的全部网络权限。** 相比 Clash Verge 在 macOS 上能用 `utun` + TUN 模式做完整的三层转发，iOS 上的实现必须受限，所以"iOS 上分流容易出岔子"是架构决定的，不全是客户端写得烂。
2. **规则匹配在用户态完成。** 每一条连接都要过一遍规则集，规则库过大（比如你导入了十几万条域名规则）会直接体现为**首包延迟**上升，而不是带宽下降。很多人测速看着挺快，却总觉得"点开网页要愣一下"，问题就出在这。
3. **后台会被挂起。** iOS 会主动回收后台 App 的 socket，长时间连接（SSH、数据库连接池）在切后台后断流是系统行为，不是机场的锅。想缓解只能开"按需连接"配合 `Always On VPN` 的描述文件（有风险，第 7 节会讲）。

### 2.2 入口链路：BGP 中转、IEPL、IPLC 的物理差异

这是选机场时的第一分水岭，也是宣传水分最大的地方。

| 类型 | 物理本质 | 典型延迟（华南→香港） | 晚高峰稳定性 | 成本量级 |
|---|---|---|---|---|
| 公网 BGP 中转 | 走公共互联网，靠 BGP 选路 | `40~120ms` 波动大 | 差，绕路明显 | 低 |
| 优化 BGP（CN2 GIA 等） | 特定运营商优质线路 | `30~60ms` | 中 | 中 |
| IEPL 国际以太网专线 | 二层专线，与公网隔离 | `10~35ms` | 好 | 高 |
| IPLC 国际私有专线 | 独占物理链路 | `15~40ms` | 极好 | 极高 |

关键点：**IEPL/IPLC 的价值不在于"快"，而在于"不堵"。** 公网线路在晚高峰 20:00–23:00 会经历骨干网拥塞，延迟从 `40ms` 飙到 `200ms` 并伴随丢包。专线绕开了这一段，所以它的曲线是平的。

识别真假专线的方法很简单：在**晚高峰**做 `mtr`，看第二跳之后是否还存在中国电信/联通/移动的骨干节点 IP。如果 `mtr` 里能看到 `202.97.x.x`（电信 163 骨干）或 `219.158.x.x`（联通 169 骨干），那它至少在入口段走了公网，所谓"纯专线"就打了折扣。

### 2.3 拥塞控制：BBRv3 与移动网络的化学反应

2026 年主流服务端已经普遍升级到 `BBRv3`。它相比 BBRv2 的核心改进是在**高丢包 + 高 RTT** 环境下更激进地探测带宽，同时降低了对随机丢包的过度反应。

这对 iOS 用户尤其重要，因为：

- 5G NR 下的无线侧丢包（`0.5%~2%`）是常态，不是异常。
- CGNAT（运营商级 NAT）导致端口映射不稳定，TCP 连接容易被重置。
- 手机在移动过程中频繁切换基站，RTT 抖动剧烈。

结论：**如果服务端还在用 CUBIC，你在 4G/5G 移动网络下的体验会明显差于用 BBRv3 的机场**，这个差距在弱信号环境下可以放大到 `2~3` 倍。选型时可以主动问客服内核版本，答不上来的基本就是盲盒。

### 2.4 协议层：TLS Reality 与 SNI 分流的现实意义

2026 年的现实是：单纯靠"加密"已经不够，流量**特征**才是被识别的对象。

- **TLS Reality：** 借用真实网站的 TLS 握手证书（如 `www.microsoft.com`），服务端不留自己的证书指纹。客户端的 ClientHello 与直连该网站几乎无差别。
- **uTLS 指纹伪装：** 让 Go 实现的 TLS 栈模拟 Chrome 的 JA3/JA4 指纹。缺了这一层，哪怕协议再新，指纹本身就会出卖你。
- **SNI 分流：** 机场入口按 SNI 把流量分发给不同落地，这决定了你能不能"一个订阅同时解锁日区和美区"。

在 Shadowrocket 里，这三项能力取决于你选的协议类型。`VLESS + Reality` 和 `Hysteria2` 是目前 iOS 上兼容性与隐蔽性平衡得最好的两个选项，后者在弱网下的表现尤其突出（基于 QUIC，无队头阻塞）。

## 四、细分人群与场景选型

### 4.1 轻度用户（社交 / 搜索 / AI 对话 / 邮件）

特征：月流量 `30~60GB`，单次连接时间短，对延迟敏感但对带宽不敏感。

选型建议：**IEPL 小流量年付套餐。** 这个人群最容易被"无限流量"的话术收割，实际上你一个月根本用不掉 `200GB`，多付的钱买的全是浪费的配额。微风网络在这个定位上做得比较克制——`50GB/月`起步、年付折合个位数月费，线路是 IEPL，正好卡在"够用且不贵"的区间。

### 4.2 流媒体重度用户

特征：4K 串流，单设备月流量 `300GB+`，对出口 IP 属性极度敏感。

选型建议：优先看**出口是否为原生 IP**，其次看单节点带宽是否稳定在 `200Mbps` 以上。注意，"能打开 Netflix"和"能稳定看 4K"是两回事，前者可能只是 DNS 解锁，实际播放会降码率到 480p。

### 4.3 远程办公 / 开发者 / 长连接

特征：SSH、数据库连接池、CI/CD 拉取镜像、长时间视频会议。

选型建议：**丢包率是一票否决项。** 同时关注是否支持 `TCP` 长连接保活和国内直连分流（避免把公司内网流量也送出去）。开发者还应关注是否提供 `UDP` 转发能力，否则 QUIC 协议的应用会退化到 TCP。

### 4.4 多设备家庭 / 跨平台

特征：iPhone + Mac + iPad + 电视盒子同时在线。

选型建议：看**同时在线设备数**是否够用，以及是否同时提供 Shadowrocket（iOS）、Clash（桌面/路由）、Surge 等格式的订阅。只支持单一客户端格式的机场，跨平台体验会很割裂。

### 4.5 游戏加速

特征：对延迟和抖动极度敏感，但对带宽要求低。

选型建议：看**抖动（jitter）**而不是平均延迟。一个平均值 `60ms` 但抖动 `±5ms` 的节点，游戏体验远好于平均值 `40ms` 但抖动 `±50ms` 的节点。

## 五、Shadowrocket 实操配置：分场景调优

### 5.1 订阅导入的三种方式

1. **扫码导入（推荐）：** 机场后台生成二维码，小火箭首页右上角 `+` 扫描即可。优点是订阅 URL 不会暴露在剪贴板历史里。
2. **URL 导入：** 复制订阅链接，小火箭 `+` → 类型选 `Subscribe` → 粘贴。注意部分机场默认给的是 Clash 格式，需要在小火箭里选择"从订阅转换"或手动换成通用格式。
3. **手动添加：** 只在订阅失效时作为应急手段，日常不推荐，因为无法自动更新。

### 5.2 全局路由与分流配置

小火箭的"全局路由"有四个选项，实际只有两个有意义：

- **配置（Config）：** 使用规则分流。这是唯一正确的日常选择。
- **代理（Proxy）：** 全量走代理。仅在分流规则出错时临时排查用。

导入订阅后，务必在 `设置 → 配置` 里确认规则集已生效。一个常见的坑是：订阅链接里带了 `&flag=clash` 这类参数，小火箭拉下来的规则格式不兼容，导致规则集为空，此时所有流量会走"兜底策略"。表现就是——国内 App 也走代理了，微信发消息转圈。

### 5.3 DNS 配置

推荐组合：

- 国内域名 → 运营商 DNS 或 `223.5.5.5`
- 国外域名 → `1.1.1.1` 或 `8.8.8.8`，走代理查询
- 开启 `DoH`（DNS over HTTPS）防止 DNS 污染

小火箭里在 `设置 → DNS` 中配置。注意：**不要**把 DNS 设成 `1.1.1.1` 却让 DNS 查询走直连，这会导致解析结果被污染，表现为"节点能连上但网页打不开"。

### 5.4 节点测速与真实延迟

小火箭内置的延迟测试本质是 `TCP` 三次握手耗时（或 `ICMP`），**它只反映 RTT，不反映带宽和丢包**。一个大带宽高丢包的节点可能测出 `30ms`，但实际下载速度很惨。

正确做法：先看延迟筛掉明显异常的节点，再用"网络诊断 → 速度测试"或实际下载大文件验证带宽，最后在晚高峰再测一次确认稳定性。

### 5.5 按需连接与省电

iOS 后台限制决定了代理常驻会耗电。建议：

- 开启 `按需连接`，仅在特定 Wi-Fi / 蜂窝网络下激活。
- 关闭"始终开启 VPN"的 `Always On` 描述文件（除非你确实需要，见第 7 节风险说明）。
- 在 `设置 → 高级` 中关闭不必要的连接日志记录。

## 六、抓包排障诊断手册

网络问题分三类：**链路问题（机场侧）**、**配置问题（客户端侧）**、**系统问题（iOS 侧）**。下面的命令帮你快速定位到具体哪一层。

> 说明：iOS 本身没有完整的命令行环境，以下命令建议在**同一局域网内的 Mac** 上执行，或在 `iSH` / `a-Shell` 这类 iOS 终端里执行简化版本。所有命令均需 `sudo` 权限的已在注释中标出。

### 6.1 基础连通性

```bash
# 测试目标端口是否可达，比 ping 更准（ping 可能被 ICMP 限速）
tcping -t 5 -p 443 hk1.example.com

# 连续测试 20 次，观察丢包和抖动
tcping -c 20 -p 443 hk1.example.com
```

### 6.2 路由追踪：判断是否真的走专线

```bash
# -r 显示 AS 号，-w 宽输出，-z 显示丢包，-b 显示 IP 和域名，-c 100 采样 100 次
sudo mtr -rwzbc 100 1.1.1.1
```

**判定规则：**

| mtr 现象 | 含义 | 处置 |
|---|---|---|
| 第 2~4 跳出现 `202.97.x.x` / `219.158.x.x` | 入口走了公网骨干，非纯专线 | 降低对该机场"专线"宣传的信任度 |
| 中间某跳丢包但末跳不丢 | ICMP 限速，正常现象，无需处理 | 忽略 |
| 末跳持续丢包大于 `2%` | 链路真实拥塞 | 换节点或换机场 |
| 路径跳数超过 `20` 跳 | 绕路严重 | 换同区域其他节点对比 |
| 晚高峰延迟比白天高 `3` 倍以上 | 公网拥塞，未走专线 | 一票否决 |

### 6.3 DNS 排查（macOS）

```bash
# 查看当前系统使用的 DNS 服务器
scutil --dns | grep nameserver

# 查看 Wi-Fi 接口的详细网络信息，包括 DNS、网关、路由器
networksetup -getinfo "Wi-Fi"

# 指定 DNS 查询，绕过缓存
dig +short @1.1.1.1 www.google.com

# 追踪 DNS 解析全过程，定位污染发生在哪一步
dig +trace www.google.com

# 对比不同 DNS 的解析结果，结果不一致通常意味着污染
nslookup www.google.com 223.5.5.5
nslookup www.google.com 8.8.8.8
```

### 6.4 应用层验证

```bash
# 测试 HTTPS 握手耗时（不下载内容）
curl -o /dev/null -s -w "DNS: %{time_namelookup}s  TCP: %{time_connect}s  TLS: %{time_appconnect}s  总计: %{time_total}s\n" https://www.google.com

# 测试实际下载速度（下载 10MB 计时）
curl -o /dev/null -s -w "%{speed_download} bytes/s\n" https://speed.cloudflare.com/__down?bytes=10000000

# 查看 TLS 证书链，确认是否被中间人劫持
openssl s_client -connect www.google.com:443 -servername www.google.com &lt; /dev/null
```

**应用层判定表：**

| 指标 | 正常范围 | 异常含义 |
|---|---|---|
| `time_namelookup` | 小于 `0.05s` | 超过 `0.5s` → DNS 污染或 DNS 服务器响应慢 |
| `time_connect` | 小于 `0.3s` | 超过 `1s` → 链路 RTT 高或 TCP 被重置 |
| `time_appconnect` | 小于 `0.5s` | 异常高 → TLS 握手被干扰 |
| `speed_download` | 大于 `5MB/s` | 低于 `1MB/s` → 带宽受限或严重超售 |

### 6.5 端口与 UDP 连通性

```bash
# 测试 UDP 端口（Hysteria2 需要 UDP 通）
nc -vzu hk1.example.com 443

# 检查本地是否有程序占用代理端口
lsof -i :1080
lsof -i :6152
```

## 七、行业避坑矩阵

这一节是干货中的干货。以下每一条都是真实踩坑案例的抽象。

| 宣传话术 | 真实含义 | 识别方法 | 避坑建议 |
|---|---|---|---|
| "无限流量，不限速" | 有隐性公平使用策略（FUP），超量后限速到 `1Mbps` | 问客服具体限速阈值，含糊其辞的即是 | 远离，除非你确认自己用不到阈值 |
| "纯 IPLC 专线" | 只有部分节点是专线，其余是公网 | 晚高峰 `mtr` 看第二跳 | 逐节点验证，别信整体宣传 |
| "节点数量 200+" | 大量节点共享同一台落地，超售严重 | 测速多个"不同地区"节点，IP 段高度重合 | 节点数量从来不是优势，质量才是 |
| "全流媒体解锁" | DNS 解锁伪装成原生解锁 | 打开 Netflix 看是否只能播放自制剧；查 IP 的 `whois` 归属 | 要求提供原生 IP 证明 |
| "支持所有客户端" | 只提供 SS 订阅，其他靠第三方转换 | 直接问订阅格式 | 要求提供 Shadowrocket 专用订阅 |
| "免费试用 7 天" | 试用节点和付费节点是两套服务器 | 试用期测速，付费后对比 | 付费前先小额月付验证 |
| "老牌机场，运营 5 年" | 域名可能刚注册 | `whois` 查域名注册时间 | 域名年龄小于 `1` 年需谨慎 |
| "送独家客户端" | 引导安装第三方描述文件或企业证书 | 检查是否要求安装 `VPN` 描述文件 | **绝对不要**安装来源不明的描述文件 |

**关于描述文件的特别警告：** iOS 上安装 `Always On VPN` 描述文件会授予该配置持续接管网络的能力，且部分描述文件包含设备管理权限。除非是你能完全信任的服务商，否则不要安装。这是 iOS 独有的高危风险点，安卓用户不会有这个概念。

## 八、常见问题 FAQ

**Q1：订阅导入后，所有节点都显示超时，是机场跑路了吗？**

先别急着下结论。按顺序排查：

1. 关闭代理，直接访问机场官网，网站能不能打开？打不开 → 可能真的是网站被墙或跑路。
2. 官网能打开但订阅链接拉不下来 → 是订阅 URL 被墙，尝试用国内可访问的镜像订阅地址。
3. 订阅拉下来了但节点全超时 → 本地网络问题，切换 Wi-Fi/蜂窝网络重试。
4. 以上都正常 → 用小火箭的"网络诊断"功能查看具体错误码。

**Q2：为什么同样一个订阅，在我安卓手机上飞快，iPhone 上很慢？**

大概率是三个原因之一：安卓端用的是 `TUN` 模式 + 更宽松的分流规则；iOS 端规则集过大导致首包延迟高；或者安卓端用了 `Hysteria2` 而 iOS 端因为配置错误退化到了 `SS`。检查两端的协议是否一致。

**Q3：小火箭开着代理，微信、银行 App 就报错怎么办？**

这是分流规则没生效，国内流量被送出去了。检查 `设置 → 配置` 里的规则集是否加载成功，以及"全局路由"是否误设为"代理"。银行 App 通常还会检测代理环境，建议在规则里把银行类域名加入直连。

**Q4：延迟只有 `20ms`，但打开 YouTube 还是要转圈？**

延迟低不代表带宽够。`20ms` 只说明 TCP 握手快，转圈是因为带宽被超售或落地出口拥塞。用第 6.4 节的 `curl` 测试实际下载速度，如果低于 `1MB/s`，问题在带宽不在延迟。

**Q5：小火箭特别耗电，正常吗？**

代理常驻确实会增加耗电，但正常情况下后台耗电应该小于 `5%`。如果超过 `15%`，检查是否开启了详细日志记录、是否有 App 在持续发起连接、或者节点是否在反复重连（重连会持续唤醒网络栈）。

**Q6：换新 iPhone 后，小火箭配置全丢了怎么恢复？**

Shadowrocket 支持 iCloud 同步，前提是你在旧设备上开启了 `设置 → iCloud 同步`。如果没有开，只能重新导入订阅。建议的备份方案是：把订阅 URL 存在密码管理器里，规则配置导出为文件存 iCloud Drive。注意订阅 URL 本身就是凭证，泄露等于账号泄露。
