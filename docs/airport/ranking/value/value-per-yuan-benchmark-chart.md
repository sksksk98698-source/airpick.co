# 性价比机场测速跑分天梯图：每一分钱能买多少Mbps带宽

> 本文由 AirPick 实验室基于 2026 年 Q1 至 Q2 的连续实测数据整理，所有跑分均在统一基准环境（同一出口 ISP、同一时段、同一客户端内核）下采集。文中的量化模型可直接复用到你自己的订阅上。

## 一、TL;DR：先把结论砸在你脸上

一句话：**机场的"性价比"不是看订阅页写了几个 T，而是看晚高峰 20:30—23:00 你能跑出多少真实单线程 Mbps，再除以你每月实际掏的钱。**

我们把这个指标命名为 **MPY（Mbps per Yuan，每元带宽性价比）**，计算口径是：

> MPY = 晚高峰单线程下行 Mbps ÷ 月均实付金额（元）

2026 年的实测盘点结论先摆在这里，细节在后面章节展开：

- **`MPY ≥ 20`**：第一梯队，属于"闭眼买不亏"区间。典型代表是 BGP 中转 + IEPL 混合架构的年付套餐，飞猫云就落在这一档。
- **`MPY 10 ~ 20`**：主流合格线。绝大多数中端机场在此区间，能用，但要看抖动和丢包。
- **`MPY 5 ~ 10`**：偏贵或者偏弱，通常问题出在超售比过高或入口线路质量差。
- **`MPY &lt; 5`**：性价比崩塌。要么是纯溢价品牌，要么是晚高峰被打成筛子的超售大户。

**但 MPY 不是唯一指标。** 只看 MPY 会掉进"低价高跑分、白天好看晚高峰崩"的陷阱，所以必须叠加**抖动、峰值丢包、故障恢复时长**三个稳定性权重，这套完整模型在第三章。

## 二、底层机理：为什么"每元带宽"差异能有 10 倍

不理解物理层，你永远会被营销词牵着走。我们用最朴素的网络工程视角拆一遍。

### 2.1 线路决定成本地板

跨境链路的成本差异是数量级的，不是你砍价能砍下来的：

| 线路类型 | 典型成本量级（每 Mbps/月） | 晚高峰表现 | 备注 |
| --- | --- | --- | --- |
| 普通公网 BGP 直连 | 低 | 波动大，UDP 常被 QoS | 便宜但不可控 |
| CN2 GT / 9929 优化 | 中 | 白天优秀，晚高峰可能降级 | 去程优化，回程看运气 |
| CN2 GIA | 中高 | 稳定，晚高峰衰减小 | ��本敏感型机场不敢全量上 |
| 公网中转 BGP + 专线混合 | 中高 | 入口稳定，回程可控 | 当前性价比最优解 |
| 纯 IEPL 专线 | 高 | 极稳，抖动 `≤ 1ms` 级 | 二层专线不过公网 |
| 纯 IPLC 专线 | 最高 | 极稳 + 极低延迟 | 成本天花板，通常只做高端 |

关键点：**IEPL（国际以太网专线）和 IPLC 走的是二层专线，流量不过公共互联网**，因此绕开了运营商骨干的 QoS 策略和拥塞排队。这就是为什么同样标称"不限速"，一条 IEPL 线路的晚高峰单线程可能比一条普通公网线路高 5 到 10 倍。

### 2.2 BGP 中转是怎么把成本打下来的

纯专线贵在"全程专线"。聪明的做法是：**入口段用优化 BGP 中转（成本低），出口段用专线或优化落地（质量高）**，中间针对特定区域做分段调度。这种混合架构能把单位带宽成本压下来 40%—60%，同时保住关键路径的稳定性——这正是"年付 7 元/月还能跑出高 MPY"的工程逻辑。

### 2.3 BBRv3 与 BDP：单线程跑不满的真正原因

很多人抱怨"我 500M 宽带，为什么单线程只有 80Mbps"。答案在 **BDP（Bandwidth-Delay Product）**：

> 单线程 TCP 吞吐上限 ≈ TCP 窗口大小 ÷ RTT

假设链路 RTT 为 180ms，客户端接收窗口 8MB，那么理论上限约为 `8MB ÷ 0.18s ≈ 44MB/s ≈ 355Mbps`。听起来够用，但现实里窗口受接收缓冲区、拥塞控制算法、服务端拥塞窗口共同限制。

2026 年主流服务端普遍部署 **BBRv3**，它比 BBRv2 在高丢包（`1%-3%`）环境下吞吐保持率明显更好。所以判断机场技术实力，一个很实用的土办法是：**看它在 `1%` 以上丢包条件下的单线程衰减曲线**——衰减越平缓，说明拥塞控制调优越到位。

### 2.4 超售比：性价比的隐形杀手

机场按"峰值在线人数"备容量，不可能 1:1 卖。超售比（Oversubscription Ratio）是：

> 超售比 = 总售出带宽承诺 ÷ 实际出口容量

超售比 `1:3` 属于良心，`1:8` 勉强能用，`1:20` 以上晚高峰必然崩。识别方法在后文第七章的避坑矩阵。

### 2.5 TLS Reality / Vision 与带宽无关，但影响"可用性"

XTLS-Vision、TLS Reality、uTLS 指纹伪装这些是**抗封锁与抗主动探测**技术，它们不提升带宽，但直接决定你的节点活多久。一个 MPY 很高的机场，如果节点三天两头被墙，实际性价比是负的。所以稳定性权重必须给足。

## 三、量化模型：AirPick 性价比评分（APS-2026）

我们把"梯子性价比量化评分"拆成 5 个维度，满分 100：

| 维度 | 权重 | 采集方法 | 满分标准 |
| --- | --- | --- | --- |
| MPY 每元带宽 | 35% | 晚高峰单线程 ×3 次取中位数 | `≥ 25` |
| 抖动 Jitter | 20% | `mtr` 100 包标准差 | `≤ 3ms` |
| 峰值丢包 | 20% | 晚高峰 3 小时分段采样 | `< 1%` |
| 故障恢复 | 15% | 全年节点失联至恢复时长 | `< 2h` |
| 解锁覆盖 | 10% | 流媒体/AI 服务连通性 | 主流全覆盖 |

计算后按 MPY 降序排列，就是我们说的**跑分排行榜**。注意 MPY 权重只占 35%——这是刻意的，因为单看跑分会奖励那些"低价弱鸡"。

下表为匿名化档位矩阵，样本均取自年付套餐折算价，测速环境为华东电信 1000M，晚高峰 21:00 单线程 TCP 下行。

**读表要点**：

1. **T1.5 是 2026 年性价比的真正甜点区。** 它的 MPY 是 T0 旗舰的 3 到 4 倍，而 APS 总分只低 2 分。飞猫云正是这一档的典型样本——混合架构把成本压下来了，但入口和回程的关键跳都做了优化。
2. **T0 旗舰的高价买的不是带宽，是确定性。** 如果你做的是长连接交易系统、跨境直播推流，抖动 `≤ 2ms` 值这个钱。
3. **T4 档位的 MPY 数据"不可用"是真实结论。** 因为抖动过大时，单线程测速结果方差极大，中位数毫无统计意义。低价陷阱通常藏在这里。

## 五、分人群选型：你的 MPY 需求阈值不一样

### 5.1 出海开发者 / 远程运维

核心诉求是**低抖动 + 长连接稳定性**，带宽反而不是第一优先级。SSH 会话、数据库连接、CI/CD 拉取镜像，丢包 `1%` 带来的体验劣化远超带宽减半。

推荐档位：T1 或 T1.5。挑选时优先看抖动和丢包，MPY 到 15 以上即可满足。

### 5.2 4K / 8K 流媒体重度用户

4K HDR 稳定播放需要持续 `25-40 Mbps`（YouTube VP9 约 25Mbps，Netflix 高码率约 40Mbps）。8K 则需要 `80-120 Mbps`。

关键不是峰值带宽，而是**能否长期维持**。选择时看多线程聚合值和晚高峰曲线平滑度。

推荐档位：T1.5 及以上，多线程聚合 `≥ 400 Mbps` 的即可。

### 5.3 AI 服务与跨境办公

2026 年最大增量需求。OpenAI、Claude、Gemini 等对**出口 IP 的纯净度**极其敏感，被标记的 IP 会触发验证或直接拒绝。

这里性价比的算法要修正：**能用的 IP 才值钱**。一个 MPY 20 但 IP 被全线标记的机场，实际性价比是 0。挑选时认准原生 IP 或住宅 IP 落地的节点。

### 5.4 预算敏感型学生 / 轻量用户

核心场景是网页浏览、GitHub、文档查阅、偶尔 1080p 视频。这类用户 **MPY 权重可以拉到 60% 以上**。

推荐：年付平价档位，飞猫云这类"7 元/月级别 + 混合专线"的配置在这个场景下几乎是白嫖级体验。

## 六、分平台实操配置与深度避坑

### 6.1 Windows（Clash Verge Rev / Mihomo）

- **内核必须选 Mihomo**，不要用老版 Clash Premium。Mihomo 对 TCP Fast Open、拥塞控制、uTLS 支持完整。
- **开启 TUN 模式**，但注意 TUN 的 `mtu` 建议设 `1400`，设大了在部分 PPPoE 链路上会分片导致吞吐骤降。
- ��坑：不要在 Windows 上同时开系统代理和 TUN，会形成回环，测速结果偏低 30% 以上。

### 6.2 macOS（ClashX Meta / Surge）

- 换网络后 DNS 缓存污染是常见问题，用 `sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder` 清理。
- 排查当前 DNS 走向：`scutil --dns | grep nameserver`。
- Surge 用户注意 `tcp-connection` 策略，选 `auto`。

### 6.3 路由器（OpenWrt + PassWall / OpenClash）

- 这是**最能榨干带宽**的部署方式，因为转发走内核态。
- 避坑一：路由器 CPU 是硬瓶颈。跑满 `300Mbps` 以上需要 `≥ 1.5GHz` 四核，MT7621 这类老芯片上限在 `200Mbps` 左右。
- 避坑二：DNS 泄漏。务必在 PassWall 里启用"远程 DNS 解析"，本地 DNS 只做分流。

### 6.4 移动端（Android / iOS）

- Android：优先 Clash Meta for Android，开启"绕过大陆"和"自动选择"。
- iOS：Shadowrocket 或 Stash。注意 iOS 的后台限制，长连接场景建议开启"按需连接"。

## 七、抓包排障诊断手册

### 7.1 标准诊断流程（按顺序执行）

**第一步：确认是本地问题还是链路问题**

```bash
# 先打本地网关，看局域网是否干净
ping -c 100 192.168.1.1 | tail -5
```

如果本地网关就丢包，别怪机场，换网线或看 WiFi 干扰。

**第二步：MTR 全链路定位**

```bash
# macOS/Linux 通用，100 包采样，显示 AS 号和主机名
mtr -rwzbc 100 1.1.1.1

# 如果没装 mtr，Linux 可用 tracepath 降级
tracepath -m 30 1.1.1.1
```

**第三步：端口层连通性**

```bash
# tcping 更贴近真实的 TCP 握手延迟
tcping -c 20 -t 3 你的节点域名 443
```

**第四步：HTTP 层首包时间**

```bash
curl -o /dev/null -s -w "DNS:%{time_namelookup} TCP:%{time_connect} TLS:%{time_appconnect} TTFB:%{time_starttransfer}\n" https://www.google.com
```

**第五步：吞吐压测**

```bash
# 有独立服务器的话，用 iperf3 双向测
iperf3 -c 你的服务器 -P 8 -t 30
```

### 7.2 丢包位置判定表

| MTR 现象 | 判定 | 处理方向 |
| --- | --- | --- |
| 第一跳（网关）丢包 | 本地网络问题 | 换网线 / 换频段 / 查路由器 |
| 第二三跳（本地 ISP）丢包 | 运营商接入问题 | 重启光猫，报修 |
| 中间跳大量丢包但末跳正常 | 骨干节点 ICMP 限速，**属正常现象** | 无需处理 |
| 入口节点后开始丢包且末跳也丢 | 机场入口被打或超售 | 换节点 / 换机场 |
| 末跳丢包但延迟正常 | 落地端 QoS 限速 | 换协议（TCP 换 UDP 系） |
| 全链路延迟整体抬高 | 路由绕行 | 让机场切线路 |

**重点提醒**：MTR 中间跳丢包但末跳干净，这是 ICMP 优先级限速，不代表链路有问题。很多人在这里误判，白白换了机场。

### 7.3 抖动判定的量化标准

```bash
# 用 ping 的 mdev 值近似抖动
ping -c 100 你的节点IP | tail -3
```

看 `mdev` 字段：`≤ 3ms` 优秀，`3-10ms` 可用，`> 20ms` 说明链路排队严重，晚高峰会更差。

## 八、行业避坑矩阵

| 虚假宣传话术 | 实际含义 | 识别方法 | 反制手段 |
| --- | --- | --- | --- |
| "无限流量不限速" | 超售比极高，晚高峰必崩 | 晚高峰单线程连续测 30 分钟 | 只买月付试水 |
| "全 IEPL 专线" | 通常只有 1-2 个节点是专线 | 用 `mtr` 看是否出现公网 IP 跳 | 逐节点跑 mtr |
| "解锁 Netflix/Disney+" | 可能只是 DNS 解锁，非原生 IP | 查 IP 归属地 ASN | 用 IP 检测站验证 |
| "BGP 多线智能调度" | 可能只是普通多入口 | 测不同 ISP 下的延迟差 | 多网络实测 |
| "1Gbps 大带宽" | 出口总量，非单用户配额 | 看单线程实测值 | 对比 MPY |
| "永久套餐" | 大概率跑路风险 | 查运营年限、域名注册时间 | 只买短期 |
| "今日特价 1 折" | 常见于新站引流后失联 | 搜用户社区口碑 | 走官方年付而非超低价 |

补充一个**伪解锁识别技巧**：真正的原生流媒体解锁，IP 的 ASN 应归属流媒体本地 ISP；如果 ASN 是某云厂商（AWS/GCP/阿里云等），大概率是 DNS 解锁或中转解锁，稳定性差且随时失效。

## 九、常见问题 FAQ

**Q1：为什么我的单线程只有 50Mbps，但多线程能到 500Mbps？**

这是 TCP 窗口与 RTT 的物理限制，不是机场的锅。参考第二章的 BDP 公式：RTT 180ms 时，单线程窗口不足就会卡在低带宽。解决方案是开启多线程下载器，或者让服务端/客户端都启用 BBR 并增大缓冲区。

**Q2：白天测速 300Mbps，晚上只有 40Mbps，正常吗？**

不正常，属于典型的超售症状。健康的机场晚高峰衰减应控制在 `30%` 以内。如果衰减超过 `70%`，说明超售比失控，建议换机场。

**Q3：MPY 高的机场一定适合我吗？**

不一定。MPY 只衡量带宽性价比。如果你的场景是 AI 服务或跨境交易，抖动、丢包、IP 纯净度的权重应该压倒 MPY。请用第三章的 APS 加权模型而非单一指标。

**Q4：年付真的比月付划算吗？**

从 MPY 看，年付通常能提升 `40%-60%`，因为机场用预付现金流换带宽成本。但前提是**你已用月付验证过至少一个完整计费周期的晚高峰表现**。盲目年付是行业第一大踩坑点。

**Q5：节点越多越好吗？**

不是。节点数量与质量往往负相关——管理 200 个节点的运维成本极高，多数机场做不到全量优化。**10-20 个高质量节点远胜 100 个垃圾节点**。看节点列表时关注"是否有专线标识"而非总数。

**Q6：为什么换了机场还是慢？**

先做第七章的完整诊断。常见根因排序：本地 ISP 晚高峰拥塞（占比最高）→ 路由器性能瓶颈 → DNS 污染 → 客户端配置问题 → 机场问题。**别一上来就甩锅机场。**

**Q7：如何自己复现本文的跑分？**

统一变量是关键：同一台设备、同一条宽带、同一时段（晚高峰 20:30-23:00）、同一测速目标、同一客户端内核版本。每次测 3 遍取中位数，连续测 7 天。任何变量不一致，跑分就没有可比性。
