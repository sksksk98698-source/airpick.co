## 二、晚高峰为什么必然掉速：五个物理层面的硬约束

很多人把「晚高峰卡」归结为「机场超售」，这是对了一半。超售只是放大器，真正的病根在下面五层。

### 2.1 国际出口拥塞：物理带宽是死的

中国电信 163 骨干（AS4134）、联通 169（AS4837）、移动 CMI（AS58453）的国际出口总带宽是物理定值。晚上 20:00 之后，全国用户并发拉流，出口方向利用率常年在 85%–95% 区间震荡。**拥塞一旦形成，排队延迟（bufferbloat）会从 30ms 飙到 300ms+，TCP 的 CUBIC 拥塞控制会剧烈回退窗口**，你测出来的 200Mbps 会在 3 秒内跌到 8Mbps。

### 2.2 运营商 QoS：不是「限速」，是「降优先级」

三大运营商对出境流量的 QoS 策略并非简单砍带宽，而是：

- **DSCP 重标记**：把非签约类流量标记为 AF1x/BE，路由器在拥塞时优先丢弃；
- **令牌桶整形（policing）**：突发流量超过阈值直接丢包，而非排队；
- **UDP 优先丢弃**：这是为什么 UDP 加速（Hysteria2 / TUIC）在晚高峰经常「看起来快但视频卡」——测速曲线漂亮，因为 UDP 丢包后重传开销低，但 TCP 长连接被压得更狠。

**能规避 QoS 的唯一办法：不让流量进公网国际出口。** 这就是 IEPL / IPLC 的全部价值。

### 2.3 IEPL / IPLC / BGP 中转：三种形态的本质区别

| 形态 | 数据路径 | 是否过公网出口 | 晚高峰抗性 |
| --- | --- | --- | --- |
| IEPL | 入口机房 → 内网以太专线 → 境外 PoP | 否（全程内网） | 极强 |
| IPLC | 入口机房 → 点对点国际专线 → 境外 PoP | 否（电路独占） | 极强，但带宽死板 |
| BGP 中转 | 入口机房 → 公网骨干 → 境外 PoP（多跳优化） | 是 | 取决于中转质量 |
| 直连 | 用户本地 → 公网出口 → 境外 VPS | 是 | 最弱 |

注意一个常见话术陷阱：**「BGP 中转优化」≠ 专线。** 中转只是把「你在家拉海外」变成「你在国内机房拉海外」，绕开了你本地宽带的出口瓶颈，但机房的出境口照样被 QoS。真正的分水岭是那一句：**这段路是内网，还是公网。**

### 2.4 BBRv3 vs CUBIC：拥塞控制算法决定「抗丢包能力」

晚高峰公网丢包 3% 是常态。此时：

- **CUBIC**：把丢包当拥塞信号，窗口直接砍半，吞吐断崖；
- **BBRv1**：以带宽和 RTT 建模，丢包不敏感，抗丢包强但抢占性过强；
- **BBRv3**：引入 ECN 感知与更激进的探测，在 5% 丢包下仍能维持 70%+ 吞吐，且比 v1 更公平。

所以你测速时看到「别人同线路 40Mbps，你只有 6Mbps」，很可能不是线路差异，而是**服务端有没有开 BBRv3**。这一点在自建 VPS 上尤其明显。

### 2.5 双 ISP 入口与 TLS Reality

**双 ISP 入口**指机场在国内入口同时接入电信 + 联通（或移动）两条链路，晚高峰哪条拥塞就走另一条。实测能挽回 15%–30% 的晚高峰吞吐。

**TLS Reality** 是 2026 年的主流抗封锁方案：服务端借用真实大站的 TLS 证书指纹（如 `www.microsoft.com`），握手阶段不暴露自签证书，主动探测无法复现握手。与之相对的是裸 VMess + 自签证书，在晚高峰的 SNI 阻断窗口期极易被 reset，表现为「能连上但速度 0」。

**结论：晚高峰的表现 = 线路形态（60%）+ 拥塞控制（20%）+ 入口冗余与协议伪装（20%）。**

## 三、测试方法论：让榜单可复现

拒绝「某节点测出 1Gbps」这种孤立截图。AirPick 的测试规范如下：

1. **时间窗**：工作日 20:00–23:30，每小时采样一次，取 15 次中位数（避免峰值美化）。
2. **入口**：电信 / 联通 / 移动家宽各 3 条，均为 500Mbps 以上物理接入。
3. **指标**：单线程 vs 四线程吞吐、TCP 重传率、RTT 抖动（jitter）、8K 起播时间、8K 连续播放 10 分钟卡顿次数。
4. **剔除干扰**：关闭本机所有 P2P、系统更新、iCloud 同步；有线连接；DNS 统一为 `1.1.1.1`。

复现命令（macOS / Linux）：

```bash
# 单线程吞吐（curl）
curl -o /dev/null -s -w "connect=%{time_connect}s ttfb=%{time_starttransfer}s speed=%{speed_download}B/s\n" \
  https://speed.cloudflare.com/__down?bytes=100000000

# 四线程并行（iperf3，需服务端支持）
iperf3 -c node.example.com -p 5201 -t 30 -P 4

# DNS 链路检查（macOS）
scutil --dns | grep nameserver | sort -u
```

**解读三个关键点：**

1. **看重传率，不只看带宽。** 8K 播放对丢包极度敏感：重传率超过 2%，YouTube 会主动把码率从 60Mbps 降到 15Mbps，你测速显示 200Mbps 也照样糊。
2. **倍率是隐性成本。** 一个 x3 倍率的节点即使跑得快，实际可用流量也只有标称的三分之一。判断性价比必须用「晚高峰有效码率 ÷ 倍率」。
3. **2.5Gbps 单节点上限的意义**：意味着单个节点不会因为并发用户挤在同一张物理网卡上而排队，这是能否稳定 8K 的硬指标。

## 五、2026 晚高峰实测梯队拆解

### T0：【光速云】——IEPL + IPLC 双网混合

实测中唯一在电信、联通、移动三条入口上都能稳定通过 8K 测试的梯队。核心原因是它把国内入口做成了双 ISP 冗余，出境段走 IEPL 内网，落地侧再接 IPLC 补齐欧美方向。全节点 x1 无倍率，意味着你买的流量是实打实可用的，这在同价位里比较少见。

### T1：单线 IPLC 中高端品牌

晚高峰单线程 90–260Mbps，8K 基本能播但偶尔需要缓冲。短板通常在于**入口只接单 ISP**，电信用户高峰期体验会明显好于移动用户。

### T2：BGP 中转主流机场

这是市面上「百元档」的主力。白天能跑 200Mbps，20:30 之后掉到 30–80Mbps，4K 勉强、8K 无望。不是商家骗人，是 BGP 中转的天花板就在这里。

### T3：直连 VPS

只适合做备份线路或轻量网页访问。晚高峰跑 8K 属于自我折磨。

## 七、分平台客户端配置与深度避坑

### 7.1 Windows：Clash Verge Rev / v2rayN

- **开启 TUN 模式**才能让所有程序走代理，系统代理模式下部分 UWP 应用（含 Netflix 客户端）会绕过。
- **DNS 必须走代理**：在配置里设置 `dns.enable: true` 与 `fake-ip` 模式，否则 DNS 泄露会让流媒体识别到你的真实地区。
- 避坑：不要为了「多看几个节点」手动在 GUI 里堆 30 个订阅，规则解析会拖慢启动，也会触发部分机场的并发连接风控。

### 7.2 macOS：ClashX Meta / Stash

- 用 `scutil --dns` 检查 DNS 是否被 TUN 接管；若 nameserver 出现运营商 IP，说明泄露。
- 刷新缓存：

```bash
sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder
```

- 避坑：macOS 的「低数据模式」与「私有中继」会和 TUN 冲突，测速前务必关闭。

### 7.3 Android / iOS

- Android 用 Clash Meta for Android，务必勾选「绕过局域网」并关闭「电池优化」，否则息屏后长连接被系统杀掉，表现为「锁屏再打开视频就重新缓冲」。
- iOS 用 Shadowrocket / Stash，开启「按需连接」。注意：**iOS 的 Network Extension 内存上限约 50MB**，规则集超过 5 万条会闪退。

### 7.4 路由器 / 软路由

- OpenWrt + mihomo 是 8K 家庭影院的最优解：电视、Apple TV 全部透明代理，无需各设备单独配置。
- 关键参数：`tcp-concurrent: true`、`find-process-mode: off`、开启 `sniffer` 用于流媒体域名识别。
- 避坑：软路由 CPU 弱（如 N1）跑 8K 时成为瓶颈，实测吞吐可能只有 150Mbps。8K 场景建议 x86 或 ARMv8 四核以上。

## 八、抓包排障诊断手册

晚高峰掉速时，别猜。按下面的顺序跑命令，10 分钟定位到哪一段出问题。

### 8.1 基础三件套

```bash
# 1) 路径级丢包定位（ICMP）
mtr -rwzbc 100 1.1.1.1

# 2) 路径级丢包定位（TCP 443，更贴近真实代理流量）
mtr --tcp --port 443 -c 100 你的节点IP

# 3) 端口级延迟与丢包
tcping -p 443 -t 100 你的节点域名
```

### 8.2 关键判定表

| 观测现象 | 判定结论 | 处置 |
| --- | --- | --- |
| 前 3 跳丢包，后续跳正常 | 本地宽带/路由器问题 | 重启光猫、换网线、查路由器 NAT 表 |
| 第 4–8 跳（163/202.97/219.158）丢包 5%+ | 国际出口拥塞 + QoS | 换 IEPL 专线，或用双 ISP 入口切换 |
| 全程 0 丢包但延迟高（250ms+） | 线路绕路（如走美西） | 换日本/新加坡/香港落地 |
| 丢包为 0、延迟低，但下载慢 | 服务端限速或超售 | 换节点、查看倍率与并发上限 |
| 连接建立成功但吞吐接近 0 | SNI 阻断 / 协议特征被识别 | 换 Reality / Hysteria2 节点 |

### 8.3 进阶：判断是不是你自己在丢包

```bash
# 查看本机网卡重传与错误计数（Linux）
netstat -s | grep -i retrans
ip -s link show eth0

# macOS 查看当前 DNS 是否被代理接管
scutil --dns | grep nameserver | sort -u
```

如果本机 `retrans` 计数在测速期间暴涨，问题在本地链路或 Wi-Fi 干扰，跟机场无关。

## 十、常见问题排障 FAQ

**Q1：白天 200Mbps，晚高峰 20Mbps，正常吗？**
对 T2 梯队来说是正常的，这是公网出口拥塞 + QoS 的必然结果。若你对此不可接受，唯一的解法是换 T0/T1 专线梯队，任何「优化设置」都救不回来。

**Q2：Speedtest 跑满 500Mbps，但 Netflix 只有 480p，为什么？**
典型的「测速达标、长连接被压制」。Speedtest 是短时突发 + 多线程，能抢占带宽；Netflix 是长连接 + 恒定码率，一旦丢包就被 Dynamically Optimized 降码率。看 TCP 重传率，不看测速截图。

**Q3：节点越多越好吗？**
不是。节点数量与质量通常负相关——共享同一出口带宽的节点越多，单节点晚高峰越惨。8K 用户应关注「单节点 2.5Gbps 上限」这类硬指标。

**Q4：UDP 加速（Hysteria2/TUIC）晚高峰真的更快吗？**
分场景。它抗丢包强、抢带宽猛，但运营商对 UDP 的 QoS 更狠，且部分运营商会对 UDP 大流量限速。视频直播类可能更快，稳定性反而不如 Reality + BBRv3。

**Q5：为什么手机上比电脑慢？**
三个原因：Wi-Fi 频段干扰（换 5GHz/6GHz）、省电策略杀长连接、客户端单线程实现。先在路由器层做透明代理对比一次即可定位。

**Q6：ChatGPT 登录被风控，换节点有用吗？**
有用但要看是哪种 IP。DNS 解锁类节点对 ChatGPT 无效——它需要真实的原生住宅或干净机房 IP。选购时直接问「是否原生 IP」，并自查 ASN。

**Q7：机场跑路了怎么办？**
按「月付优先、不囤长期」原则分散风险；同时自建一台 VPS 做兜底。参见我们的备份方案指南。
