# 如何辨识假专线：普通公网中转伪装 IEPL 的五大鉴定法门

> 一句话结论先给：**市面上标称「IEPL 专线」的机场，真正端到端跑在运营商二层专线通道上的，不超过两成。** 剩下八成的所谓「专线」，本质是「入口 BGP 优化 + 公网骨干中转 + 出口落地」的三段式组合，其中只有第一段沾了「专线」两个字的边。本文不玩概念，直接给你五套可复现的鉴定方法、一张量化对照矩阵、一套排障命令与判定表——花 20 分钟，你自己就能把绝大多数伪专线扒出来。

---

## 一、TL;DR：三分钟自查清单

如果你不想读完整篇，先做这三件事，命中任意一条，基本可以判定为**伪专线**：

1. **开 `mtr` 追一跳到落地 IP**。如果中间出现 `202.97.x.x`（电信 163）、`219.158.x.x`（联通 169）、`221.179.x.x` / `211.136.x.x`（移动）或海外 Tier-1 的公网跳，说明流量走了公共互联网骨干——这**不是专线**。
2. **晚高峰（20:00–23:00）连测 60 秒丢包与抖动**。真专线的丢包应稳定在 `0.1%` 以内、抖动 `≤ 3ms`；如果你看到丢包 3%–15%、抖动 30ms+ 且逐晚复现，那就是公网拥塞的典型指纹。
3. **反向成本核算**。一条上海↔香港 100Mbps 的真 IEPL，运营商一级报价月租普遍在 1.5 万–3 万元人民币区间，二级代理批发也在 3000 元以上。**任何标价 ¥15/月还宣称「企业级 IEPL 专线」的产品，物理上不可能成立。**

## 二、底层机理：为什么"专线"和"优化"是两个物种

先把三个常被混用的词拆干净。

**IPLC（International Private Leased Circuit）** 是传统国际私有租用电路，基于 TDM/SDH 的时分复用通道，物理上是一条「钉死」的通道，带宽恒定、不与其他用户共享时隙。价格极高，现在新部署已经很少。

**IEPL（International Ethernet Private Line）** 是 IPLC 的以太网演进版本，本质是运营商在 OTN/MPLS 骨干上开的一条 **二层点对点以太网专线（E-Line / EVC）**。它的关键特征是：两端之间是一段**逻辑独占的 VLAN 通道**，流量由运营商 MPLS 标签或 OTN 时隙转发，**不进入公共互联网的 BGP 路由表**。物理承载可能是海底光缆里的一个波长或一个时隙。

**"三网优化入口 / BGP 中转 / CN2 GIA"** 则完全是另一回事。它们的共同点是：**流量最终仍然进入公共互联网**，只是入口段选择了对国内三网相对友好的线路（比如电信 CN2、联通 9929/AS4837、移动 CMIN2）。CN2 GIA 走的中间跳是 `59.43.x.x`，已经很优秀，但它依然是**公共骨干上的公共资源**——晚高峰该挤还是挤。

这里有个行业黑话陷阱：**「IEPL 入口」**。很多机场宣传「IEPL 入口」，指的是用户到入口机房的这一段是专线，但从入口机房到海外落地仍然是公网中转。这叫**半专线**，效果介于纯公网和真专线之间，但价格往往按纯专线卖。

还要破除两个营销烟雾弹：

- **BBRv3** 是拥塞控制算法，作用是在丢包发生后更快地恢复吞吐。它能"掩盖"丢包，但**不能消除物理层的拥塞**。很多伪专线用 BBRv3 让测速数字好看，实际体验仍然是锯齿状的。
- **TLS Reality / XTLS** 是传输层伪装方案，解决的是抗主动探测与流量特征识别，**跟专线不专线没有任何关系**。把 REALITY 和 IEPL 绑在一起宣传的，多半是在混淆视听。

一句话总结底层差异：**真专线拼的是"有没有人跟你抢"，伪专线拼的是"抢的时候你排第几"。**

## 三、核心参数对照矩阵（10 项量化指标）

| # | 观测指标 | 真 IEPL/IPLC 专线 | CN2 GIA / 9929 高端优化 | 公网中转伪装"专线" |
|---|---|---|---|---|
| 1 | Traceroute 中间跳 | 仅 2–4 跳，中间为内网段（`10.x` / `100.64.x` / 无响应） | 5–10 跳，可见 `59.43.x.x` 或 `9929` | 8–15 跳，可见 `202.97` / `219.158` / Tier-1 公网 |
| 2 | 晚高峰丢包率 | 稳定 `≤ 0.1%` | `0.5% – 3%` | `3% – 15%`，逐晚规律复现 |
| 3 | 抖动 jitter（60s 采样） | `≤ 3ms` | `5 – 15ms` | `30 – 200ms`，呈尖峰分布 |
| 4 | 单线程下行吞吐 | 可达套餐标称的 `85%–95%` | `50%–80%` | `10%–40%`，多线程才好看 |
| 5 | 首包延迟（TCP 握手） | 等于物理 RTT，波动 `±2ms` | 物理 RTT，波动 `±8ms` | 明显高于物理 RTT，波动大 |
| 6 | 沪→港 RTT 参考值 | `25–35ms` | `28–40ms` | `40–80ms`（绕路或排队） |
| 7 | 带宽保证（CIR/PIR） | 有明确 CIR 承诺 | 无承诺，共享 | 无承诺，且超售比常超 1:200 |
| 8 | 路由稳定性（7 天） | AS Path 无变化 | 偶发 BGP 收敛 | 频繁换路，IP 段漂移 |
| 9 | 二级代理成本（100M） | 月租 `¥3000+` | 月租 `¥300–800` | 月租 `¥100–300` |
| 10 | 可探测量 | 延迟、抖动、AS Path 三重一致 | 延迟优秀但抖动可见 | 延迟、抖动、路由三项均露馅 |

注意第 10 项：**真专线的三个维度是互相印证的**。如果你发现"延迟只有 30ms 很像专线，但抖动高达 80ms"，那答案就很清楚了——这是**入口优化得好、出口在排队**的半专线或纯公网中转。

## 四、五大鉴定法门（核心章节）

### 法门一：Traceroute 中间跳审计——看"看不见的跳"

最直接的方法。真专线两端走的是运营商内网，中间路由器**通常不响应 ICMP TTL 超时**，你只会看到一连串 `* * *`，然后直接到达落地。这恰恰是专线的特征。

```bash
# macOS / Linux：TCP 模式穿透性更好，避免 ICMP 被限速
sudo mtr -rwzc 200 --tcp --port 443 <落地IP>

# Windows：先跑 tracert 看拓扑，再用 pathping 看丢包分布
tracert -d <落地IP>
pathping -n -q 50 <落地IP>
```

**判定表：**

| 中间跳特征 | 判定 |
|---|---|
| 2–4 跳，中间 `* * *` 或 `10.x` / `100.64.x` 内网段 | 高概率真专线 |
| 出现 `59.43.x.x` 且跳数 5–8 | CN2 GIA，优秀公网，非专线 |
| 出现 `202.97.x.x` | 电信 163 公网出口，伪专线 |
| 出现 `219.158.x.x` | 联通 169 公网出口，伪专线 |
| 落地前出现海外 Tier-1（如 NTT / Cogent / Telia AS 段） | 公网中转，伪专线 |
| 全程 `* * *` 且延迟等于物理 RTT、抖动极低 | 高概率真专线（需配合法门二交叉验证） |

⚠️ **避坑提示**：单独用 traceroute 会被"屏蔽 ICMP"这一招骗过。有些公网中转商会主动在中间跳上丢弃 TTL 超时报文，伪造出一片 `* * *`。所以必须结合法门二。

### 法门二：延迟-抖动双指纹分析

专线的核心价值不在"快"，而在"稳"。用 `ping` 做长采样（至少 200 包），看统计分布的**标准差**：

```bash
# 200 包长采样，观察 mdev（抖动）
ping -c 200 -i 0.2 <落地IP>

# macOS 更细：tcping 直接打 TCP 端口，绕过 ICMP 优先级差异
tcping -c 200 -i 0.2 <落地IP> 443
```

**看三个数字**：avg、max、mdev。

- `max - avg` 若长期超过 `15ms`，说明存在排队延迟，公网特征。
- `mdev` 若超过 `5ms`，基本可以排除独占通道。
- **分别在 14:00 和 21:30 各测一轮**。如果两组数据的 avg 差异超过 `20ms`、或晚高峰 mdev 直接翻十倍，这就是公网拥塞的教科书级指纹。

真专线在晚高峰的表现应该和白天**几乎一致**——因为它根本不参与公共互联网的争夺。

### 法门三：单线程吞吐测试——掀开超售的盖子

超售是伪专线最藏不住的破绽。方法很简单：**只用单线程测**。

```bash
# 单线程拉取大文件，观察稳定态速率（剔除首 3 秒 TCP 慢启动）
curl -o /dev/null -w "connect:%{time_connect}s ttfb:%{time_starttransfer}s speed:%{speed_download}\n" \
  --max-time 30 https://<测试文件URL>

# 有 iperf3 服务端的话，直接打单流
iperf3 -c <服务端> -t 30 -P 1
```

关键判读：**把单线程结果和你的套餐标称带宽对比**。

| 单线程 / 标称带宽 | 判定 |
|---|---|
| `≥ 80%` | 通道质量优秀，可能是真专线 |
| `50% – 80%` | 高端公网优化线路的正常水平 |
| `20% – 50%` | 存在明显超售或队列瓶颈 |
| `≤ 20%` | 严重超售，或中间有单流限速 |

顺带说一个常见作弊手法：**测速白名单**。部分机场对 Speedtest 的测速服务器 IP 段做直连或高优先级路由，测出来 500Mbps，实际打开 YouTube 只有 5Mbps。**永远以单线程真实业务下载（Google Drive 大文件、Cloudflare 大文件）为准，不要信页面上那个漂亮的测速截图。**

### 法门四：IP 归属与 AS Path 反查

```bash
# 查落地 IP 的归属与 AS 号
whois <落地IP> | grep -iE "orgname|netname|origin|country"

# 查这个 AS 是不是"专线型"运营商（一般企业级 IEPL 会挂在运营商 AS 下）
# 观察是否为你完全没见过的小机房 / 家宽段 / 云厂商弹性 IP 段
```

几个典型信号：

- 落地 IP 属于**知名云厂商弹性 IP 段**（如某些 VPS 大厂的公共段）——这是"租 VPS 当落地"的特征，跟专线无关。
- 落地 IP 段在多个机场之间**重复出现**——说明是同一批中转批发商在转卖，属于典型的"二房东"资源。
- `whois` 显示的是**家宽或 IDC 小机房**，但宣传"运营商直连专线"——直接对不上。

另外可以做一件事：**遍历你机场所有节点，统计它们落地 IP 的 C 段数量**。真专线机场通常有大量独立原生机房 IP，而伪专线机场的落地节点会高度集中在极少数几个 C 段里——因为成本摆在那儿。

### 法门五：成本反推与商业逻辑证伪

这一条不需要任何命令，但杀伤力最大。

**算一笔账**：一条上海↔香港 100Mbps 的真 IEPL，运营商一级报价月租约 `¥1.5万–3万`，二级代理批发价约 `¥3000–8000`。假设一个机场买了 1Gbps（10 条），月成本约 `¥30万+`。要覆盖这个成本，即使超售到 1:100，也需要至少 500 名付费用户 × `¥60/月` 才勉强持平——**还不算落地机房、IP、面板、客服和维护成本**。

所以：

- 标价 `¥15/月` 卖"IEPL 专线无限流量"——**物理上不成立**。
- 标价 `¥300/月` 但用户数上万的"IEPL 专线"——大概率只在入口段用了专线，出口是公网。
- 真正的企业级专线机场，定价通常在 `¥60–200/月` 的中高端区间，且**明确标注流量额度或并发限制**，因为带宽是他们最贵的成本。

## 五、分场景选型：你真的需要专线吗？

不是所有人都该为专线付溢价。按真实需求分：

**A. 跨境办公 / 远程会议（Teams、Zoom、Google Meet）**
对**抖动**最敏感。`30ms` 的稳定抖动比 `200ms` 的高抖动更影响会议体验。这类用户必须上真专线或顶级 CN2 GIA，重点看 mdev，别看峰值带宽。参考 [企业级专线机场分类](/airport/type/premium/)。

**B. 跨境电商多店铺 / 多账号防关联**
核心诉求是**独立原生 IP 的纯净度与稳定性**，不是带宽。一个 IP 段被大量用户共享的伪专线机场，最容易触发平台风控。建议优先选择落地 IP 数量足够多、能做独立 IP 分配的服务商。

**C. 4K/8K 流媒体与海外内容消费**
真正需要的是**出口落地质量与解锁能力**，20Mbps 的稳定通道就够了。这类场景不需要真专线，但需要防止"伪解锁"（详见第七章）。可参考 [流媒体解锁评测](/reviews/)。

**D. 开发者：GitHub / Docker / npm / HuggingFace**
关注的是**首包延迟和 TLS 握手耗时**。伪专线的"绕路"会让 npm install 变成噩梦。用 `curl -w` 看 `time_connect`，这才是你的核心指标。

**E. 对延迟极端敏感的场景（远程桌面、金融行情、云游戏）**
必须真专线，没有替代方案。抖动超过 `5ms` 的线路在这类场景下不可用。

## 六、分客户端实操配置与避坑

鉴定做完，配置也得跟上。不同平台有不同的泄漏点。

**Windows / Clash Verge Rev（mihomo 内核）**
- 开启 **TUN 模式**，否则部分 UWP 应用会绕过代理。
- `fake-ip-filter` 里必须加入你的银行、内网域名，否则会出现"国内网站走代理"的诡异现象。
- 开启 **Sniffer（域名嗅探）**，避免 DNS 污染导致的"连上了但打不开"。
- 关闭 `fallback` 分组，改用 `url-test` 并设置合理的 `interval`（建议 300s，太频繁会造成无谓握手）。

**macOS / Surge、Stash、sing-box**
- 运行 `scutil --dns` 检查系统 DNS 是否被代理层接管。若 `resolver #1` 仍是运营商 DNS，说明存在 DNS 泄漏风险。
- `sudo tcpdump -i utun3 -n port 53` 抓一下代理网卡上的 DNS 查询，正常情况下不应出现明文 53 端口的境外查询。
- 用 `netstat -rn | grep default` 确认默认路由是否已被 TUN 接口接管。

**iOS / Shadowrocket、Loon**
- 关闭"绕过中国大陆"的粗粒度规则，改用精确规则集。
- 检查是否开启了 `UDP Direct`，某些游戏和语音场景需要。

**软路由 / OpenWrt**
- 强烈建议使用 **mihomo 或 sing-box** 而非老旧的 SSR-Plus，后者的 DNS 处理在多 WAN 环境下极易出错。
- 双 ISP 场景下务必做策略路由，**不要把专线流量和家宽流量混在一个默认路由里**，否则专线的低抖动优势会被本地网络抖动吃掉。

更多客户端细节可查阅 [客户端配置中心](/client/) 与 [Clash Verge 深度配置](/client/app/clash/)。

## 七、抓包排障诊断手册

当你怀疑线路有问题时，按这个顺序走。

**Step 1：确认延迟基线**

```bash
mtr -rwzc 200 --tcp --port 443 <落地IP>
```

**Step 2：分层定位丢包点**

| 现象 | 定位 |
