## 二、底层机理：为什么有的专线是「真专线」，有的是「假装专线」

### 2.1 IEPL 与 IPLC 的物理差别

**IPLC（International Private Leased Circuit）** 是点对点国际专线，传统上跑在 SDH/OTN 传输网上，两端之间是一条独占的物理通道，不经过任何公共互联网交换节点（IXP）。它的典型特征是高稳定性、低抖动，但带宽颗粒度粗（传统为 E1/T1 的整数倍），扩容贵。

**IEPL（International Ethernet Private Line）** 是同思路的以太网版本，接口是 GE/10GE，带宽可以按兆比特粒度调整。对用户来说，两者体感几乎一致，区别在于 IEPL 更适合弹性扩带宽。

关键点在于：**这两种东西的成本是按「公里 + 兆比特」双维度计费的。** 一条中港 1Gbps 的 IEPL，月成本在四位数美元量级。所以当你看到某个服务商宣称「全节点 IEPL」却只收 15 元/月，只有两种可能：要么他在撒谎，要么他在超售到极致。

### 2.2 BGP 中转与「半专线」的混合结构

绝大多数中端机场的真实结构是：

```
用户 → 国内入口（BGP 中转机，如上海电信/移动） → 优化回程（CN2 GIA / 9929 / CMIN2） → 海外落地
```

这种结构里，**入口到出口之间走的是公网**，只是一路上走的路由质量比较好。它和真专线的差距不在于「线路名字」，而在于**抖动（jitter）**。专线的 RTT 抖动通常在 `±2ms` 以内，优化 BGP 在晚高峰可以抖到 `±30ms`。

「半专线」则是指入口走真专线、出口走公网，或者反之。这种做法在成本上能省 60%，在体验上能拿到真专线 70% 的效果——所以它才会被大量用于宣传。

### 2.3 物理下限：为什么「香港 5ms」是真的，「洛杉矶 5ms」是扯淡

光在光纤中的传播速度约为 `2×10⁸ m/s`。这个数字决定了所有声称延迟的物理下限：

| 目的地 | 典型光缆路径长度 | 理论 RTT 下限 | 优质专线实测 RTT | 普通公网晚高峰 |
| --- | --- | --- | --- | --- |
| 香港 | 约 60–300 km | 约 6–10 ms | `5–12 ms` | `20–60 ms` |
| 日本东京 | 约 2000–2600 km | 约 25–35 ms | `28–40 ms` | `60–140 ms` |
| 新加坡 | 约 4000–5000 km | 约 45–60 ms | `55–75 ms` | `90–200 ms` |
| 美西洛杉矶 | 约 11000–13000 km | 约 115–140 ms | `125–155 ms` | `180–350 ms` |
| 美东纽约 | 约 18000–20000 km | 约 185–215 ms | `195–230 ms` | `260–450 ms` |
| 德国法兰克福 | 约 16000–19000 km | 约 165–200 ms | `175–215 ms` | `250–400 ms` |

**判定铁律：任何宣称「上海到洛杉矶 80ms」的服务商，你可以直接关掉页面。** 这不是技术问题，是光速问题。要么它在偷换概念（把 UDP 首包延迟当 RTT 报），要么它在测速工具上做了手脚。

### 2.4 拥塞控制与协议层：BBRv3 与 TLS Reality

2026 年还在用默认 CUBIC 的服务商，基本可以判定为技术团队已经停止迭代。**BBRv3 的价值在于：在高丢包链路（例如晚高峰 3% 丢包）下，能把吞吐量维持在链路容量的 70% 以上，而 CUBIC 会直接塌到 20%。** 这解释了为什么有些节点「延迟看着正常，但下载就是慢」——问题不在延迟，在拥塞控制算法。

协议层，`TLS Reality`（以及 `uTLS` 指纹伪装）目前是最稳的一档。它的原理不是加密强度，而是**让 TLS 握手指纹看起来和访问 microsoft.com 完全一致**，从而在 SNI 检测层面不产生可识别特征。相比之下，早期 VMess 的 `alterId` 特征早已被完全识别，2026 年还在主推裸 VMess 的服务商，属于技术上已经放弃抵抗。

### 2.5 双 ISP 与入口冗余

**入口单线是专线服务商最隐蔽的单点故障。** 一台入口机只接电信，那联通用户从它那里进，第一跳就要绕到电信的互联互通节点，晚高峰必炸。

优质服务商的做法是：入口同时接入电信 + 联通（双 ISP），甚至再加移动和 BGP 多线，让三网用户都从「同一运营商」进入，避免跨网结算带来的额外跳数与抖动。

### 2.6 超售比：一切体验问题的根因

超售比 = 所有用户订阅的带宽总和 ÷ 出口实际带宽。

- 超售比 `1:1` 到 `1:3`：企业级，晚高峰基本无感。
- 超售比 `1:5` 到 `1:10`：优质机场，晚高峰带宽保持率约 80%。
- 超售比 `1:20` 以上：便宜大碗型，晚高峰带宽保持率通常跌破 30%。

**这就是为什么「同一个机场，白天飞快、晚上成狗」——不是线路坏了，是邻居上线了。**

## 四、细分人群与场景选型

同样是「高端专线」，不同人群的最优解完全不同。买错不是因为服务商差，是因为需求错配。

### 4.1 跨境电商 / 多店铺运营（最挑剔的一类）

核心诉求是**独立 IP + IP 纯净度 + 长期不变**。这类用户对延迟不敏感（`200ms` 也能接受），但对「IP 会不会被平台标记」极度敏感。

选型重点：
- 必须有机房独享 IP，且 IP 段未被大规模滥用过。
- 支持 IP 长期固定，不因换节点而变更。
- 拒绝任何形式的「共享出口 IP」方案。

参考 [多店铺 IP 隔离方案对比](/airport/)。

### 4.2 4K/8K 流媒体与原盘下载

核心诉求是**大带宽 + 不挤兑**。这是一个纯粹拼超售比的场景——白天能跑 300Mbps、晚上只剩 30Mbps 的机场，看 4K 原盘必然转圈。

选型重点：
- 晚高峰带宽保持率 `≥ 80%`。
- 单节点带宽上限 `≥ 300Mbps`。
- 支持 UDP 与 QUIC（YouTube 现在大量走 QUIC）。

### 4.3 跨境游戏加速

核心诉求是**低抖动 + 原生 UDP**。注意，游戏看的是抖动不是延迟：`60ms ± 2ms` 的体验远好于 `40ms ± 30ms`。

选型重点：
- 香港/日本专线，抖动 `≤ 5ms`。
- 必须全节点原生 UDP，不能用 UDP over TCP 伪装。

### 4.4 程序员 / 大文件传输 / CI 拉取

核心诉求是**TCP 吞吐稳定性 + 长时间连接不中断**。`git clone` 一个几 GB 的仓库、`docker pull` 拉镜像，最怕的是传到 80% 断线。

选型重点：
- 支持 BBRv3 或等效的现代拥塞控制。
- 服务器端 TCP Keep-Alive 配置合理。
- 有专门的大带宽节点。

### 4.5 移动办公 / 出差党

核心诉求是**多端同步 + 配置简单 + 弱网可用**。高铁、酒店 Wi-Fi、机场公共网络这些场景的共性特征是丢包高、抖动大，这时候拥���控制算法的作用比线路本身还大。

## 五、分平台实操配置与深度避坑

### 5.1 Windows

推荐客户端：Clash Verge Rev（mihomo 内核）、v2rayN。

**必做三件事：**

1. **开启 TUN 模式而非系统代理。** 系统代理只接管 WinINET/WinHTTP，很多软件（Steam、部分游戏、Docker Desktop、WSL2）根本不走。TUN 模式在网络层接管，覆盖完整。
2. **检查 DNS 泄漏。** 系统代理模式下，DNS 查询经常直接走本地 ISP 的 DNS，导致 CDN 解析到国内节点、或者域名被污染。开启 TUN 后配合 `fake-ip` 模式可解决。
3. **关闭「自动选择」的盲目性。** 自动测速选节点默认按延迟排序，会选出「延迟低但带宽差、超售严重」的节点。建议手动按场景分组。

**常见坑：** IPv6 泄漏。Windows 默认开启 IPv6，如果代理规则没覆盖 IPv6，流量会绕过代理直接出去。解决方式是 TUN 模式开启 IPv6 接管，或在网卡属性里临时禁用 IPv6。

### 5.2 macOS

推荐客户端：Clash Verge Rev、Surge、Stash。

**必做：**

- 使用 `sudo scutil --dns | head -40` 确认当前解析器顺序。如果 `resolver #1` 指向路由器或运营商 DNS，说明代理的 DNS 劫持没生效。
- Surge 用户注意 `enhanced mode` 与 `TUN` 的取舍：TUN 覆盖更全，但会与部分 VPN 软件冲突。

### 5.3 iOS / iPadOS

推荐：Shadowrocket、Stash、Loon。

**避坑重点：** iOS 上「按需连接（On Demand）」如果配置不当，会在 Wi-Fi 与蜂窝切换时反复重连，表现为「刚切网络就断几秒」。建议关闭按需，改为手动控制。

### 5.4 Android

推荐：Clash Meta for Android、v2rayNG。

**避坑重点：** 国产 ROM 的省电策略会杀掉代理进程，表现为「锁屏几分钟后代理就死了」。需要在电池优化白名单里加入客户端，并锁定后台。

### 5.5 路由器（OpenWrt / ImmortalWrt）

推荐内核：mihomo。

**避坑重点：**
- 硬件性能是硬上限。MT7621 这类老芯片跑 `AES-256-GCM` 只能到 `80Mbps` 左右，买再贵的专线也白搭。想跑满 500Mbps 需要 ARMv8 及以上、支持 AES 硬件加速的芯片。
- 分流规则不要全量代理，否则国内视频也会绕出去，浪费带宽还慢。

## 六、抓包排障诊断手册

当你觉得「今天特别卡」时，不要凭感觉骂服务商。按下面流程走一遍，5 分钟定位问题层级。

### 6.1 链路质量：mtr

```bash
# Linux / macOS，100 个包，报告模式，显示 ASN
mtr -rwzbc 100 1.1.1.1

# 指定走 TCP 443，避免 ICMP 被限速导致的误判
mtr -rwzbc 100 -T -P 443 your-node-host
```

**判读要点：**
- **看最后一跳，不看中间跳。** 中间节点丢包但后续正常，说明只是那台路由器不响应 ICMP，不是真丢包。
- **看抖动而非平均。** `StDev` 超过 `20ms` 就是明显抖动。
- **对比不同时间。** 白天 mtr 与晚高峰 mtr 对比，才能看出超售问题。

### 6.2 端口连通性与握手耗时

```bash
# Linux 探端口
nc -zv your-node-host 443

# macOS / Linux 完整握手计时
curl -o /dev/null -s -w "dns:%{time_namelookup} conn:%{time_connect} tls:%{time_appconnect} total:%{time_total}\n" https://www.google.com
```

**判��：** `time_connect` 正常但 `time_appconnect` 很大，说明是 TLS 握手被干扰（协议层问题）；两者都大，说明链路层问题。

### 6.3 DNS 排查

```bash
# macOS
scutil --dns | head -40

# 通用
dig +short @1.1.1.1 www.google.com
nslookup www.youtube.com
```

**判定：** 如果 `@1.1.1.1` 返回的 IP 与本地默认返回的不一致，且默认返回的是国内 IP，说明 DNS 泄漏。

### 6.4 TCP 重传率

```bash
# Linux
nstat -az | grep -i -E "Retrans|OutSegs"
ss -s
```

**判定：** `TcpRetransSegs ÷ TcpOutSegs` 超过 `2%` 就属于链路质量差；超过 `5%` 基本无法正常使用。

### 6.5 综合判定表

| 现象 | mtr 表现 | 最可能原因 | 处置 |
| --- | --- | --- | --- |
| 延迟正常但下载慢 | 抖动小，丢包 `0.1%–1%` | 拥塞控制算法或超售 | 换节点 / 换服务商 |
| 白天好晚上差 | 晚高峰 RTT 上升 `30ms+` | 超售 | 换服务商 |
| 连接频繁重置 | 到落地跳丢包突增 | 协议被识别 / 中间设备干扰 | 换协议（TLS Reality） |
| 只有某类网站慢 | 链路正常 | 分流规则或 DNS | 检查规则与 DNS |
| 打开就断，重连才好 | 首跳正常 | MTU / MSS 问题 | 调整 MTU 至 1400 |
| 全部节点同时炸 | 首跳即异常 | 本地网络或客户端问题 | 重启网卡 / 换客户端 |

## 七、行业常见避坑矩阵

这是本文最有价值的一节。以下 8 种套路，是我们过去两年在读者投诉里出现频率最高的。

| # | 宣传话术 | 真实情况 | 识别方法 | 风险等级 |

| 1 | 「全节点 IEPL 专线」 | 只有入口是专线 | 追问出口是否也走专线，要求出示路由 | 高 |

## 八、常见问题排障 FAQ

**Q1：为什么我买了「高端专线」，晚高峰还是卡？**

先按第六节的 mtr 流程走一遍。如果确认是链路层问题，大概率是超售。注意，专线本身不解决超售——专线解决的是「线路质量」，超售是「资源分配」问题。两者独立。

**Q2：同一个订阅，手机快电脑慢，是什么原因？**

按可能性排序：① 电脑的 MTU 设置不当；② 电脑上其他软件（杀毒、VPN、虚拟网卡）在抢路由；③ 客户端内核版本太老；④ 电脑网卡驱动或 Wi-Fi 信道问题。先换客户端测试。

**Q3：节点延迟很低，但打开网页很慢。**

这是典型的「延迟指标欺骗」。低延迟可能是 ICMP 被优先响应造成的假象。用第六节的 `curl` 计时命令测真实 TLS 握手与首字节时间，这才是体感相关的指标。

**Q4：UDP 转发到底有多重要？**

非常重要。YouTube 大量走 QUIC（基于 UDP），大多数游戏的实时数据走 UDP，WebRTC 视频通话走 UDP。如果一个节点不支持 UDP，你会看到：网站能开但视频加载慢、游戏无法连接。选购前务必确认全节点 UDP 支持。

**Q5：可以多人共用一份订阅吗？**

取决于服务商的并发设备限制。共享会显著抬高实际使用强度，触发限速概率大增。如果是团队使用，建议按人头购买或选择明确支持多设备的方案。

**Q6：如何判断一个 IP 是不是「原生」？**

两个维度：① 归属查询——看 IP 注册地与实际机房位置是否一致；② 行为测试——在目标平台（流媒体、电商后台）实测，看是否触发验证码或风控。很多所谓「原生 IP」只是在 DNS 层面做了分流，实际仍然是广播 IP。

**Q7：多久应该重新评估一次手上的服务商？**

建议每季度一次，重点看晚高峰带宽保持率是否下滑。行业里最常见的退化路径是：新品牌上线 → 口碑积累 → 大量拉新 → 超售比恶化 → 老用户流失。周期通常是 12–24 个月。
