# 免费试用机场的正确姿势：如何在试用期内测出真实水平

> 更新于 2026 年 · AirPick 实验室 · 全文约 3800 字 · 建议阅读 12 分钟

## 一、TL;DR：先给结论，再看论证

如果你只想拿一个可执行的判断标准，那就记住这一句话：**试用期唯一有效的测速窗口是晚高峰 20:00–23:00，唯一有效的测试手段是长时程多线程压力测试，而不是任何 App 内置的那个「一键测速」。**

进一步压缩成四条硬规则：

1. **单线程速度决定上限，晚高峰丢包决定下限。** 前者看商家有没有真带宽，后者看有没有真专线。只看前者，你必然踩「试用快付款慢」。
2. **试用节点和付费节点大概率不是同一批出口。** 试用通常落在低成本 BGP 中转池或共享公网隧道上，付费才给 IEPL 专线。所以试用测出来的数字，只能当上限参考，不能当承诺基线。
3. **不要用「能不能上 ChatGPT」作为验收标准。** 那只能筛选掉落地 IP 被污染的最差选项，对速度、稳定性、超售率零信息量。
4. **至少覆盖两个晚高峰再付款。** 单个晚高峰可能是机房维护，连续两个晚高峰都掉到 20Mbps 以下，可以直接放弃。

## 二、底层机理：为什么「试用快、付款慢」是结构性必然，而非道德问题

很多人把试用期掉速归因于商家「坏」。真相更无聊一些：这是**成本结构决定的工程选择**，不是临时起意。

### 2.1 带宽买的是「峰值」，不是「流量」

机场从上游采购出口带宽，主流计费方式有两种：

- **固定带宽包月**：比如 10Gbps ��享口，无论用不用，每月固定成本。
- **95 计费**：按「去掉最高 5% 采样点后的峰值」结算，突发可以便宜，但持续跑满就极贵。

试用用户的流量在商家账本里是**纯成本、零收入**。所以任何理性的商家都会把试用流量导向成本最低的路径：共享 BGP 中转、公网隧道、甚至二手家宽。付费用户才被迁移到成本高一个数量级的专线池。

这不是「试用坑」，这是预算约束下的默认行为。你要做的不是抱怨，而是**识别出这条分界线到底在哪**。

### 2.2 QoS：你被丢进了低优先级队列

现代机房交换机普遍支持多级队列调度（WFQ / 优先级队列）。在高负载端口的出口，运营商和机房的策略通常是：

| 队列级别 | 典型对象 | 拥塞时的表现 |
| --- | --- | --- |
| EF（加速转发） | 专线、企业客户 | 几乎不掉包 |
| AF1–AF4 | 普通付费云主机 | 轻微抖动，可控 |
| BE（尽力而为） | 共享中转、试用流量 | 丢包率可从 `0.1%` 飙到 `8%` |

晚高峰的那一刻，你感受的不是「带宽不够」，而是**排队被丢包**。丢包会直接触发 TCP 拥塞控制降窗，于是速度断崖式下跌——即使物理带宽还剩一大截。

### 2.3 BBRv3 与拥塞控制：为什么有些节点「看起来慢其实很快」

TCP 的拥塞控制算法决定丢包时的反应方式：

- **Cubic（Linux 默认）**：丢包即大幅降窗，长肥管道（高 RTT × 高带宽）上恢复极慢。
- **BBRv1/v2/v3**：基于带宽时延积建模，丢包不直接等于降窗。

一台部署了 BBRv3 的落地机，在 `2%` 丢包下仍能维持较高吞吐；而对面如果是 Cubic，同样的链路直接腰斩。**这意味着：单纯用 `ping` 延迟去评判一个节点是不公平的，你必须实测吞吐。**

### 2.4 IEPL / IPLC：分界线到底在哪

- **BGP 中转**：流量走公网，经过多个运营商 AS 跳转。便宜、灵活、晚高峰不可控。
- **IPLC**：国际私有专线，点对点，全程不经过公网。贵、稳定、延迟曲线几乎是一条直线。
- **IEPL**：以太网接口的 IPLC 变体，更灵活，本质同上。

**这是唯一能真正解决晚高峰掉速的技术手段。** 任何号称「优化线路」「高端中转」但没提 IPLC/IEPL 的产品，晚高峰都可能翻车。

所以试用阶段最该验证的就是这一件事：**这个节点在 21:30 的时候，丢包率是多少。**

### 2.5 TLS Reality 与协议指纹：和速度无关，和「活着」有关

2026 ���主流机场普遍采用 Reality / Vision / uTLS 指纹伪装。这些技术解决的是**被动探测与 QoS 识别**问题，对带宽没有提升，但能显著降低「同一条线路被整段限速」的概率。

判断标准很简单：试用期内是否出现**整节点集体断连、需要频繁更换订阅链接**。出现超过 3 次，说明协议抗性不足，不建议长期持有。

## 四、试用期测速标准 SOP：72 小时分阶段执行

### 阶段 0｜领试用之前（5 分钟）

先看条款，不看节点。重点确认四件事：

- 试用期限：24 小时和 72 小时的测法完全不同，前者只能测一次晚高峰。
- 试用节点范围：如果只有 1–2 个节点，基本不具备代表性。
- 是否限速：部分机场在试用条款里藏着「试用期限速 50Mbps」。
- 是否需要实名/支付信息：需要预付的严格来说不叫试用。

### 阶段 1｜冷启动基线（0–30 分钟）

先记录你**本地真实网络**的基线，否则后面所有数字都没有参照系。

```bash
# 1. 本机直连基线（不走代理）
curl -o /dev/null -s -w "direct_ttfb=%{time_starttransfer}\n" https://www.cloudflare.com/cdn-cgi/trace

# 2. 本机公网出口与 ASN
curl -s https://ipinfo.io/json

# 3. macOS 检查 DNS 链路（排查 DNS 泄漏前置）
scutil --dns | grep nameserver | head -5

# 4. 路由质量基线（走代理前后各跑一次）
sudo mtr -rwzc 80 -T -P 443 1.1.1.1
```

**判定要点**：如果本机直连 `1.1.1.1` 就已经有 `5%` 丢包，那这个测试环境本身就是脏的，后面所有结论不可信。先解决本地网络（换 Wi-Fi 信道、关掉路由器的 QoS、排查运营商拥塞）。

### 阶段 2｜节点质量横向扫描（30 分钟 – 2 小时）

对每个试用节点跑统一的三件套：

```bash
# A. 单线程吞吐（20 秒平均）
curl -x socks5h://127.0.0.1:7890 -o /dev/null \
  --speed-time 20 --speed-limit 1 \
  -w "avg=%{speed_download} B/s ttfb=%{time_starttransfer}s\n" \
  "https://speed.cloudflare.com/__down?bytes=200000000"

# B. 端到端各阶段耗时拆解
curl -x socks5h://127.0.0.1:7890 -o /dev/null -s \
  -w "dns=%{time_namelookup} conn=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total}\n" \
  https://www.youtube.com/

# C. TCP 层健康度（Linux 看拥塞窗口与 RTT）
ss -tin | grep -A1 7890
```

**关键动作**：把 `time_namelookup` 单独拎出来看。如果它超过 `300ms`，说明 **DNS 解析被代理拖慢了**，这会让你误判成「节点慢」，实际是解析链路问题。

### 阶段 3｜晚高峰压力测试（20:30–23:00）

这是**唯一有决策价值的窗口**。

```bash
# 移动端 / macOS 用 tcping 连续采样 100 次
tcping -c 100 -i 1 -p 443 your-node-domain.com

# 更强的路由全路径分析（-z 显示 ASN，-c 采样次数���
sudo mtr -rwzc 200 -T -P 443 your-node-domain.com

# 并发聚合测试（8 线程，30 秒）
# 分别在本地开 8 个终端跑上面的 curl A 命令，累加速度
```

**判定表：**

| 现象 | 结论 | 处置 |
| --- | --- | --- |
| RTT 稳定，丢包 `< 0.5%` | 疑似真专线 | 加分，继续观察 |
| RTT 稳定但丢包 `2%–5%` | 共享专线或高优先级中转 | 可接受，看价格 |
| 20:00 后 RTT 从 60ms 跳到 250ms | 公网绕路，晚高峰公网拥塞 | 减分 |
| 丢包 `> 8%` 且持续 | 严重超售或 BE 队列 | 直接淘汰 |
| 凌晨很快、晚上腰斩 | 典型共享带宽超售模型 | 看价格能否接受 |

### 阶段 4｜长连接与断流观测（24–72 小时）

```bash
# 挂一个 2 小时以上的持续下载，记录是否中断
for i in $(seq 1 120); do
  curl -x socks5h://127.0.0.1:7890 -o /dev/null -s -m 60 \
    -w "$(date +%H:%M) speed=%{speed_download} code=%{http_code}\n" \
    "https://speed.cloudflare.com/__down?bytes=50000000"
  sleep 60
done
```

把日志存下来。**你要找的是「阶梯式下跌」和「瞬间归零」**：

- 阶梯式下跌 → 触发限速阈值（超量降速）。
- 瞬间归零 → 节点掉线或 IP 被墙，属于重大稳定性问题。

### 阶段 5｜打分决策

按第三章的 10 项矩阵逐项打分。建议阈值：**总分 70 分以上可入月付，85 分以上可入年付。任何一项标「极高」权重的指标不及格，一票否决。**

## 五、辨别「试用专用诱饵节点」的 7 个信号

这是本文最实用的部分。诱饵节点的特征是可以被系统性识别的：

1. **试用节点数量远少于付费节点。** 试用 2 个、付费 60 个，你测的就是一个特供样本。
2. **试用节点名带「Trial / 试用 / Speed」字样。** 名字本身就是分类标签，说明它是独立池。
3. **试用节点延迟低得离谱。** 比如香港节点 RTT 只有 `8ms`，这在物理上要求你就在香港机房隔壁——大概率是找到了一个「近端入口」，不反映真实出口质量。
4. **试用节点不提供倍率标注。** 付费页写明 x1/x2，试用页只字不提，说明计费规则可能在付款后变化。
5. **试用期结束后节点名被改名或重编号。** 说明这不是稳定资产，随时可能被替换。
6. **只有试用节点能上 ChatGPT，付费节点反而不行。** 典型的「诱饵落地 + 低质付费落地」组合。
7. **试用期不限速、条款里写「付费后按套餐限速」。** 这是最直白的一种，条款里通常藏在「服务说明」最后一段。

**交叉验证法**：付款前，去第三方评测站看该机场**付费节点**的独立测速数据，和你的试用数据做差值。差值超过 40%，说明试用池与付费池不是同一套。

## 六、分客户端实操配置与深度避坑

### 6.1 桌面端（Clash Verge Rev / Mihomo）

- **务必开启 TUN 模式做完整测试**，系统代理模式测出来的速度会偏高，因为部分流量走了直连。
- 关闭「自动选择 / url-test」策略组。测速时要**手动锁定单一节点**，否则策略组会在你测试过程中悄悄切换，数据全部作废。
- 把 `tolerance` 设成 `0`，避免延迟抖动触发切换。
- 测速期间关掉浏览器的 QUIC（`chrome://flags` 里禁用 QUIC），否则 YouTube 走 UDP 443，你的 TCP 测试数据不代表实际体验。

### 6.2 iOS（Shadowrocket / Stash / Loon）

- iOS 的 `测速` 功能只测 TCP 握手，不测吞吐，**参考价值接近零**。
- 真正的测法是：用 Shadowrocket 挂节点，打开 Speedtest 或 Fast.com，**并且把测速 App 本身设为走代理**（部分客户端默认放行测速 App 直连，你测的是本地宽带）。
- 注意 iOS 低功耗模式会限制后台网络，测晚高峰前请关闭。

### 6.3 Android（Sing-box / NekoBox / v2rayNG）

- 打开 `Per-app proxy`，只代理测速 App，避免全局代理引入额外开销。
- 关闭电池优化，否则长时间下载会被系统掐断，你会误判成「节点断流」。

### 6.4 通用避坑

- **不要用客户端自带的「延迟测试」当验收**。它测的是握手 RTT，不含吞吐。
- **不要在同一个时间点只测一次**。至少 3 次采样取中位数，剔除首次冷启动。
- **不要用 HTTP 测速站代替 HTTPS**。TLS 握手失败率是重要指标。

## 七、抓包排障诊断手册

当你觉得「慢」但不知道慢在哪一环，按下面的顺序排除：

```bash
# 1. 代理端口是否真的在监听
lsof -i :7890          # macOS / Linux
netstat -ano | findstr 7890   # Windows

# 2. DNS 是否泄漏（应返回代理侧 DNS，而非本地运营商）
dig +short txt o-o.myaddr.l.google.com @1.1.1.1

# 3. 分段路由追踪，看在哪一跳劣化
sudo mtr -rwzc 100 -T -P 443 your-node.com

# 4. 对比直连与代理的 TTFB 差值
#    直连
curl -o /dev/null -s -w "direct=%{time_starttransfer}\n" https://www.gstatic.com/generate_204
#    代理
curl -x socks5h://127.0.0.1:7890 -o /dev/null -s -w "proxy=%{time_starttransfer}\n" https://www.gstatic.com/generate_204

# 5. macOS 系统级网络质量评分
networkQuality -v

# 6. Windows 端 TCP 连通性
Test-NetConnection your-node.com -Port 443 -InformationLevel Detailed
```

**判定逻辑表：**

| 症状 | 最可能原因 | 处置 |
| --- | --- | --- |
| `time_namelookup` `> 500ms` | DNS 走本地或被劫持 | 改用代理侧 DNS 或 DoH |
| `time_connect` 正常，`time_appconnect` 极高 | TLS 握手被干扰 / 协议指纹暴露 | 换 Reality/Vision 协议节点 |
| TTFB 正常，总时长爆炸 | 落地侧带宽不足 | 换落地机，或换机场 |
| mtr 在某跳后丢包持续 `> 5%` | 该 AS 出口拥塞 | 换入口线路（电信/联通/移动各试） |
| 白天正常，20:00 后 RTT 翻 3 倍 | 公网拥塞，无专线 | 淘汰或仅在非高峰用 |

## 八、行业常见避坑矩阵

| 宣传话术 | 真实含义 | 验证手段 |
| --- | --- | --- |
| 「单节点 10Gbps」 | 机房端口上限，非你的可用带宽 | 多线程实测聚合速度 |
| 「不限速不限量」 | 通常有 FUP 条款，超量降速 | 查 ToS 中的 Fair Use 段落 |
| 「原生 IP」 | 可能只是广播 IP 或 DNS 解锁 | 查 ASN + 流媒体实测 |
| 「全节点解锁 ChatGPT」 | 可能仅 DNS 层解锁，速度极差 | 实际登录并对话测试 |
| 「IEPL 专线」 | 可能只有 1 个节点是，其余是中转 | 逐节点跑 mtr 看路径 |
| 「99.9% 可用性」 | 通常无 SLA 赔付，纯话术 | 看是否有 SLA 文档 |
| 「试用即享全功能」 | 试用池独立，与付费池无关 | 交叉比对第三方付费测速 |
| 「用户数 10 万+」 | 超售风险信号，除非出口带宽同步公开 | 晚高峰丢包率是唯一真相 |

**超售率速算**：关注订阅用户数 ÷ 公开出口带宽。如果 10 万用户共享 20Gbps，人均 `0.2Mbps`，晚高峰必然崩。这个数字自己算一遍，比看任何评测都可靠。

## 九、常见问题 FAQ

**Q1：试用期只有 24 小时，来不及测两个晚高峰怎么办？**
只测一个晚高峰，但把采样密度提高：20:30–23:00 之间每 5 分钟跑一次 mtr，用 30 个采样点判断趋势。如果曲线持续劣化而非平稳，说明是超售而非偶发维护。

**Q2：试用节点很快，但担心付款后变慢，有没有低成本验证？**
买最小档月付（通常十几到二十几元），付款后立即用同一套脚本复测，24 小时内数据差异超过 40% 就申请退款（前提是支持退款）。这是成本最低的「付费池验证」。

**Q3：延迟 `50ms` 但下载只有 `10Mbps`，正常吗？**
完全可能。低延迟代表路径短，低带宽代表出口被限速或队列拥塞。这两个指标独立，不要用延迟推断速度。参见第七章判定表。

**Q4：同一节点，手机上快、电脑上慢，为什么？**
检查三点：电脑是否开了其他 VPN 或企业代理、是否走了 TUN 双栈导致 DNS 绕路、是否浏览器 QUIC 与 TCP 混跑互相抢占。用 `lsof -i :7890` 确认只有一个代理进程在监听。

**Q5：试用期能连上但频繁断流，是节点问题还是客户端问题？**
先用 `tcping -c 100` 打节点端口，看丢包是否集中在连接层。如果 tcping 稳定而实际使用断流，问题在协议层（MTU、分片、uTLS 指纹）。把 MTU 降到 `1380` 试一次。

**Q6：怎么判断一个机场是不是真专线？**
只看一件事：**晚高峰丢包率**。真 IPLC/IEPL 在 21:30 的丢包率通常 `< 0.3%`，且 RTT 全天波动 `< 15ms`。公网中转几乎不可能做到。这也是为什么在高强度使用场景下，像 [光速云](/reviews/guangsucloud/) 这类明确以 IEPL 内网专线 + 全球 IPLC 为主干、并公开单节点带宽上限的服务，会更值得在试用阶段重点验证其晚高峰曲线。

**Q7：试用期测出来全绿，是不是就能买年付了？**
不要。建议节奏是：试用 → 月付 1 个月 → 季付 → 再考虑年付。机场行业的生命周期波动很大，一次性投入超过 3 个月的费用，风险收益不划算。
