# 真假 CN2 GIA 路由追踪实战：手把手教你看懂去程回程 59.43 节点

## TL;DR：三句话看懂真假 GIA

第一，**去程看"起点"**：真正的 CN2 GIA，从你本地省网出口之后的第一跳就应该进入 `59.43.x.x`，而不是先在 `202.97.x.x`（163 骨干）里绕一大圈才切进去。

第二，**回程看"首跳"**：从落地机房出来的第一跳或第二跳就直奔 `59.43.x.x`，全程不夹 `202.97`，才叫回程 GIA。

第三，**稳定看"晚高峰"**：路由表写得再漂亮，20:00–23:00 电信方向丢包超过 `1%`、抖动超过 30ms，那就是超售或者伪 GIA。路由是"资格赛"，晚高峰表现才是"决赛"。

本文不讲玄学，只讲能复现的判定方法。所有命令你都可以直接复制粘贴执行。

## 一、为什么 59.43 是分水岭：从物理链路说起

中国电信的国际出口骨干有两条完全不同的腿：

**第一条腿是 163 骨干（AS4134）**，也就是你 traceroute 里最常见的 `202.97.x.x`。它是 1990 年代建设的公共互联网出口，全国所有家宽、IDC 流量默认都往这里挤。它的特点是：带宽池共享、无差异化 QoS、晚高峰必堵、丢包随机。国内三大运营商的互联互通也大量依赖它。

**第二条腿是 CN2（AS4809）**，2005 年前后建成，定位是"精品承载网"。它内部又分两档：

- **CN2 GT（Global Transit）**：国内段仍然走 163（`202.97`），只在国际出口之后才切入 `59.43`。本质上还是"163 的改良版"，晚高峰该堵还是堵。
- **CN2 GIA（Global Internet Access）**：从省级城域网直接接入 CN2 核心，**国内段就是 `59.43.x.x`**，一直跑到国际落地。这也是为什么 GIA 的单价通常是 GT 的 3–8 倍。

所以 `59.43` 这个网段（`59.43.0.0/16`）本身没魔力，**它的魔力在于"出现的位置"**。位置越靠前（跳数越小），说明你的流量越早脱离了 163 的泥潭。

再往上还有一层：**IEPL / IPLC 物理专线**。它们不走公网 BGP，而是运营商之间点对点拉一根二层以太网专线（IEPL）或时隙专线（IPLC），两端是独立内网 IP，中间不过公网路由表。延迟可以压到 GIA 的 70% 左右，且**几乎不受晚高峰影响**——但价格是另一回事，且带宽通常是固定小水管（10M/50M/100M 这种）。

至于 **BBRv3**，它是 Google 的拥塞控制算法，作用是"在已经丢包的链路上把吞吐抢回来"。它能让 5% 丢包的链路跑出可用体验，但**它不能降低延迟、不能修复路由绕路、不能把 163 变成 GIA**。很多人误以为装了 BBR 就是好线路，这是逻辑错位。

## 二、去程与回程：为什么"半程 GIA"是最常见的坑

网络是双向的。你去访问服务器走一条路，服务器回你走另一条路，**这两条路在 BGP 世界里完全独立**。

- **去程（Outbound / 本地 → 服务器）**：由你的运营商（电信/联通/移动）决定选路，商家无法控制你在国内怎么走。
- **回程（Inbound / 服务器 → 本地）**：由服务器所在机房的 BGP 策略决定，**这才是商家真正能花钱买的东西**。

市面上 90% 的"CN2 GIA 机场/VPS"实际上是：

| 类型 | 去程 | 回程 | 实际体验 |
| --- | --- | --- | --- |
| 真·双向 GIA | 59.43 全程 | 59.43 全程 | 晚高峰稳如狗 |
| 半程 GIA | 202.97 → 59.43 | 59.43 全程 | 下载稳，但请求延迟抖 |
| 伪 GIA | 202.97 全程 | 202.97 全程 | 和 163 没区别 |
| 反向半程 | 59.43 全程 | 202.97 全程 | 上传/回包丢得厉害 |

**"半程 GIA"是最难识别的**：商家在宣传页放一张回程漂亮的 traceroute 截图，你本地去程却在 163 里堵着。所以必须**双向都测**，而且要用**不同运营商**分别测。

还有一个隐藏变量是**双 ISP 接入**。优质机房会同时接入电信 CN2 + 联通 CUII（`9929`）+ 移动 CMI（`223.120`），做 BGP 多线。这样电信用户走 GIA、联通用户走 9929，各走各的精品线。这种架构的成本远高于单线，是判断商家"有没有真花钱"的关键信号。

## 四、分人群选型：别用 GIA 的价格买 163 的体验

**场景 A：跨境远程办公 / 代码仓库同步 / SSH 长连接**
核心痛点是**请求-响应延迟**和**长连接稳定性**，不是峰值带宽。优先选双向 GIA 或 IEPL，节点落地选日本/新加坡（延迟 40–70ms），比美西更舒服。参考 [/scenario/remote-work/](/scenario/)。

**场景 B：4K 流媒体 / 大文件下载**
需要的是**持续吞吐**。GIA 的 100M 共享带宽在晚高峰可能掉到 30M。这类用户更适合"专线 + 大带宽共享"的组合，或者直接选 IEPL 大带宽套餐。

**场景 C：跨境直播 / 实时音视频**
对**抖动**极度敏感。抖动超过 30ms 就会出现画面马赛克。必须选 IEPL 或至少双上联 GIA，且要避开超售比高的低价商家。

**场景 D：多设备 / 家庭共享**
需要并发连接数支持。注意看商家的"同时在线设备数"限制，以及是否有 NAT 类型优化。

**场景 E：预算敏感型轻度用户**
老老实实买 CN2 GT 或优质 BGP 中转即可，别为用不上的 GIA 溢价买单。详细选型维度见 [/scenario/](/scenario/)。

## 五、实操：分平台路由追踪与配置

### 5.1 Windows：BestTrace（IPIP.net 出品）

下载后解压即用，无需安装。关键操作：

1. 输入目标 IP 或域名，**勾选"显示 AS 号"**（这一步最重要，能直接看到 `AS4809`）。
2. 选择"Tracert"模式，等待完成。
3. **重点看第 1 跳之后的前 5 跳**：

```
1  192.168.1.1        [局域网]
2  100.64.0.1         [运营商 CGNAT]
3  59.43.18x.x        AS4809   ← 真 GIA 在这里就能看到
4  59.43.24x.x        AS4809
...
```

如果第 3–8 跳全是 `202.97.x.x AS4134`，直到第 9 跳才出现 `59.43`，那就是 CN2 GT 而非 GIA。

### 5.2 macOS / Linux：NextTrace 或原生 traceroute

macOS 建议用 NextTrace（支持 TCP 探测，更容易穿透 ICMP 限速）：

```bash
# 安装
brew install nexttrace

# TCP SYN 探测，最贴近真实网页访问
nexttrace -T -p 443 1.2.3.4

# 同时解析 ASN 与地理位置
nexttrace --map 1.2.3.4
```

原生命令要用 TCP 模式，因为很多骨干路由器对 ICMP 做了限速或直接不回：

```bash
# macOS / Linux
sudo traceroute -T -p 443 -n -q 1 -w 1 1.2.3.4

# Windows
tracert -d -h 20 1.2.3.4
```

### 5.3 测回程：必须登录到服务器执行

回程测试**只能在服务器端做**，因为回程路由由服务器机房决定。

```bash
# 1. 先拿到你本地的公网 IP
#    在浏览器打开 ip.sb 或 ipinfo.io 查看

# 2. 登录 VPS，向你的本地 IP 做追踪
traceroute -T -p 443 -n 你的本地公网IP

# 3. 或者用国内公共测试 IP 做回程基准
#    电信上海： 180.153.28.1
#    联通北京： 123.125.99.1
#    移动广东： 211.136.192.1
besttrace -q 1 180.153.28.1
```

**判定标准**：回程结果里第一个 `59.43` 出现的跳数 ≤ 3，且中间不夹杂 `202.97`，就是标准的回程 GIA。

### 5.4 客户端侧配置要点（避坑）

- **不要开"全局代理"后再测速**。测速时走的是代理出口，路由追踪结果会失真。测试时必须**直连目标 IP**。
- **关闭 IPv6**。很多商家 IPv6 走的是完全不同的路径（可能是 163），会污染你的判断。
- **禁用本地 DNS 缓存**。`ipconfig /flushdns`（Windows）或 `sudo dscacheutil -flushcache`（macOS）。
- **TLS Reality / XTLS 类协议**对路由无影响，但会增加 5–15ms 握手开销，测速时注意区分是线路问题还是协议开销。更多配置细节见 [/tutorial/](/tutorial/)。

## 六、抓包排障诊断手册

### 6.1 必备命令速查

```bash
# ① 连续 100 个 TCP 包的路由质量（最推荐）
mtr -rwzc 100 -T -P 443 1.2.3.4

# ② 只看某一段路径的丢包分布
mtr --report --report-cycles 200 --tcp --port 443 1.2.3.4

# ③ TCP 握手延迟（真实建连耗时）
curl -o /dev/null -s -w "DNS: %{time_namelookup}s | TCP: %{time_connect}s | TLS: %{time_appconnect}s | TTFB: %{time_starttransfer}s\n" https://example.com

# ④ tcping（Windows 需先安装 tcping.exe）
tcping -t -n 100 1.2.3.4 443

# ⑤ 大包探测 MTU / 分片问题
ping -M do -s 1472 1.2.3.4     # Linux
ping -f -l 1472 1.2.3.4        # Windows

# ⑥ 路由历史快照（判断是否动态绕路）
nexttrace --trace 1.2.3.4 && sleep 60 && nexttrace --trace 1.2.3.4
```

### 6.2 结果判定表

| 现象 | 可能原因 | 处理动作 |
| --- | --- | --- |
| 中间跳大量 `* * *`，但末跳正常 | 骨干路由器 ICMP 限速（正常） | 换 TCP 模式重测，忽略星号 |
| 从第 N 跳开始持续丢包，且后续跳也丢 | 该跳链路真实拥塞 | 对比晚高峰/凌晨数据，确认是否为超售 |
| 首跳就丢包 | 本地网卡/路由器问题 | 检查本地 MTU、网线、Wi-Fi 干扰 |
| TCP 追踪与 ICMP 追踪路径完全不同 | 运营商差异化 QoS | 以 TCP 结果为准（更贴近实际） |
| 延迟曲线呈阶梯状（每跳 +30ms） | 跨洋绕路（如经欧洲） | 要求商家优化，或换机房 |
| 同一目标，电信走 GIA、联通走 163 | 商家只买了电信精品线 | 联通/移动用户需另选，见 [/scenario/](/scenario/) |
| TTFB 高但 TCP 握手快 | 服务端处理慢，非线路问题 | 排查服务端，别冤枉线路 |

### 6.3 一个真实排障案例

某用户反馈"晚高峰 4K 卡顿，但白天正常"。

排查过程：

1. `mtr -rwzc 100 -T -P 443` 显示第 7 跳（`59.43.18x.x`）丢包 4.2%，其余跳 `0%`。
2. 换 `nexttrace` TCP 模式复测，同样的丢包点。
3. 切换联通线路测同一目标，走的是 `219.158`，零丢包。
4. **结论**：该商家的 GIA 带宽池在电信方向已接近饱和，属于典型的"GIA 线路 + 超售"。GIA 不是免死金牌，**带宽池大小才决定晚高峰表现**。

## 七、行业避坑矩阵：识别 6 种常见套路

| 套路 | 表面话术 | 真实情况 | 验证方法 |
| --- | --- | --- | --- |
| **伪 GIA** | "CN2 GIA 高速线路" | 全程 `202.97`，一丁点 59.43 都没有 | traceroute 全程查找 `59.43` |
| **半程 GIA** | 放一张漂亮回程截图 | 只买了回程 GIA，去程在 163 堵 | 必须自己跑双向追踪 |
| **GT 冒充 GIA** | "CN2 精品线路" | 是 CN2 GT，出境后才有 59.43 | 看首个 59.43 出现的跳数 |
| **虚假解锁** | "全解锁 Netflix/Disney+" | 用 DNS 劫持伪装，实际区域错乱 | 登录账号看内容库 + 查 IP 归属 |
| **超售挤兑** | "500M 大带宽" | 50 人共享 500M，晚高峰掉到 5M | 晚高峰多次测速取 P5 值 |
| **共享 IP 污染** | "原生 IP" | IP 段被大量用于爬虫，已被风控 | 查 IP 历史信誉、黑名单命中情况 |

关于 IP 纯净度的判定，可以看 [/tech/ip-purity/](/tech/ip/)。一句话原则：**便宜到离谱的 GIA，一定在别的地方省了钱**。

## 八、FAQ：7 个真实痛点

**Q1：只有去程有 59.43，回程是 202.97，算真 GIA 吗？**
不算双向 GIA，属于"反向半程"。这类线路下载（服务器→你）会走 163，晚高峰丢包明显。除非你只做上传类业务，否则不建议。

**Q2：59.43 出现了，但延迟 250ms，正常吗？**
不正常。`59.43` 只是资格证明，不代表路径最优。可能是绕了美国西海岸→东海岸→欧洲，或者落地机房回程绕行。要看**整体路径的跳数和地理走向**，而不只看有没有 59.43。

**Q3：装了 BBRv3，晚高峰还是丢包，是不是算法没用？**
BBRv3 解决的是"丢包后的吞吐恢复"，不是"防止丢包"。链路本身拥塞导致的丢包，算法无能为力。真正解法是换线路或降低并发。

**Q4：traceroute 结果里有 `* * *`，是线路坏了吗？**
绝大多数情况是骨干路由器对 ICMP 做了限速或禁用响应，属于正常现象。用 `-T -p 443` 走 TCP 探测通常能看到结果。判定线路质量要看**末跳延迟和最终丢包率**，不要被中间星号误导。

**Q5：为什么我用电信和联通测同一台服务器，路径完全不同？**
因为 BGP 选路基于各运营商的策略和商业关系。电信有 CN2，联通有 CUII（`9929`），移动有 CMI。优质机房会针对三大运营商分别优化，这就是"双 ISP / 三线"的价值所在。完整解读见 [/tech/](/tech/)。

**Q6：落地 IP 说是"原生 IP"，怎么验证？**
三步：① 用 `whois` 查 IP 的注册国家和 ASN 归属；② 用多个 IP 信誉库查是否在黑名单；③ 实际访问目标服务（如流媒体、银行）看是否触发风控。仅"IP 归属地正确"不等于"干净"。

**Q7：ICMP 追踪和 TCP 追踪结果差很多，信哪个？**
信 TCP。ICMP 在骨干网被普遍降级处理，而 TCP 443 是你实际访问时走的路径。所有严肃的线路评测都应基于 TCP 探测。
