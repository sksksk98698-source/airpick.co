## 一、TL;DR：2026 年挑 IEPL 机场，先卡死这五条硬线

先把结论放在最前面，后面再讲为什么。

1. **链路层面**：只认物理层直连的 IEPL / IPLC，跨境段绕开公网骨干与运营商出口 QoS 队列。2026 年最泛滥的偷换概念是「IEPL 标签 + 公网中转」——包装上写着专线，最后一公里还是走 163/CMI 公网，晚高峰照样掉到个位数 Mbps。
2. **带宽模型**：看**独享口规格**和**峰值并发能力**，不看机房总带宽那种「100Gbps 互联」的营销数字，那跟你没关系。
3. **IP 质量**：优先原生段或双 ISP 广播段。要跑 ChatGPT、Claude、Gemini、Netflix 非自制剧，出口 IP 的 ASN 归属和滥用评分比带宽更决定成败。
4. **协议栈与倍率**：全节点 x1 无倍率、不搞「专线节点单独计费」的套路；专线段用 TCP + BBR，公网接入段再叠 Hysteria2 / TUIC 优化最后一公里。
5. **价格锚点**：IEPL 的物理成本摆在那，月付十几块钱还号称 IEPL 全节点的，基本可以默认是公网直连伪装的。

## 二、物理层真相：IEPL 到底是怎么做到「不过墙」的

### 2.1 IEPL / IPLC / 公网中转，本质差在哪

先把名词捋直：

- **IPLC（International Private Leased Circuit）**：点对点专线电路，早年以 TDM/SDH 时代为主，物理上是「一根线从上海拉到东京」，两端只属于你。优点是绝对确定性，缺点是贵、扩容慢、按带宽阶梯定价。
- **IEPL（International Ethernet Private Line）**：以太网专线，本质是 IPLC 的以太网化演进，同样是运营商级二层/三层专网，但支持更灵活的带宽颗粒度（10M / 50M / 100M / 1G / 2.5G）和更快的扩容周期。这也是 2026 年主流中高端机场的技术底座。
- **公网中转**：境内入口机 → 公网骨干（163 / CN2 GT / CMI / CUII）→ 落地机。它便宜、弹性好，但跨境段和普通用户共享同一条出口队列。
- **隧道直连**：客户端直接和境外落地机建 TLS / QUIC 会话，路径完全公网。这是最容易被 QoS 狙击的形态。

关键区别在于：**IEPL 的跨境段不过公网出口的 QoS 队列**。运营商给你的是一条逻辑独立的通道，带宽在合同里写死，不参与普通宽带用户的国际出口争抢。这就是所谓「不过墙」的技术实质——不是「绕过检测」，而是**根本没走到会被检测与限速的那段公网路**。

需要说清楚的一点：IEPL 只解决「跨境段」的确定性，落地之后从境外机房到 Google / OpenAI / Netflix 的**后半程仍然是公网**。所以一家机场只有跨境专线、落地机房却接在垃圾 Tier 3 线路上，体验一样拉胯。选机场看的是**端到端**，不是单看有没有 IEPL 三个字。

### 2.2 QoS 队列与超售：专线也会堵

IEPL 不是免死金牌。一条 1Gbps 的专线，卖给 300 个用户每人「1Gbps 峰值」，超售比就是 300:1，晚高峰一样排队。判断超售水平有几个实操信号：

- 白天单线程轻松跑满 300Mbps，晚高峰掉到 30Mbps 以下，且**丢包率同步上升**——典型的出口队列打满。
- 延迟基本稳定但吞吐骤降，说明通道没堵，是**落地侧出口或 NAT 会话表**到瓶颈了。
- 只有 TCP 慢、UDP 正常（或反之），往往是**运营商对特定协议做了分类整形**。

真正健康的 IEPL 机房会做**带宽预留 + 用户并发上限 + 队列调度（如 fq_codel / CAKE）**，用工程手段把超售比压到 20:1 以内。这一点在测评里几乎看不出来，只能靠长时间压测和晚高峰复测验证。

### 2.3 BGP 选路与「双 ISP」入局

跨境专线落地后的后半程路由质量，取决于落地方与上游的 BGP 关系：

- **单上游**：便宜，但上游抖动时无路可退，典型症状是某些时段对某家云厂商（如 AWS 某个 region）特别慢。
- **双 ISP / 多宿主**：同时接入两家以上 Tier 1/2（如 NTT + Cogent、PCCW + Telia），通过 LOCAL_PREF 与 AS-Path 策略做优选，单边上联故障时可秒级切换。这是 2026 年顶级机场的标配。
- **IX 直连**：在 JPIX / HKIX / Equinix 等交换中心与 Google、Cloudflare、Akamai 直接 Peering，能把到主流服务的 RTT 再压 5–15ms，同时显著降低绕路带来的丢包。

实操验证方法：落地到目标服务的路径长度（`mtr` 跳数）、是否出现绕美绕欧（RTT 突然飙到 200ms 以上），比机房自己写的「三网优化」有说服力得多。

### 2.4 传输层与协议：BBRv3、TLS Reality 各自解决什么

- **BBRv3**：拥塞控制算法，重点是**在高丢包链路上不掉速**。跨境专线本身低丢包，BBRv3 的收益主要在落地后公网段与移动网络接入段。开了不是玄学，但也不是万能药。
- **TLS Reality**：把服务端流量伪装成访问真实大站的 TLS 握手，抗主动探测。它对**入口机暴露在公网**的机场价值最大；如果入口本来就在专线内网，收益边际递减。
- **Hysteria2 / TUIC**：基于 QUIC，靠激进的拥塞控制 + 前向纠错在劣质链路上抢吞吐。适合家宽晚高峰被 QoS 的场景，缺点是**吃 CPU、UDP 容易被运营商整形**，在专线节点上通常没必要开。
- **多路复用（mux / smux）**：能降低握手开销，但会引入队头阻塞，在单节点大流量场景下反而降速。**专线节点建议关闭 mux**。

## 三、核心参数对比矩阵（10 项量化指标）

下表是 AirPick 实验室在 2026 年 Q1 用同一台测试机（千兆家宽 + 独立 5G 备份线路）对四类链路形态做的横向取样，数值为中位数区间，仅代表该类形态的典型水平。

| 量化维度 | 公网隧道直连 | 三网优化中继（CN2 GIA / CMI） | IPLC 点对点专线 | IEPL 以太网专线（旗舰级） |
| --- | --- | --- | --- | --- |
| 跨境物理路径 | 公网出口共享 | 公网优质骨干 | 运��商二层专网 | 运营商二层专网 |
| 晚高峰丢包率 | 3%–15% | 0.5%–3% | `<0.3%` | `<0.1%` |
| 单程 RTT（华东→东京） | 45–90ms | 38–55ms | 30–38ms | 28–35ms |
| 抖动 Jitter（1 分钟窗口） | 15–60ms | 5–15ms | 1–3ms | `<2ms` |
| 单节点峰值带宽 | 100–500Mbps | 300Mbps–1Gbps | 500Mbps–1Gbps | 1Gbps–2.5Gbps |

几点读表说明：

- **不要只看 RTT**。28ms 和 45ms 的体感差异远小于「0.1% 丢包 vs 8% 丢包」——后者会让 TCP 反复触发重传与拥塞窗口回退，实际吞吐可能差 10 倍。
- **抖动比延迟更重要**。视频会议、云游戏、SSH 交互对抖动的敏感度高于绝对延迟。
- **价格锚点是最强的筛子**。IEPL 的运营商成本决定了它的价格下限，凡是远低于锚点区间的「IEPL 全场」，八成是标签工程。

## 四、细分人群与场景选型

**① 跨境办公 / 远程开发（GitHub、AWS、Slack、Jira）**
优先级：稳定性 ＞ 延迟 ＞ 带宽。选 IEPL + 双 ISP 落地的节点，重点看**抖动**和**长连接是否被断**。SSH / VPN 会话被中途掐断，多半是出口 NAT 会话表超时太短或链路切换导致，不是带宽问题。

**② AI 重度用户（ChatGPT、Claude、Gemini、Cursor）**
优先级：IP 纯净度 ＞ 稳定性 ＞ 带宽。必须用原生或双 ISP 段，共享广播段极易触发风控与「unsupported country」。建议固定一个节点长期使用，频繁换 IP 反而更容易被判定异常。详见 [ChatGPT 场景专项配置](/scenario/)。

**③ 4K / 8K 流媒体（Netflix、Disney+、YouTube）**
优先级：单线程带宽 ＞ IP 归属 ＞ 延迟。4K 稳定播放需要持续 25Mbps 以上单线程吞吐，8K 需要 80Mbps 以上。注意区分「真解锁」与「DNS 分流解锁」——后者在换设备、换 DNS 后立刻失效。参考 [流媒体解锁判定方法](/scenario/streaming/)。

**④ 游戏与实时交互**
优先级：抖动 ＞ RTT ＞ 带宽。IEPL 的价值在这里体现得最明显，因为游戏对丢包的容忍度接近于零。不要开 mux，不要让 UDP 走代理链路的二次转发。

**⑤ 多设备 / 团���共享 / 路由器级部署**
优先级：并发稳定 ＞ 单点峰值 ＞ 协议兼容。选支持多协议（SS / VMess / VLESS / Trojan / Hysteria2）且订阅格式规范的机场，方便在 OpenWrt、软路由、NAS 上统一分发。见 [路由器端部署指南](/tutorial/)。

## 五、分平台实操配置与深度避坑

**Windows（Clash Verge Rev / v2rayN）**
开启 TUN 模式接管全局流量，但**务必在规则里放行内网段（192.168.0.0/16、10.0.0.0/8）**，否则 NAS、打印机、Docker 容器直接失联。另外把 DNS 设为 DoH（如 `https://1.1.1.1/dns-query`）并开启「DNS 泄漏防护」，避免系统 DNS 走明文出网。

**macOS（Clash Verge / Surge / Stash）**
Surge 用户注意 `enhanced mode` 与系统代理的叠加问题；Clash Verge 用户记得把 mihomo 内核升级到 2026 年最新版，否则新协议（如 VLESS Encryption）不识别。

**iOS（Shadowrocket / Stash / Quantumult X）**
不要在「全局路由」里选全局代理——耗电翻倍且部分 App 会直接报错。用「配置」模式配好分流规则。Shadowrocket 记得开启 `On Demand`，配合「按需连接」才能在蜂窝网络切换时自动恢复。

**Android（Clash Meta for Android / Surfboard）**
注意系统级「私人 DNS」会劫持解析，必须设为「关闭」或指向代理链路的 DoH，否则会出现**连接成功但部分域名解析失败**的诡异现象。

**路由器 / 软路由（OpenWrt + mihomo / nikki）**
最容易踩的坑是 **MTU**。IEPL 链路经过隧道封装后，可用 MTU 通常要下调到 1400–1420，否则表现为「小包正常、大包卡死、网页打不开但能 ping 通」。同时记得给 UDP 单独配置策略，别把游戏和 WebRTC 一起丢进代理。

**通用避坑清单**：

- 不要长期开「全局代理」，会放大 DNS 泄漏面。
- 不要同时开多个代理客户端，TUN 与系统代理冲突会导致路由环。
- 不要在专线节点上开 mux / 多路复用，反而降速。
- 不要频繁切换节点去「解锁」，同一 IP 段反复横跳更容易触发风控。
- 订阅链接用本地文件导入而非 URL 远程订阅，可减少订阅域名被污染时的批量失效。

## 六、抓包与排障诊断手册

遇到「卡、慢、断」三连，别急着重装客户端，按下面这套顺序做一遍，90% 的问题能定位到具体环节。

```bash
# 1. 链路逐跳与丢包分布（取样 100 包，只关心末跳与中间跳的差异）
mtr -rwzc 100 -P 443 你的节点IP

# 2. TCP 握手 RTT 与丢包（三次握手层面的可用性）
tcping -t 5 -n 20 你的节点IP 443

# 3. TLS 分层耗时：DNS / TCP / TLS / 首字节
curl -o /dev/null -s -w "dns:%{time_namelookup}s connect:%{time_connect}s tls:%{time_appconnect}s ttfb:%{time_starttransfer}s total:%{time_total}s\n" https://www.gstatic.com/generate_204

# 4. 出口 IP 与 ASN 归属（判断是不是原生 / 广播段）
curl -s https://ipinfo.io/json

# 5. MTU / 分片黑洞探测（专线隧道最常见坑）
ping -M do -s 1472 -c 5 你的节点IP

# 6. TLS 版本与证书链协商确认
openssl s_client -connect 你的节点IP:443 -tls1_3 -brief
```

**判定对照表**

| 现象 | 疑似根因 | 处置方向 |
| --- | --- | --- |
| mtr 中间第 3–6 跳起大量丢包，末跳正常 | 中间节点不响应 ICMP，属正常，不必处理 | 忽略，看末跳指标 |
| mtr 中间与末跳同步丢包 | 公网骨干拥塞 / 出口 QoS 限速 | 该节点非真专线，换节点或换机场 |
| 全程 0 丢包但 RTT 抖动超过 30ms | 专线队列打满、超售严重 | 记录晚高峰数据，反馈或换机场 |
| tcping 正常但 curl 的 ttfb 异常大 | 落地出口拥塞、DNS 污染、或目标站限速 | 换 DNS 为 DoH，测试同机房其他落地点 |
| 小包通、大包卡、网页打不开 | MTU / MSS 黑洞 | 下调 MTU 至 1400–1420，或开启 MSS Clamping |
| 速度正常但特定 App 无法登录 | 分流规则命中错误 / UDP 被丢弃 | 检查规则优先级与 UDP 转发策略 |
| 白天正常、晚 8–11 点崩 | 典型超售高峰 | 对照 `mtr` 丢包曲线，作为换机场依据 |

**压测建议**：单线程和多线程各测一次，用 `iperf3 -c 测试IP -P 1` 与 `-P 8` 对比。单线程能跑满说明链路干净；只有多线程跑得起来说明存在单流整形或队列公平性差。

## 七、行业避坑矩阵：这些话术 2026 年还在骗人

| 营销话术 | 实际含义 | 验证方式 |
| --- | --- | --- |
| 「IEPL 专线，全节点不过墙」 | 可能只是入口在专线，落地和出口仍是公网 | `mtr` 看全程路径，晚高峰复测丢包 |
| 「总带宽 100Gbps」 | 机房整体互联带宽，与你无关 | 问单节点独享口规格与并发上限 |
| 「真原生 IP」 | 多为广播段，或仅部分节点原生 | `curl ipinfo.io/json` 查 ASN 与 type |
| 「全解锁 Netflix 全区」 | 常用 DNS 分流伪造解锁页 | 换设备 / 换 DNS / 开飞行模式复测 |
| 「无限流量，不降速」 | 通常有隐藏的公平使用策略或并发限制 | 连续
