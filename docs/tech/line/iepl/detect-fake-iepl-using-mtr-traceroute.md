# 真假 IEPL 鉴定实战：如何利用 MTR 和路由追踪揪出公网伪装专线

## 一、TL;DR：三分钟结论先行

如果你只想拿走一句话的答案：**在 2026 年，判断一条线路是不是真 IEPL，最有效的单点证据不是测速，而是 `mtr` 出来的「中间跳 AS 号」和「TTL 转折模式」**。速度可以靠超售用户的运气伪造，但一跳一跳的 AS 号不会撒谎。

三个可直接落地的判定口径：

1. 从中国大陆入口到香港/日本落地，**真 IEPL 在 `mtr` 上通常只显示 2–5 跳**，且中间跳要么是 RFC1918 私网地址（`10.x` / `172.16-31.x` / `192.168.x`），要么干脆被运营商 ICMP 抑制显示为 `???`。
2. 如果中间跳里密集出现 **`AS4134`（电信 163）、`AS4837`（联通 169）、`AS9808`（移动 CMI）、`AS58453`（CMI 国际）** 的公网 IP，基本可以断定你走的是公网中转，"IEPL" 只是营销话术。
3. 真专线的延迟**方差极小**：连续 100 次 `mtr` 的 `StDev` 一般落在 `1–5 ms`；公网中转在晚高峰的 `StDev` 常飙到 `30–120 ms`。这是比平均延迟更硬的证据。

## 二、底层机理：IEPL、IPLC 与「公网中转」到底差在哪

先把名词理清楚，否则一切鉴定都是玄学。

**IEPL（International Ethernet Private Line）** 和 **IPLC（International Private Leased Circuit）** 都是运营商级的**点对点二层专线**。物理上，它们在跨境段走的是运营商自建或租用的海底光缆暗光纤资源，通过 SDH/OTN 承载；逻辑上，两端之间的流量**不进入公共互联网**，不经过任何第三方 AS 的路由器转发。

这意味着两件关键的事：

- **路径确定性**：专线是"电路交换"思维，路由表里根本查不到中间的转发节点，因为中间根本没有 IP 层转发。这也是为什么真专线 `mtr` 中间经常是 `???`——不是探测失败，而是**那一段压根没有可被 ICMP 回应的三层接口**。
- **拥塞隔离性**：公网流量走的是"尽力而为"（Best Effort）模型，被 `QoS` 分级、被 `BBRv3` 重传、被骨干网抖动牵连。专线有独立的带宽承诺（CIR），别人晚高峰刷 4K，跟你没关系。

而市面上大量"伪 IEPL"，其实是这几种东西的排列组合：

| 伪装名目 | 真实架构 | 识别特征 |
| --- | --- | --- |
| 「IEPL 中转」 | 国内 BGP 入口 → 公网 163/169 → 海外落地 | 中间跳出现 `AS4134` / `AS4837` |
| 「IPLC 专线」 | 海外 VPS 之间打隧道（GRE/WireGuard） | 中间跳全是公网 IP，AS 号跳跃 3 个以上 |
| 「CN2 GIA 专线」 | 电信 CN2 GIA 商业线路 | 出现 `AS4809`，属半真半假（高端公网） |
| 「三网优化」 | 三线 BGP + 智能 DNS 调度 | 高峰 StDev 剧烈波动 |

顺带说一句 `TLS Reality` 等抗封锁协议：它们解决的是**握手特征被识别**的问题，跟线路质量无关。很多人把"能用 Reality、能连上"当成"线路好"的证据，这是两码事——协议层和链路层是两个正交维度。

再看 **双 ISP / BGP Anycast** 这一层：正规服务商会在香港、日本、新加坡同时接入 2–3 家运营商（如 HKT + PCCW + NTT），一旦一条链路被切，BGP 会在秒级重收敛。**这也是判断服务商是否"真有钱"的旁证**——能同时买多家上游 transit 的，通常不会拿公网中转来糊弄你。

以下数值来自 AirPick 实验室在 2026 年 1 月对 30+ 条线路的采样，采样窗口覆盖工作日 21:00–23:00 晚高峰。

| # | 量化指标 | 真 IEPL / IPLC | 公网中转伪专线 | CN2 GIA（高端公网） | 判定权重 |
| --- | --- | --- | --- | --- | --- |
| 1 | 中间三层跳数（大陆→HK） | 2–5 跳 | 8–16 跳 | 6–10 跳 | ★★★★★ |
| 2 | 中间跳 AS 号种类 | 0–1 种（多为私网） | 3–6 种 | 1–2 种（AS4809） | ★★★★★ |
| 3 | 平均 RTT（沪→HK） | 12–28 ms | 35–80 ms | 25–45 ms | ★★★★ |
| 4 | RTT 标准差 StDev | `1–5 ms` | `30–120 ms` | `8–25 ms` | ★★★★★ |
| 5 | 晚高峰丢包率 | `< 0.3%` | `2%–15%` | `0.5%–3%` | ★★★★ |
| 6 | 抖动 Jitter（p95） | `2–8 ms` | `40–200 ms` | `10–40 ms` | ★★★★ |
| 7 | 单节点可用带宽上限 | 1–10 Gbps | 100–500 Mbps | 500 Mbps–2 Gbps | ★★★ |
| 8 | IP 纯净度（ChatGPT 风控通过） | 原生住宅/机房段 | 高度复用段 | 多数可用 | ★★★ |

**读表要点**：不要只盯着第 3 行"平均延迟"。伪专线完全可以把平均延迟做到 30 ms 以内——因为它就是靠"绕路但不堵"来骗你。真正暴露它的是第 4 行和第 6 行，也就是**稳定性**。

## 四、人群与场景选型推荐

不同的人对"专线"的需求完全不同，别被营销绑架。

- **纯网页 / 文档办公族（每天 1–3 GB）**：优先看第 2 行和第 8 行。你不需要 2.5 Gbps，但你需要 ChatGPT 不掉线、Google Docs 不同步失败。此时"原生 IP + 低抖动"比"大带宽"重要十倍。建议关注 [场景选型指南](/scenario/)。
- **视频 / 直播 / 4K 流媒体党**：看第 5 行和第 7 行。晚高峰丢包是 4K 卡顿的头号杀手，带宽反而是次要的。IEPL 的价值在这里最直观。
- **跨境开发者 / DevOps**：看第 9 行和第 6 行。`git clone`、`docker pull`、`npm install` 对**长连接稳定性**敏感，一次抖动就等于一次超时重试。建议直接看 [技术架构板块](/tech/)。
- **游戏加速 / 实时音视频**：看第 6 行 Jitter。IEPL 是唯一能让 `p95` 抖动压在 10 ms 以内的方案。
- **多设备家庭 / 小型团队**：看第 7 行和第 9 行，同时确认节点是否支持 `UDP` 与多并发。参考 [多设备教程](/tutorial/)。

## 五、分客户端 / 分平台实操配置与深度避坑

### Windows

- 推荐 `WinMTR` 或 `PingPlotter`，前者免费但已停更，后者有 GUI 曲线，适合看抖动趋势。
- **避坑**：Windows 自带防火墙会吞 ICMP，先临时关掉再测，否则你会误判成"中间跳全是 `???` 的好专线"。

### macOS / Linux

```bash
# 最常用：TCP 模式 + 100 包 + 0.2s 间隔 + 宽屏输出
mtr -rwzc 100 -i 0.2 --tcp --port 443 --psize 64 your-node.example.com

# 只看关键列，输出更清爽
mtr -rwzc 100 -o "LSDRA MXVW" your-node.example.com
```

### 路由器 / OpenWrt

- 装 `mtr` 后建议把 `mtr` 跑在**路由器本体**而不是电脑上，避免 NAT 转换影响 TTL 判定。
- **避坑**：很多路由器内置的"线路检测"是 HTTP HEAD 测速，那玩意只能测出通不通，测不出过不过墙。

### iOS / Android

- iOS 用 `iNetTools` 或 `HE.NET Network Tools`；Android 用 `PingTools`。
- **避坑**：移动端 App 受蜂窝网络 NAT 限制，测出来的跳数天然比有线多 1–3 跳，别拿手机数据去否定一条真专线。

## 六、抓包排障诊断手册：命令 + 判定表

### 6.1 MTR 三连击

```bash
# 1) 基础 TCP 追踪（穿透大多数 ICMP 抑制）
mtr -rwzc 200 --tcp --port 443 --psize 64 node.example.com

# 2) UDP 模式对照（部分线路对 TCP 探测有特殊处理）
mtr -rwzc 200 --udp --port 443 node.example.com

# 3) 高频短测，专门看抖动收敛
mtr -rwzc 500 -i 0.1 node.example.com
```

### 6.2 tcping / curl 补充证据

```bash
# 端口层延迟与丢包（Windows 与 Linux 均可用 tcping）
tcping -t -n 100 node.example.com 443

# 分阶段耗时：DNS / TCP / TLS / TTFB
curl -o /dev/null -s -w "dns:%{time_namelookup} tcp:%{time_connect} tls:%{time_appconnect} ttfb:%{time_starttransfer} total:%{time_total}\n" https://node.example.com
```

### 6.3 判定表

| 现象 | 真专线 | 公网中转伪专线 | 备注 |
| --- | --- | --- | --- |
| 第 3–6 跳出现 `10.x` / `192.168.x` | ✅ 常见 | ❌ 罕见 | 私网地址 = 未出公网 |
| 第 3–6 跳出现 `AS4134/4837/9808` | ❌ | ✅ 典型 | 直接判伪 |
| 中间跳全为 `???`，但 RTT 稳定 | ✅ 可能 | ⚠️ 需二次验证 | 用 `--tcp` 重测对照 |
| 首跳 RTT `> 80 ms`（大陆→HK） | ❌ | ✅ | 物理距离不支持 |
| 200 包 StDev `> 30 ms` | ❌ | ✅ | 铁证 |
| 末跳与终点 AS 不一致 | ❌ | ✅ | 落地被二次转发 |
| TTL 呈规律递减且无跳变 | ✅ | ⚠️ | 需结合 AS 判断 |

**一个容易被忽略的细节**：真专线由于是二层透传，`traceroute` 的 TTL 递减逻辑经常"断层"——比如前 2 跳 TTL=1、2，然后直接跳到 TTL=9。这种**不连续**反而是好信号，说明中间整段被 MPLS 或 OTN 封装掉了。

另一类硬核证据是看 **MTU**。很多伪专线走了隧道（GRE/IPsec/WireGuard），`ping -M do -s 1472` 会失败，因为隧道头占了字节。真 IEPL 通常支持完整 1500 MTU。

```bash
# Linux: 逐步逼近 MTU
ping -M do -s 1472 -c 3 node.example.com
# 若报 "Message too long"，说明有隧道封装，MTU &lt; 1500
```

## 七、行业常见避坑矩阵

| 宣传话术 | 常见真相 | 验证手段 |
| --- | --- | --- |
| 「IEPL 专线，不限速」 | 实际是 BGP 中转 + 高峰限速 | 晚高峰 `mtr` 看 StDev 与丢包 |
| 「直连香港，0 中转」 | 内地公网直连 HKIX | `mtr` 中间跳 AS 号必现 |
| 「原生 IP，全解锁」 | IP 段被数十人共用 | 查 IP 归属 ASN + 流媒体实测 |
| 「2.5G 独享」 | 峰值可达但持续限速 | `iperf3` 持续 60s 测平均值 |
| 「CN2 GIA 顶级线路」 | 实为 CN2 GT 或混合路由 | `mtr` 看是否全程 `AS4809` |
| 「不限设备数」 | 靠 IMEI/IP 指纹限并发 | 多设备同时压测 |

**最关键的一条心法**：任何声称"专线"的服务商，你都应该要求它给出**节点的 AS 号与上游 transit 名单**。给不出来的，一律按公网中转对待。这个信息在 [机场评测库](/reviews/) 里对每一家都有交叉验证。

## 八、常见问题 FAQ

**Q1：我用 `mtr` 测出来中间全是 `???`，是不是就是真专线？**
不一定。`???` 有两种成因：一是真专线二层透传无三层接口；二是对方路由器设了 `no ip unreachables` 或限速 ICMP。区分方法是换成 `mtr --tcp --port 443` 再测一次——真���线依然会是 `???`，而公网节点在 TCP 模式下会暴露出 IP。

**Q2：为什么我测速很快，但看 YouTube 还是转圈？**
测速走的是短连接突发，流媒体走的是长连接稳定传输。这是典型的"带宽够、抖动差"。查 `mtr` 的 `StDev`，如果大于 30 ms，就是链路抖动问题，跟带宽无关。

**Q3：机场说自己"过墙"，我该怎么验证？**
"过墙"是伪概念。准确的说法是"跨境段是否走专线"。看 `mtr` 第二、三跳之后是否立刻进入境外 AS。如果前面还在 `AS4134` 里绕了 5 跳才出境，那就是普通公网。

**Q4：晚高峰延迟从 25 ms 飙到 180 ms，是不是被超售了？**
大概率是。真专线有 CIR 承诺，晚高峰 RTT 波动通常 `±5 ms` 以内。飙到 7 倍说明带宽被共享，或者上游 transit 被 DDoS 波及。

**Q5：手机测的和电脑测的差这么多，信哪个？**
信电脑（有线）。蜂窝网络的 NAT 层数天然更多，且基站到核心网的路径不可控。所有严肃的线路评测都应该在有线环境下做，参考我们的 [测试方法论](/tech/)。

**Q6：`iperf3` 测出来只有标称速度的 30%，正常吗？**
如果是单线程测，正常。跨境链路的单流受 TCP 拥塞控制（`BBRv3` / `CUBIC`）和 `BDP` 限制，往往需要 `-P 8` 多流才能跑满。单流慢不代表线路差。

**Q7：IEPL 一定比 CN2 GIA 好吗？**
理论上是（专线 vs 公网），但成本差 5–10 倍。对绝大多数个人用户，优质 CN2 GIA 已经够用。只有对抖动极度敏感的场景（直播推流、实时交易、云游戏）才值得上真 IEPL。别为营销溢价买单。

## 十、结语

真假 IEPL 的鉴定，本质是一场**信息不对称的攻防**。服务商掌握节点与路由的全部信息，用户只能靠外部探测推断。而 `mtr` 恰恰是那个把黑箱撬开一条缝的工具——它不完美，中间跳可能被抑制、TTL 可能被伪造，但它给出的 **AS 号序列、跳数结构与统计方差**，是任何营销话术都无法长期掩盖的物理事实。

记住三条铁律：**看 AS 不看广告、看 StDev 不看均值、看晚高峰不看闲时**。

把这三条量化标准握在手里，你就不需要再相信任何人的"亲测推荐"——包括我们。所有数据都可以自己复现，这才是硬核玩家的底气。
