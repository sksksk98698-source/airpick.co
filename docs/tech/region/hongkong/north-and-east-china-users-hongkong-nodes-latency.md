# 华东与北方用户用香港节点划算吗：长途跨省内网传输延迟测算

> 站点路径：`docs/tech/region/hongkong/north-and-east-china-users-hongkong-nodes-latency.md` · 归属栏目：[/tech/region/hongkong/](/tech/region/)

## 一、TL;DR：先给结论，再看推演

一句话：**对华北、华东用户来说，香港不是"最优解"，而是"折中解"——它在延迟、带宽、IP 纯净度三者之间取得了一个还算能接受的平衡，但前提是你买到的是真正走了优化中转的线路。**

- 北京电信 163 直连香港，晚高峰实测常见 90-150ms；换成联通 9929 或移动 CMI，能压到 40-60ms；走 IEPL 京港专线的优质中转，可稳定在 28-40ms。
- 上海到香港的物理地板约 15-18ms（RTT），优质线路实际落在 22-32ms；上海到东京的地板约 20-23ms，实际 25-38ms。**上海的答案取决于用途：游戏/低延迟交互选香港，流媒体/AI 大带宽选日本。**
- 跨省中转"内网"并不是免费的：从华北出口绕到华南出口再落地香港，每绕一段就多 8-20ms 排队延迟，且晚高峰会被骨干 QoS 策略放大。
- 全国选型没有万能解：华北看联通 9929/移动 CMI，华东看电信 CN2 GIA/日本 IIJ，华南直连香港，西南可考虑新加坡，西北建议先解决本地出口质量再谈落地。

下面把物理层、协议层、运营层三层拆开讲。

---

## 二、物理层：光速不是营销话术，它是硬地板

所有延迟讨论都必须从光纤中的光速开始。真空光速约 `3×10^8 m/s`，但在石英光纤中，由于折射率约为 1.467，实际传播速度只有 `2.04×10^8 m/s` 左右，也就是每公里约 4.9 微秒。**来回一趟，就是每公里 9.8 微秒。**

据此可以算出几个不可突破的物理地板：

| 常用路径 | 直线距离 | 实际光缆绕行 | 单向理论延迟 | RTT 物理地板 |
| --- | --- | --- | --- | --- |
| 北京 → 香港 | 约 1970 km | 约 2400-2800 km | 12-14 ms | 24-28 ms |
| 上海 → 香港 | 约 1210 km | 约 1500-1800 km | 7.5-9 ms | 15-18 ms |
| 广州 → 香港 | 约 130 km | 约 180-260 km | 0.9-1.3 ms | 1.8-2.6 ms |
| 上海 → 东京 | 约 1770 km | 约 2100-2400 km | 10.5-12 ms | 21-24 ms |
| 北京 → 东京 | 约 2100 km | 约 2600-3000 km | 13-15 ms | 26-30 ms |

注意两点：

第一，**这个地板只计算了"光在玻璃里跑"的时间**，还没算路由器转发、光电转换、交换机排队、拥塞控制窗口爬升、TLS 握手往返。真实业务延迟通���是物理地板的 1.5-3 倍。

第二，跨省"内网传输"本质上就是服务商自建的跨省骨干或租用的 IEPL/IPLC 专线，把用户流量从本地出口拉到落地机房。它省掉的不是光速，而是**公网骨干的绕行和排队**。这就是为什么同样从北京出发，163 公网能给到 100ms+，而 IEPL 专线能压到 35ms 以内。

## 三、选路层：BGP、IEPL/IPLC、双 ISP 与 BBRv3 的四方博弈

### 3.1 BGP 选路：为什么你的包在"绕圈"

公网 BGP 遵循的是"最短 AS Path + 本地策略"，不是"最短物理距离"。北京电信的流量去香港，很可能先到上海、再到广州、再出海，甚至绕美国西海岸一圈回来。这解释了为什么 `mtr` 出来的跳数能到 20+ 而延迟居高不下。

关键判定：看 `mtr` 中每一跳的 AS 号和地理标注。如果出现 NTT、Telia、Cogent 这种 Tier-1 国际段，基本可以断定走的是公网绕行，晚高峰必炸。

### 3.2 IEPL vs IPLC：差在"独占"二字

- **IPLC（International Private Leased Circuit）**：物理层独占专线，两端固定，延迟抖动极小，价格最贵，通常按 `E1/T1` 或 `STM-1` 计费。
- **IEPL（International Ethernet Private Line）**：以太网专线，二层透传，可承载 VLAN，成本比 IPLC 低一档，是目前主流中高端机场/专线服务商的"内网"底座。
- **公网 + 优化路由**：通过购买优质上游带宽（如 PCCW、HKT、CMI、CN2 GIA）并做 BGP 调优，成本最低，但 QoS 不可控。

### 3.3 双 ISP / 多线接入的意义

华北用户接入方是电信、联通还是移动，决定了你出海的"第一公里"。香港侧落地的机房如果有双 ISP（如 HKT + PCCW + CMI 三线），就能针对不同省份用户做回程优化。**单 ISP 香港机房对北方用户几乎必然出现晚高峰抖动。**

### 3.4 BBRv3 与 TLS Reality：软件层的补偿

物理和选路是硬约束，软件层能做的是"减少浪费"：

- **BBRv3**：基于带宽时延积（BDP）建模的拥塞控制，比 CUBIC 在高带宽长肥管道（Long Fat Network）上提速 30-200%，尤其对北京→香港这种 40ms 链路，能显著改善大文件吞吐。
- **TLS Reality**：规避 SNI 阻断与主动探测，握手阶段借用真实网站证书指纹，降低被 QoS 降级的概率。

一句话：**硬件决定上限，软件决定你能拿到上限的百分之几。**

## 五、细分人群与场景选型：别用一把尺子量全国

**1. 华北游戏玩家（北京/天津/石家庄）**
优先级：延迟稳定性 `>` 绝对延迟 `>` 带宽。选联通 9929 或移动 CMI 中转的香港节点，或直连日本。避开纯公网香港线路。

**2. 华东办公/远程开发（上海/杭州/南京）**
需要长连接稳定 + SSH/RDP 不断流。香港优质中转 25-30ms 完全够用，比日本多 3-5ms 但通常更便宜。

**3. 华东流媒体/AI 重度用户**
日本机房带宽资源更充裕，大厂 CDN 覆盖更好，4K 拉流和模型下载体验优于香港。参见 [/scenario/](/scenario/)。

**4. 华南用户（广州/深圳/厦门）**
别绕了，直连香港。物理距离 130km，延迟地板 2ms，任何中转都是负优化。参见 [/tech/region/hongkong/](/tech/region/)。

**5. 西南/西北用户（成都/西安/兰州）**
本地出口质量是瓶颈。先看省内到成都/西安出口的延迟，再谈落地。西南可考虑新加坡（走昆明/南宁出海），西北建议优先解决本地 ISP 出口。

## 六、分客户端实操配置与深度避坑

### 6.1 桌面端（Clash Verge / Mihomo / sing-box）

- 开启 `Tun Mode` 时务必把 DNS 交给内核处理（`enhanced-mode: fake-ip`），否则系统 DNS 会泄漏，导致"延迟看起来很低但实际走直连"。
- 测速节点用 `url-test` 分组，间隔设 300s 而不是 60s，避免频繁探测本身污染延迟数据。
- 出口协议优先 `VLESS + Reality` 或 `Hysteria2`，避免老旧的 `SS + 简单加密` 在高丢包链路上雪崩。

### 6.2 移动端（Shadowrocket / Surge / Stash）

- iOS 上关闭"低数据模式"，否则系统会限制后台长连接。
- Android 的省电策略会杀掉 tun 进程，需要加入白名单。

### 6.3 路由/软路由

- OpenWrt 上跑 sing-box 时，务必关闭 `flow offload`，否则 TCP 窗口调整会失效。

**最常见的坑**：买了一堆"香港 GIA"节点，结果测速 200Mbps 但实际用起来卡——大概率是节点侧做了共享带宽池超售，或者你的客户端 TCP 栈没开 BBR。排查方法见下节。

## 七、抓包排障诊断手册：用命令说话

### 7.1 三把基础工具

```bash
# 1. 全链路丢包与延迟分布（Linux/macOS，需要 root）
mtr -rwzbc 100 1.1.1.1

# 2. 分段 TCP 握手耗时
curl -o /dev/null -s -w "DNS:%{time_namelookup} TCP:%{time_connect} TLS:%{time_appconnect} TTFB:%{time_starttransfer} TOTAL:%{time_total}\n" https://www.example.com

# 3. 端口级 RTT 与丢包（Windows / 跨平台）
tcping -n 50 -i 1 hk-node.example.com 443
```

### 7.2 判定表

| 现象 | 可能原因 | 处置 |
| --- | --- | --- |
| `mtr` 首跳丢包高 | 本地路由/光猫问题 | 更换 LAN 口或重启光猫 |
| 中间某跳丢包但后续正常 | 路由器 ICMP 限速，非真丢包 | 忽略，看末跳 |
| 末跳丢包 `> 2%` | 节点侧拥塞或超售 | 切换节点，反馈服务商 |
| `TCP` 握手耗时高但 TLS 正常 | 跨境骨干拥塞 | 换中转入口 |
| `TLS` 阶段耗时特别高 | 被 QoS 或 SNI 阻断 | 启用 Reality/换协议 |
| 延迟正常但吞吐低 | TCP 拥塞控制未优化 | 客户端���启 BBR |
| 晚高峰延迟翻倍 | 公网绕行 | 换 IEPL 专线节点 |

### 7.3 快速定位"伪低延迟"

有些客户端显示的延迟是"TCP 三次握手时间"，但实际业务走的是 UDP 或 QUIC，两者可能完全不同。用 `tcping` 得到的数值才是真实可用延迟。更多排障细节见 [/help/](/help/)。

## 八、行业避坑矩阵：识破六种典型话术

| 宣传话术 | 真实情况 | 验证方法 |
| --- | --- | --- |
| "香港 CN2 GIA ��连" | 很多只是普通 PCCW，甚至公网 | `mtr` 看是否出现 `59.43.*.*` |
| "延迟 5ms 到香港" | 大概率是测速节点在国内 | 用 `tcping` 打真实业务端口 |
| "不限流量不限速" | 共享池超售，晚高峰腰斩 | 连续测 3 天晚高峰 20:00-23:00 |
| "解锁 Netflix 全解锁" | 只解锁自制剧，非原生 IP | 查 `Netflix 原创 + 第三方` 双测试 |
| "IEPL 专线" | 实际是 IEPL 一段 + 公网一段 | 看全程 AS Path 是否单跳 |
| "IP 住宅纯净" | 出租机房的 IPv4，已被标记 | 查 IP 信誉库与 ASN 类型 |

**核心原则**：任何延迟承诺都必须在晚高峰实测。白天 30ms、晚上 150ms 的线路，在工程上等于不可用。

## 九、FAQ：七个真实痛点

**Q1：北京连香港多少毫秒才算正常？**
优质中转 28-42ms 属正常；公网直连 70ms 起步，晚高峰破百很常见。低于 25ms 的宣称基本不可信，那是物理地板之外的数字。

**Q2：上海连日本还是连香港？**
看用途。游戏/低延迟交互选香港（约 22-32ms vs 日本 25-38ms）；流媒体、AI 下载、大带宽场景选日本。

**Q3：跨省中转的"内网"到底损耗多少？**
从华北出口绕到华南出口，典型增加 8-20ms，晚高峰可放大到 30ms+。这不是内网慢，是骨干 QoS 在起作用。

**Q4：为什么我测速 500Mbps 但是看视频还是卡？**
测速走的是多线程并发短连接，视频走的是单条长连接。瓶颈在单线程 TCP 窗口与拥塞控制，检查客户端是否启用 BBR。

**Q5：香港节点 IP 被封了怎么办？**
优先换协议（Reality/Hysteria2）而不是换 IP。IP 封锁通常伴随 SNI 阻断，换 IP 不解决根本问题。

**Q6：手机流量和家宽测出来延迟差很多，正常吗？**
正常。移动 CMI 出口在某些省份优于电信，反之亦然。建议用同一节点在两种网络下分别 `tcping` 对比。

**Q7：西南用户是不是应该直接放弃香港？**
不必。成都/重庆走重庆出口到香港，优质线路可压到 40-55ms；但如果你的主用途是大带宽，新加坡的性价比更高。参见 [/tech/](/tech/)。
