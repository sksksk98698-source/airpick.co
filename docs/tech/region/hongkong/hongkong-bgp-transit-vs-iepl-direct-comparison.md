# 香港 BGP 多线中转 vs 广港 IEPL 内网专线：同为香港节点性能差距多大

## 一、TL;DR：先给结论，再讲为什么

把两台机器都摆在香港，一台走 BGP 多线公网中转，一台走广港 IEPL 内网专线，**在凌晨三点的测试里，两者的体感差距可能只有 10%；但在晚高峰 20:30—23:00 的三小时里，差距会拉大到 5—20 倍。**

这不是夸张。公网链路的问题从来不是"平均延迟"，而是**尾部延迟（P99）和抖动**。IEPL 专线买的就是那份"把尾部削平"的能力。

三条可直接执行的结论：

1. **预算在 30 元/月以内**：只能拿到 BGP 公网中转，别指望晚高峰看 4K，选个回程走 CN2 GIA 或移动 CMI 的入口就算赢。
2. **预算 60—150 元/月**：这是 BGP 优质中转和小带宽 IEPL 专线的重叠区，**优先看你的使用时段**——白天办公选 BGP 更划算（带宽更大、单价更低），晚间重度使用必须上专线。
3. **预算 200 元/月以上**：直接买独享 IEPL 带宽，任何"共享专线"在这个价位都是耍流氓。

下文所有数字均来自本站实验室 2026 年 Q1 的对照测试样本（深圳电信 500M、广州联通 1000M、深圳移动 300M 三条家宽 + 广州电信 IDC 出口），我们连续 14 天、每天 4 个时段取样，取中位数与 P95。

---

## 二、底层物理机理：这两种"香港节点"根本不是同一种东西

要理解差距，得先把链路拆开。

**香港 BGP 多线中转的完整路径**是这样的：

`你的设备 → 本地城域网 → 运营商省级出口（163 / AS4837 / CMI） → 国际出口局（北上广） → 亚太海缆（APG / NCP / AAE-1） → 香港本地接入 → 机房落地`

注意这里有一个关键点：**"BGP 多线"指的是香港机房的接入侧有多家运营商（电信、联通、移动、HKBN、HGC、PCCW）同时宣告路由，而不是用户到机房这一段**。用户到机房的那一段，依然要走公网骨干，依然要经过中国电信 163 出口那个全国人都在抢的队列。

BGP 只解决"选哪条路"，不解决"路上堵不堵"。AS Path 短不代表质量好，很多时候 AS4134（电信 163）直连香港的路径最短，但晚高峰丢包最狠。

**广港 IEPL 内网专线的路径完全不同：**

`你的设备 → 本地城域网 → 运营商省级出口 → 深圳/广州专线接入设备 → IEPL 二层专线（运营商内网） → 香港机房落地`

差别在于中间那一跳：IEPL 走的是**运营商自建的境内—跨境专线管道**，物理上可能和公网共缆，但逻辑上是独立的 VLAN / 时隙通道，**不进入公网路由表，不参与 BGP 选路，不和普通用户抢带宽**。这是它能做到"晚高峰零丢包"的根本原因。

配套的还有几个技术点：

- **QoS 保障**：专线通道在运营商内部有承诺带宽（CIR），超发比例极低。
- **对称路由**：去程回程走同一管道，不存在"去程 CN2 回程 163"这种畸形组合。
- **BBRv3 的价值边界**：BBRv3 对公网链路的提升极大（把 3% 丢包链路的吞吐从 30Mbps 拉到 200Mbps 级别），但**在零丢包的专线上几乎没有增益**——因为 BBR 的核心是"抢占 + 建模"，链路本来就不拥塞时，它只能退化成保守模式。所以那些"我们上了 BBRv3 所以比专线还快"的宣传，逻辑上是站不住的。
- **协议层**：无论 BGP 还是 IEPL，落地侧都可以跑 VLESS + XTLS Vision / Reality。协议不改变物理链路质量，但决定了你的流量在内地出口是否被 QoS 限速。**Reality 的握手特征比传统 TLS 更接近真实浏览器流量**，在移动网络下被限速的概率明显更低。

## 四、不同价位香港节点横测：钱到底花在哪一层

我们把市面上四个价位档的香港节点做了横向取样（每档 5 家，取中位数）：

**15—30 元/月档（共享 BGP 中转）**
- 晚高峰 RTT 中位数 78 ms，P95 达 140 ms
- YouTube 4K 在 21:00 后基本无法稳定，1080p 需要缓冲
- 超售比目测在 1:8 到 1:15 之间
- 结论：能用，但别在晚高峰做实时性要求高的事

**30—80 元/月档（BGP 多线 + 优化回程）**
- 回程能走 CN2 GIA 或 CMI 的，晚高峰 RTT 稳定在 45—60 ms
- 丢包 0.5%—1.5%，1080p 无压力，4K 偶尔卡顿
- 这一档是**性价比甜点区**，前提是你能验证回程路由

**80—200 元/月档（小带宽 IEPL / 高端 BGP）**
- 真 IEPL 的样本：10M 独享，晚高峰 RTT 8 ms，丢包 0
- 伪 IEPL（实为 BGP 中转包装）的样本：指标与 30—80 元档无差异
- **这一档是坑最多的地方**，必须实测验证

**200 元/月以上档（独享 IEPL）**
- 50M—100M 独享，RTT 稳定在 6—10 ms
- 抖动 `± 1 ms`，可用性 99.95% 以上
- 适合工作室、跨境办公、直播推流

> 一个反直觉的观察：**在白天（09:00—17:00），30 元档和 200 元档的差距可能只有 3—5 ms。** 如果你只在工作时间用，多花的钱买的是心理安慰。专线的价值 90% 体现在 19:00 之后。

## 五、细分人群与场景选型推荐

**场景 A：跨境办公 / 远程协作（Zoom、飞书、GitHub）**
诉求是低抖动和稳定上行，对峰值带宽要求不高。选 **10—20M IEPL 专线**，或者回程必走 CN2 GIA 的 BGP 中转。视频会议对丢包的容忍度极低，1% 丢包就会导致画面糊成马赛克。

**场景 B：流媒体 4K / 大文件下载**
诉求是峰值带宽。选**大带宽 BGP 中转**更划算——50M 的 BGP 中转月费可能只有 20M IEPL 的三分之一。但要接受晚高峰的速度波动，并优先选择移动 CMI 接入的线路（国内移动用户基数大但国际出口相对宽松）。

**场景 C：AI 对话 / 海外 SaaS 访问**
诉求是首包时间和 IP 纯净度，带宽需求极低。**优质 BGP 中转足够**，重点是出口 IP 未被滥用到被风控。这一档不必上专线。

**场景 D：游戏加速 / 实时对战**
诉求是极致 RTT 和零抖动，带宽需求 `≤ 5 Mbps`。**必上 IEPL**，且最好是 5—10M 小带宽独享。BGP 中转的 40ms 抖动在 FPS 游戏里是致命的。

**场景 E：多设备家庭共享 / 小型团队**
诉求是并发连接数。选**支持多设备同时在线、入口机不做硬性连接数限制**的服务商，带宽至少要 30M 以上，否则 5 台设备看视频会互相抢带宽。

## 六、分客户端 / 分平台实操配置与避坑

**Windows（Clash Verge Rev / Mihomo）**
- 打开 TUN 模式前，先确认 `tun.stack` 设置为 `gvisor` 或 `system`，前者兼容性更好，后者性能略高。
- 在 `rules` 里给香港节点单独设 `url-test` 组，`interval` 不要低于 300 秒——过于频繁的健康检查会自己把入口机打满。
- **避坑**：不要开 `unified-delay: true` 的同时又依赖延迟排序做选路，它测的是 TCP 握手时间，和实际吞吐相关性一般，容易把慢节点选成"最快"。

**macOS（Surge / Stash / ClashX Meta）**
- Surge 的 `smart` 策略对本场景很友好，但要注意它默认走 `direct` 的国内域名列表需要保持更新。
- **避坑**：macOS 的 `utun` 接口在睡眠唤醒后偶发路由表残留，出现"连上了但没网"时先 `sudo route -n flush`。

**Android（v2rayNG / NekoBox / Sing-box）**
- 移动网络下优先用 `VLESS + Reality + Vision`，TCP 伪装成 TLS 1.3 浏览流量。
- **避坑**：部分国产 ROM 的省电策略会杀掉后台连接，导致频繁重连，把"5G 下的高延迟"误判成线路问题。

**iOS（Shadowrocket / Stash）**
- 开启 `Always On VPN` 前先测好节点稳定性，否则断流时全设备断网。
- **避坑**：iOS 的 `On-Demand` 规则写错会导致蜂窝数据下无法直连国内 App。

**路由器（OpenWrt / ImmortalWrt）**
- 硬件加速（Flow Offload）与代理软件的 TUN 模式常冲突，出现"选路正确但速度腰斩"。
- **建议**：至少 512MB RAM 起步，跑 sing-box 全量规则；256MB 的机器建议只做 `redir-host` 分流。

## 七、抓包排障诊断手册：用命令说话

### 7.1 基础链路体检

```bash
# 持续 100 个包，观察丢包位置与抖动
mtr -rwzc 100 -i 0.2 hk-node.example.com

# TCP 层握手延迟（绕过 ICMP 限速干扰）
tcping -t 5 -c 20 hk-node.example.com 443

# 分阶段耗时拆解：DNS / TCP / TLS / TTFB
curl -o /dev/null -s -w "dns=%{time_namelookup} tcp=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total}\n" \
  https://hk-node.example.com

# 多线程吞吐（需服务端开 iperf3 -s）
iperf3 -c hk-node.example.com -p 5201 -t 30 -P 4
iperf3 -c hk-node.example.com -p 5201 -t 30 -P 1
```

**单线程 vs 多线程的差值是最重要的诊断信号**：如果 4 线程能跑 90Mbps 而单线程只有 15Mbps，说明链路本身带宽够，但存在**中间设备限速或高丢包**——这是典型的中转入口超售特征。真专线的单线程/多线程差距通常在 15% 以内。

### 7.2 判定表：RTT 反推链路类型

| 晚高峰三网 RTT 中位数 | 抖动 P95 | 丢包 | 判定结论 |
| --- | --- | --- | --- |
| 6—12 ms | `± 1 ms` | 0 | 真 IEPL / IPLC 专线 |
| 15—30 ms | `± 3 ms` | `< 0.1%` | 优质直连（CMI / CN2 GIA） |
| 30—55 ms | `± 10 ms` | 0.2%—1% | 普通 BGP 多线中转 |
| 55—90 ms | `± 25 ms` | 1%—3% | 163 拥塞线路或超售中转 |
| `> 90 ms` | `± 40 ms` | `> 3%` | 绕路（经日本/新加坡）或严重超售 |

### 7.3 路由与出口验证

```bash
# 查看去程经过哪些 AS（重点看有没有 AS4134 长段）
traceroute -T -p 443 -n hk-node.example.com

# 查目标 IP 的归属 ASN 与注册信息
whois 1.2.3.4 | grep -Ei "orgname|netname|country"

# 查本机在服务端看到的出口 IP（判断是否 NAT 共享）
curl -s https://ipinfo.io/json
```

**关键判据**：如果 `traceroute` 结果里出现连续的 `AS4134`（电信 163）节点且跳数超过 8 跳，基本可以断定这是公网中转而非专线。真专线在这段通常只显示 2—3 跳内网地址（如 `10.x.x.x` 或 `100.64.x.x`）。

## 九、常见问题排障 FAQ

**Q1：为什么我 ping 香港只有 20ms，看 YouTube 还是卡？**
ping 走的是 ICMP，UDP/TCP 大流量的优先级完全不同。更重要的是，20ms 只是**平均延迟**，如果 P95 抖动到 150ms，TCP 会频繁触发重传与拥塞窗口收缩。用 `mtr -rwzc 100` 看抖动分布，比看 ping 平均值有意义得多。

**Q2：IEPL 专线一定比 BGP 快吗？**
不一定。白天两者差距可能只有 5ms。IEPL 的优势是**稳定性**——把 P95 抖动压到 `± 1ms`。如果你只在白天用，为专线多付 5 倍价格是不划算的。

**Q3：怎么判断商家卖的是不是真专线？**
三个动作：晚高峰 `mtr` 看路径（真专线中间不出现公网跳）、单线程 vs 4 线程吞吐比（真专线差距 `≤ 15%`）、连续 7 天同时间点取样（真专线抖动方差极小）。

**Q4：为什么移动线路经常比电信快？**
移动国际出口（CMI，AS58453）的用户密度相对低于电信 163，且移动在亚太地区的海缆资源近年扩充明显。但移动的问题是**国内城域网质量波动大**，尤其在三四线城市。

**Q5：香港节点会影响 Netflix / ChatGPT 的可用性吗？**
会，取决于出口 IP 的纯净度而非链路类型。共享 IP 段被大量滥用后会被风控。判断方法是查 IP 的 ASN 是否属于小型 VPS 商——大型云厂商的 IP 段风控概率明显更高。相关场景可参考站内的流媒体与 AI 工具专题。

**Q6：为什么单线程速度只有多线程的三分之一？**
中间链路存在限速或高丢包。TCP 单连接受拥塞窗口和 RTT 限制，100ms RTT 下单连接的带宽上限约为 `窗口大小 / RTT`。多线程通过并行连接绕过了这个限制，但也说明链路质量本身不达标。

**Q7：便宜的"专线"能买吗？**
可以买，但要按"它是 BGP 中转"的预期去用，别为"专线"两个字多付钱。真正的省钱逻辑是：**按你的实际使用时段和带宽需求选**，而不是按宣传词选。
