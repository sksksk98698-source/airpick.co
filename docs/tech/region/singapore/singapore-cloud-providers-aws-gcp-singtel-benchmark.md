# 新加坡主流机房与云厂商全景：AWS、GCP、Singtel 与 OVH 新加坡实测

> 本文是「AirPick · 机场推荐」机房与云厂商系列的第 7 篇。数据采集窗口为 2026 年 1 月 ~ 2 月，测试点覆盖中国大陆三大运营商（电信 / 联通 / 移动）18 个省级出口。

## 一、TL;DR：先把结论摆上桌

如果你只有 30 秒，记住这三条就够：

1. **做合规出海业务落地（电商、SaaS、支付回调、App 后端）** → AWS ap-southeast-1 或 GCP asia-southeast1，选谁看你的技术栈和预算，跟"翻墙体验"无关。
2. **需要极干净的东南亚原生 IP（风控白名单、流媒体、银行、多账号矩阵）** → Singtel / StarHub 自有机房托管，AS3758 段前缀，价格最高但 IP 身份最硬。
3. **要"性价比 + 亚太多地区智能跳板 + 中国方向回程优化"** → OVH 新加坡不适合做中国出口（回程绕路严重），这类需求更合理的解法是选择带三网动态负载均衡的商业中转服务，而不是自己拿云主机硬扛。

我做跨境链路这十年，见过最多的认知错位就是：**把「云厂商机房」和「翻墙节点」当成同一个东西去比**。它们服务的目标函数根本不同——前者优化的是全球内网东西向流量和 SLA，后者优化的是你到墙外的那一条单向路径。搞清楚这一点，后面所有参数才有意义。

## 二、物理底层：新加坡凭什么一年躺赚 200 亿美金带宽费

新加坡不是"因为发达所以网络好"，而是**地理位置被海缆强迫选中**。

**海缆拓扑**是第一层决定因素。截止 2026 年落地或在建的骨干包括 SEA-ME-WE 3/5、APG（亚太直达）、AAG、SJC2、INDIGO-West、Bifrost、Apricot，以及刚完成扩容的 ASC。这些海缆的登陆站主要落在 Tuas 和 Changi 两个方向，再通过陆上光纤环进入数据中心集群。**这意味着：你的数据包到新加坡的物理路径，实际上由"你所在城市 → 最近登陆站 → 海缆 → 新加坡登陆站"这四段决定**，跟机房本身关系不大。

**IXP 层**更关键。SGIX（Singapore Internet Exchange）与 SOX 承载了大量对等互联，AWS、Google、Cloudflare、Akamai、以及三大中国运营商的国际公司都在这里有端口。一个机房是否"网络好"，本质上看它**在 SGIX 的端口容量 + 有多少 Tier-1 直接对等**，而不是看它打广告说"CN2 直连"。

**机房集群分布**（按网络品质排序）：

| 区域 | 代表机房 | 特点 |
| --- | --- | --- |
| Jurong / International Business Park | Equinix SG3、Digital Realty SIN11、GCP | 靠近西侧海缆登陆站，国际出口延迟最低 |
| Tai Seng / Ayer Rajah | Equinix SG1/SG2、STT Tai Seng、AWS | 老牌核心区，对等丰富 |
| Serangoon / Loyang | Global Switch、Keppel DC | 部分金融与政企客户 |
| 东部 Changi | Singtel DC、OVH | 靠近东侧海缆与机场方向 |

**BGP 选路**是第二层。同一个机房里的两个 IP 段，回中国的路径可能完全不同：一个走 Tier-1（NTT / Telia / Tata）经香港回，一个走 Singtel 自有骨干直连广州。判断方法是看 AS Path，而不是看机房宣传页。

**QoS 与拥塞控制**是第三层。2026 年主流已经转向 BBRv3，AWS 自家用的是自研的 `TCP CUBIC 变种 + ECN`，GCP 在 QUIC 上走得最激进。如果你在境外主机上跑代理，**换内核启用 BBRv3 对新加坡 → 大陆的回程吞吐提升通常在 15%~40%**，这是最便宜的一次优化。

## 三、四大玩家网络解剖：AWS / GCP / Singtel / OVH

### AWS ap-southeast-1（AS16509）

EC2 默认网络带宽与实例规格绑定，c7i 以上可跑满 12.5Gbps，跨 AZ 延迟稳定在 `~1.2–1.8ms`。真正的卖点是 Direct Connect 和 Global Accelerator——**如果你的用户在全球，GA 能把入口收敛到最近的边缘节点**。

但对中国大陆方向，AWS 新加坡的表现很尴尬：回程大量走 NTT 和 Telia，晚高峰电信方向容易掉到 150ms 以上并伴随明显抖动。**AWS 新加坡不是"优化中国"的机房，是"优化东南亚 + 全球"的机房**。想用它做中国出口，必须自建香港/东京中转。

### GCP asia-southeast1（AS396982 / AS15169）

GCP 的杀手锏是 **Premium Tier 骨干网**——流量从新加坡上谷歌自有骨干，一直到离用户最近的边缘 PoP 才落地。实测大陆联通与移动方向，GCP 新加坡的抖动比 AWS 小 `约 30%`，平均延迟低 10–25ms，原因是谷歌在亚太的骨干冗余度更高。

注意 Standard Tier 和 Premium Tier 是两个世界。**Standard Tier 走公网，体验断崖式下跌**，务必在 Cloud Interconnect 或外网 IP 层级确认。

### Singtel 自有机房（AS3758）

这是全场唯一的"电信级"玩家。Singtel 是新加坡 incumbent carrier，同时持有 SingNet 家宽 AS9506 与移动网络。**从 Singtel 机房出来的 IP，地理定位、rDNS、WHOIS 全链路一致，风控系统几乎不会质疑**——这对跨境电商、流媒体、支付类业务是刚需。

代价是价格：带宽按 Mbps 计费，1Gbps 端口的月成本常年是 AWS 同规格的 2~3 倍，且不包 DDoS 清洗。**普通人没必要碰，业务方绕不开**。

### OVH 新加坡（AS16276）

2021 年落地，主打 Anti-DDoS 与不限流量。硬件性价比极高，但**国际出口质量是短板**：回中国大陆普遍走 Tata / NTT 绕日本或香港，晚高峰延迟可以冲到 250ms 以上，丢包 `> 3%` 是常态。它的正确用法是做欧洲方向的中转枢纽或抗 D 前端，而不是中国出口。

### 商业中转服务（如唯兔云类）

这里必须说清楚一个行业事实：**个人用户自己买云主机搭节点，是成本结构最差的一种做法**。云厂商的计费模型是为企业设计的，�� IP 单端口的价格里含了大量你用不上的东西（SLA、合规、Support）。

带**三网动态智能负载均衡**的商业中转服务，本质是把上百条线路的带宽池化后按需调度——电信用户走电信优化路径，移动用户走移动优化路径，节点故障自动切换。对 60+ 全球节点的运营方来说，单位成本被摊薄到个人用户能接受的水平。这是**架构层面的效率差异，不是"便宜没好货"**。

## 五、细分人群选型推荐

- **跨境电商独立站 / 支付回调**：Singtel 或 GCP 新加坡，IP 纯净度优先于延迟。别用廉价云段 IP，风控秒封。
- **AI 训练 / 大模型拉权重**：GCP 新加坡，Premium Tier 到 HuggingFace、S3、Azure 的带宽利用率最高。
- **海外社交矩阵 / 多账号运营**：需要"一节点一 IP 一指纹"，商业中转服务里支持指定地区出口的方案更省事。
- **游戏加速 / 低延迟交互**：看抖动不看均值，GCP 优于 AWS，商业中转服务通常有专门的低抖线路。
- **个人开发者 / 中小企业**：AWS Lightsail 新加坡做测试环境够用，但**别拿它当生产级中国出口**。
- **纯个人翻墙需求**：自建云主机的 TCO（主机 + 域名 + 时间成本 + 被封重搭）通常高于商业中转服务，除非你有强烈的自控需求。

## 六、分平台实操配置与避坑

**Windows**：Clash Verge Rev 或 sing-box GUI。常见坑是 DNS 走系统解析导致泄漏，务必在配置里显式指定 `nameserver` 与 `fallback`，并打开 `tun` 模式接管全局流量。

**macOS**：Surge / Stash / sing-box 均可。注意 macOS 的 `pf` 防火墙与 TUN 会冲突，需要正确授权。推荐参考 [客户端配置教程](/tutorial/)。

**iOS**：Shadowrocket / Stash / sing-box。低价区的 App Store 账号是刚需，建议自建家庭共享而非购买第三方账号。

**Android**：v2rayNG / NekoBox / sing-box。国产 ROM 会杀后台，需把客户端加入电池白名单，否则 TUN 会随机断开。

**路由器（OpenWrt）**：mihomo / PassWall。关键在于 **MTU 与 MSS 钳制**——境外线路 MTU 常见 1400 或 1380，不设钳制会导致大包丢、网页打到一半卡死，表现出来像"节点很慢"，其实是 TCP 分片问题。

**通用避坑**：

- 不要迷信"CN2 GIA"字样，2026 年市面上大量 IPS 转售线路冒充 GIA，看 AS Path 才有真相。
- UDP 转发必须开，否则语音、游戏、QUIC 站全部降级。
- 别把 Mux 开太大，多路复用在高丢包线路上会放大 RTT。
- TLS Reality 已成为主流抗探测方案，老式 VMess 明文握手在 2026 年被识别率显著���升。

## 七、抓包排障诊断手册

遇到"慢"，第一步永远是**分段定位**，而不是换节点。

```bash
# 1. 看逐跳路径与丢包分布
mtr -rwzc 100 -P 443 目标IP
```

判读要点：**中间跳丢包但最后一跳正常 = 无害**（路由器 CPU 限速响应 ICMP）；**从某一跳开始持续丢包且延续到终点 = 真实劣化**。

```bash
# 2. 拆解握手耗时
curl -o /dev/null -s -w "DNS: %{time_namelookup}  TCP: %{time_connect}  TLS: %{time_appconnect}  TTFB: %{time_starttransfer}  Total: %{time_total}\n" https://example.com
```

判定逻辑：`DNS` 高 → 解析被污染或用了脏递归；`TCP` 高 → 链路 RTT 或丢包问题；`TLS` 高 → 跨国握手往返次数过多；`TTFB` 高但前段正常 → 服务端处理慢，跟网络无关。

```bash
# 3. 端口级连通性（比 ping 更贴近真实）
tcping -t 5 -p 443 1.1.1.1

# 4. 吞吐与重传观察
iperf3 -c 目标IP -P 8 -t 30
ss -s   # 看 retrans 数量
ss -ti  # 单连接级别的 cwnd / rtt / retrans
```

| 现象 | 高概率原因 | 验证方法 |
| --- | --- | --- |
| ping 正常但打不开网页 | MTU 分片 / TCP MSS 未钳制 | 改 MTU 到 1380 复测 |
| 白天正常，晚 8-11 点崩 | 国际出口拥塞，非 CN2 线路 | 分时段 mtr 对比 |
| 只有视频卡，网页还行 | UDP 被丢 / QUIC 降级 | 强制 TCP 模式对比 |
| 握手成功但速度 100KB/s | 超售严重或 QoS 限速 | iperf3 单线程对比多线程 |
| 时快时慢无规律 | 路由抖动，BGP 频繁切换 | 连续 traceroute 记录 AS Path |

完整的排障流程可以对照 [帮助中心的故障诊断手册](/help/)。

## 九、常见问题 FAQ

**Q1：AWS 新加坡和 GCP 新加坡，同价格下选哪个做后端？**
看你的技术栈耦合度。已经在用 GCP 的 BigQuery / Vertex，选 GCP；依赖 AWS 生态（S3、SQS、Lambda）就选 AWS。纯网络性能层面 GCP 略优，但差距不构成决策依据。

**Q2：Singtel 原生 IP 真的能过所有风控吗？**
不是"所有"，是"显著更少触发"。风控是多因子模型（IP + 指纹 + 行为 + 支付），IP 只是其中一项。原生 IP 能帮你跨过 IP 信誉这一关，但指纹污染照样会被判。

**Q3：为什么我买的"新加坡节点"实测延迟 200ms+？**
大概率出口 IP 在 OVH 或者某些廉价云段，回程绕了日本/美国。用 `mtr` 看第 5-8 跳的 AS Path 就能确认。

**Q4：自建云主机被墙了怎么办？**
换 IP 是最直接的方案，但成本会累积。长期看，选择带**智能负载均衡与故障自动切换**的服务，比单 IP 自建抗风险能力强得多。

**Q5：晚高峰掉速是节点问题还是宽带问题？**
先在同一时刻用国内目标做测速（如测国内 CDN）。如果国内目标也掉，是你本地宽带出口问题；如果只有境外掉，才是线路问题。

**Q6：BBR 到底有没有用？**
有用，尤其在高丢包长肥管道上。但 BBRv3 提升的是吞吐与抗丢包，**不改善物理 RTT**。别指望它把 200ms 变成 60ms。

**Q7：商业中转服务会不会偷数据？**
技术上，任何中间层都具备可见性。选择支持 **VLESS + TLS Reality / XTLS** 等端到端加密方案的服务，能让中间层只看到密文��这也是我们一贯推荐 VLESS 协议的原因。
