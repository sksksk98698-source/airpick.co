# 外服电竞低延迟选线心法：不同游戏服务器与节点地区的最佳配对表

## 一、TL;DR：先给结论，再讲道理

外服游戏的延迟，**80% 由"你的出口节点地理位置"决定，15% 由"链路类型（公网中转/专线）"决定，5% 才轮到协议与客户端优化**。绝大多数人把顺序搞反了——疯狂折腾客户端参数，却不舍得把节点从洛杉矶换成首尔。

三条硬结论：

1. **就近出口原则**：节点落地城市与游戏服务器物理距离越近越好，绕路的中转比直连的专线更快。打韩服挂美西节点，神仙难救。
2. **专线优先级高于一切协议优化**：IEPL/IPLC 专线的抖动通常能压在 `±3ms` 以内，公网优化线路在晚高峰能飙到 `±40ms`。MOBA/FPS 类游戏对抖动的敏感度高于对绝对延迟的敏感度。
3. **UDP 转发能力是隐形门槛**：大量机场只优化 TCP，游戏走的却是 UDP 443/3074/27015 等端口，结果就是网页秒开、游戏狂丢包。

## 二、底层机理：为什么你的延迟"打不下来"

### 2.1 光速是天花板，绕路是地板

光纤中信号传播速度约为 `200,000 km/s`，往返延迟（RTT）的理论下限：

| 目的地 | 单程距离 | 理论 RTT | 公网实测 RTT | 优质专线 RTT |
| --- | --- | --- | --- | --- |
| 首尔 | 约 900 km | 约 9 ms | 35–60 ms | 28–38 ms |
| 东京 | 约 1,900 km | 约 19 ms | 45–75 ms | 32–45 ms |
| 新加坡 | 约 4,000 km | 约 40 ms | 70–110 ms | 48–62 ms |
| 洛杉矶 | 约 11,000 km | 约 110 ms | 150–220 ms | 125–145 ms |
| 法兰克福 | 约 16,000 km | 约 160 ms | 220–320 ms | 175–205 ms |

注意洛杉矶一行：**理论 110ms，专线 125–145ms，公网能跑到 220ms**。那多出来的 80ms 就是绕路——数据包先飞香港、再飞日本、再折返美国，或者被塞进拥塞的跨太平洋海缆。

### 2.2 BGP 选路：最便宜的路 ≠ 最快的路

公网出口走的是 BGP 最优路径，而 BGP 的"最优"是**商业最优（AS 跳数与对等成本）**，不是��迟最优。典型症状：

- 去程走 Telia 干净，回程走 Cogent 绕欧洲；
- 白天 60ms，晚高峰 180ms——因为跨洋链路被打满，QoS 队列把游戏包排在最后。

**专线（IPLC/IEPL）的本质是"买断一条私有电路"**，不经过公共互联网的 BGP 选路，也不受公网拥塞影响。IPLC 是物理专线，IEPL 是以太网接口的逻辑专线，后者带宽弹性更好、单位成本更低，是目前高端机场的主流选择。

### 2.3 QoS、BBRv3 与"延迟尖刺"

延迟尖刺（jitter spike）有两个来源：

- **缓冲膨胀（Bufferbloat）**：机场中转节点出口带宽被打满，路由器队列积压，你的小包排在几 MB 的下载包后面。表现为"平时 50ms，一进团战 400ms"。
- **拥塞控制**：BBRv3 相比 BBRv2 调整了丢包判定与 ProbeRTT 逻辑，在高丢包链路上带宽利用率更低但更稳定；老旧的 CUBIC 在跨洋链路上容易反复收缩窗口。

**游戏 UDP 不参与拥塞控制**，所以你感受到的丢包不是自己的锅，是中转节点的队列管理和出口 QoS 策略问题。

### 2.4 TLS Reality 与游戏流量

TLS Reality 属于 TCP 层的伪装技术，解决的是"被识别被封锁"的问题。但多数射击游戏走 UDP，**Reality 对游戏本身没有加速作用**，它的价值在于让你的节点长期存活。别被"Reality 加持游戏加速"的话术忽悠——游戏延迟只跟路径和转发质量有关。

### 2.5 双 ISP / 多线接入的意义

单 ISP 节点一旦遇上游维护或海缆故障，直接失联。双 ISP 节点会在入口同时接入电信/联通（或 CN2 + 移动 CMI），按客户端来源自动选入口。**对游戏党，双 ISP 的最大价值是降低"单一入口晚高峰拥塞"概率**。

## 三、核心参数对照矩阵（9 项指标）

选购或评测游戏节点时，只看"延迟"是外行。下面这张表是 AirPick 实验室用于分级的标准：

| # | 指标 | 及格线 | 优秀标准 | 测量方法 |
| --- | --- | --- | --- | --- |
| 1 | RTT 中位数 | 低于 120 ms | 低于 60 ms | `tcping -n 100` |
| 2 | 抖动 Jitter | 低于 15 ms | 低于 5 ms | mtr 1000 包标准差 |
| 3 | 丢包率 | 低于 1% | 0% | mtr / ping 长测 |
| 4 | 晚高峰衰减 | 小于 30% | 小于 10% | 20:30–22:30 复测 |
| 5 | UDP 转发支持 | 全端口 | 全端口 + 保序 | 游戏实测 / UDP 探测 |
| 6 | 路由类型 | 公网优化 | IEPL / IPLC 专线 | `mtr` 看 AS 路径 |
| 7 | 落地城市匹配度 | 同区域 | 与服务器同城 | 服务端 IP 归属查询 |
| 8 | 带宽上限 | 100Mbps | 500Mbps+ 不共享 | 晚高峰 iperf3 |
| 9 | 价格/100G | 低于 10 元 | 15–25 元（专线） | 套餐折算 |

**关键判据**：第 1、2、3 项要**同时**满足。一个 45ms 抖动却 `±60ms` 的节点，打起来比稳定 80ms 的还难受。

## 四、游戏服务器 ↔ 节点地区最佳配对表

这是本文的核心。核心逻辑：**节点落地城市应当与游戏服务器所在运维区域同城或同区域**。

| 游戏服务器区域 | 典型热门游戏 | 推荐节点落地 | 备选节点 | 目标 RTT | 关键提示 |
| --- | --- | --- | --- | --- | --- |
| 韩服 | 英雄联盟 KR、PUBG、失落的方舟 | 首尔 | 釜山 | 28–45 ms | 避免绕东京回程 |
| 日服 | 原神、FF14、Apex JP、瓦罗兰特 JP | 东京 | 大阪 | 32–50 ms | 关西线路常被忽视但更空 |
| 港台服 | 传说对决、原神亚服、CS2 亚洲 | 香港 | 台北 | 15–35 ms | 港服优先选香港 HKIX 直连 |
| 东南亚服 | MLBB、无畏契约 SG、Free Fire | 新加坡 | 吉隆坡、曼谷 | 48–70 ms | 避开绕香港的新加坡线路 |
| 美服西区 | 瓦罗兰特 NA、CS2 NA、堡垒之夜 | 洛杉矶 | 圣何塞、西雅图 | 125–150 ms | 圣何塞对北方用户更优 |
| 美服东区 | LoL NA、魔兽世界 NA、CoD | 纽约/阿什本 | 达拉斯 | 170–200 ms | 无专线时建议改选西区 |
| 欧服 | CS2 EU、LoL EUW、EVE | 法兰克福 | 阿姆斯特丹、伦敦 | 175–210 ms | 必须走专线，公网无解 |
| 中东服 | 部分手游中东区 | 迪拜 | 巴林 | 200–240 ms | 冷门，需确认机场有落地 |
| 澳服 | 部分 FPS/MMO | 悉尼 | 墨尔本 | 160–190 ms | 常经新加坡中转 |

**三条配对铁律**：

1. **同区域优先，别跨洋取巧**。国服玩家打东南亚服，香港节点看似近，实则绕行；新加坡本地出口才是最优解。
2. **美国东西部差异巨大**。同样"美服"，东区比西区多出 40–60ms，对枪战类游戏是生死线。
3. **欧服只认专线**。公网跨欧亚的路径极不稳定，晚高峰绕行俄罗斯或中东的情况屡见不鲜。

想进一步了解不同线路类型的实测差异，可参考 [/tech/](/tech/) 下的链路机制专题。

## 五、细分人群与场景选型

| 人群 | 核心诉求 | 推荐策略 | 预算区间 |
| --- | --- | --- | --- |
| 竞技 FPS 玩家 | 低抖动、零丢包 | 单点 IEPL 专线 + 固定落地 | 20–40 元/月 |
| MOBA / 手游玩家 | 稳定、便宜 | 区域专线轻量套餐 | 10–25 元/月 |
| MMO 副本党 | 长时间稳定在线 | 大流量中转 + 双 ISP | 15–30 元/月 |
| 多区服切换玩家 | 多地区节点 | 多区域套餐（日韩港新美） | 30–60 元/月 |
| 主播 / 陪玩 | 上行稳定 + 低延迟 | 专线 + 独享带宽 | 50 元/月起 |

**手游玩家特别注意**：手游走 UDP + 短连接重连，对丢包极度敏感。地铁/4G 场景下，建议选择支持 UDP over TCP 或 UDP 转发的节点，能显著降低移动网络下的握手失败率。

## 六、客户端实操配置与深度避坑

### 6.1 Windows（Clash Verge Rev / v2rayN）

- 开启 **TUN 模式**，而非系统代理。系统代理只劫持 HTTP/SOCKS 感知的流量，很多游戏客户端的 UDP 会直接绕过代理。
- 在分流规则里显式加入游戏进程：`PROCESS-NAME,VALORANT-Win64-Shipping.exe,GAME`。
- 关闭 **DNS 劫持到 FakeIP** 用于游戏进程，否则首包解析可能产生 1–2 秒卡顿。

### 6.2 路由器（OpenWrt / iStoreOS）

- 使用 **mihomo（Clash.Meta）内核**，原生支持 UDP 与 fake-ip-filter。
- 主机/游戏机的 UDP 必须走 **redirect 而非 tproxy** 时，注意内核版本，部分老固件 tproxy 对 UDP 支持有缺陷。
- 建议给游戏主机做静态 IP + 规则分流，避免全家设备抢带宽。

### 6.3 手机（Android / iOS）

- Android 用 **Clash Meta for Android**，开启"允许 UDP"。
- iOS 用 **Shadowrocket / Stash**，注意"全局路由"与"按规则"的差异，游戏建议全局或按需规则。
- 务必关闭 **iCloud 私有中继**，它会与代理产生路由冲突。

### 6.4 常见配置坑

- **MTU 不匹配**：专线常见 MTU 1400–1480，设 1500 会导致大包分片、丢包率上升。可在客户端设 `tun-mtu: 1400` 试探。
- **多节点负载均衡**：绝对不要给游戏开负载均衡/自动选择。IP 频繁切换会导致游戏会话被踢或触发风控。
- **开启 IPv6**：部分节点 IPv6 回程绕路，反而更慢。游戏场景建议关闭 IPv6 或强制 IPv4。

## 七、抓包排障诊断手册

遇到"节点明明很快，游戏就是卡"的情况，按下面顺序排查。

### 7.1 三步定位法

```bash
# 1. 看路径：哪一跳开始变慢/丢包
mtr -rwzc 500 <游戏服务器IP或节点入口IP>

# 2. 看端口：TCP 层是否通畅（UDP 用 tcping 替代方案）
tcping -n 100 <节点IP> 443
tcping -n 100 <节点IP> 12345

# 3. 看真实体验：手动测 HTTP 首包与总耗时
curl -o /dev/null -s -w "dns:%{time_namelookup} conn:%{time_connect} tls:%{time_appconnect} total:%{time_total}\n" https://<目标站点>
```

Windows 用户可用 `mtr` 的 Windows 移植版或 `pathping -n`；macOS 用 `brew install mtr` 后需 `sudo mtr`。

### 7.2 判定表

| 现象 | 可能原因 | 处置 |
| --- | --- | --- |
| 第 1 跳就丢包 | 本地网络/路由器问题 | 换网线、重启光猫、检查 WiFi 干扰 |
| 出口后第 2–3 跳起高延迟 | 入口 ISP 拥塞 | 切换双 ISP 的另一入口 |
| 中间某跳延迟高但不丢包 | ICMP 限速，属正常 | 忽略，看终点数据 |
| 终点持续 3% 丢包 | 中转过载或专线故障 | 换节点，提单反馈 |
| TCP 正常但游戏丢包 | UDP 未转发/被限速 | 换支持 UDP 的节点 |
| 白天正常晚高峰炸 | 共享带宽超售 | 换独享或专线套餐 |
| 连接成功但频繁掉线 | 会话被风控/MTU 问题 | 关负载均衡、调 MTU |

### 7.3 长期监控建议

用 `smokeping` 或简单的 `ping -i 60` 落盘脚本，连续跑 24 小时记录 RTT 与丢包，才能真正看清一个节点是否"稳"。单次测速 40ms 和长期中位数 40ms 完全是两件事。

## 八、行业避坑矩阵

| 宣传话术 | 真实情况 | 识别方法 |
| --- | --- | --- |
| "永不掉线 / 零延迟" | 物理不可能 | 任何声称低于理论 RTT 的，直接拉黑 |
| "专线"但价格 3 元/100G | 实为公网中转 | `mtr` 看 AS 路径是否穿越多个公网 AS |
| "覆盖 60 国节点" | 多为虚拟落地/转售 | 抽查落地 IP 的 ASN 与机房 |
| "解锁 Netflix/游戏" | 仅 DNS 解锁，非原生 IP | 用流媒体检测脚本验证，游戏区服需实测 |
| "不限速不限量" | 隐性 QoS 限速 | 晚高峰 iperf3 长测对比 |
| "一键加速全平台" | 客户端功能有限 | 看是否支持 UDP、TUN、规则分流 |
| "月付 5 元打美服" | 大概率超售 | 观察晚高峰丢包与抖动 |

**超售识别三招**：① 晚高峰（20:30–23:00）跑三次测速，波动超 40% 即超售；② 看节点在线人数与出口带宽比；③ 检查是否提供带宽独享选项。

## 九、FAQ：真实痛点解答

**Q1：玩韩服选什么节点？香港不是更近吗？**
香港到首尔的物理距离与上海到首尔相近，但**公网路径常绕日本**，实际 RTT 反而更高。除非机场有香港→首尔的专线直连，否则优先选首尔落地节点。

**Q2：美服欧服低延迟路线的天花板在哪？**
美西约 125–145ms，欧服约 175–210ms。低于这个值基本都是测速软件的假象（比如测的是本地 CDN 而非游戏服务器）。**别追求数字，追求稳定性**。

**Q3：为什么我网页打开飞快，游戏却狂卡？**
典型的 UDP 未被转发。检查客户端是否开启 UDP 支持，节点是否明确标注"UDP 转发"。这是最容易被忽略的一环。

**Q4：东南亚服直连技巧有哪些？**
优先选新加坡本地出口，避免经香港绕行；手游玩家启用 UDP 保序；吉隆坡/曼谷节点对马来西亚、泰国区服更优。实测中，新加坡专线比公网能省 20–30ms。

**Q5：一个节点能不能兼顾日韩美三区？**
能，但通常不是最优。多区域套餐的价值就在于"每个区都有对应的同城落地"。单节点全球通吃的代价是永远不在最佳位置。

**Q6：开了加速器还要用机场节点吗？**
游戏加速器与机场节点是两类方案。加速器针对特定游戏优化了 UDP 隧道，但覆盖游戏有限、价格更高；机场节点通用性更强。两者可以并存，但**不要同时开启**，会产生路由冲突。

**Q7：延迟 60ms 和 80ms 真的能感觉到吗？**
在 FPS 的 peek 对枪场景，20ms 足以决定生死。但在 MMO、卡牌、策略类游戏中，基本无感。**按游戏类型定标准，别被焦虑营销带节奏**。
