# Netflix 同户家庭（Household）限制与密码共享破解全实操

## 一、TL;DR：先给结论，再讲原理

如果你只想知道"到底怎么让异地家人继续看奈飞"，答案按成本从低到高排序是这样的：

1. **官方临时访问代码（Temporary Access Code）**：电视端触发同户拦截时，用主账号手机号/邮箱接收 4 位码，一次验证可维持约 14 天的正常播放。这是唯一 100% 合规、零风控、零成本的办法，但需要每两周手动续一次，且只对"家庭成员"逻辑成立。
2. **额外成员席位（Extra Member）**：运营商侧直接加钱开子账号，子账号拥有独立密码与独立推荐流，物理上不受同户判定约束。缺点是部分地区未开放，且月费已接近半价标准套餐。
3. **网络层"同出口"方案**：让异地设备在 Netflix 服务端看来与主设备处于同一个公网出口 IP（即同一"家庭网络"）。这是技术上最彻底的解法，也是本文的技术重点。核心不是"解锁"，而是**出口 IP 一致性与 ASN 可信度**两个变量。
4. **迁移家庭位置（Update Household）**：官方允许更换，但频率受限（通常 12 个月一次），且换完之后原来那批人全部失效——这是最容易"搬起石头砸自己脚"的操作。

一句话总结：**移动端宽容、TV 端严苛、同户判定的锚点是"主设备最后一次播放时的公网 IP + 设备指纹图"**。理解了这句话，后面所有操作都是推导。

## 二、底层机理：Netflix 到底怎么判断"你是不是同一户"

要把这件事做干净，必须先搞清楚 Netflix 的同户判定不是单一信号，而是**多信号加权**。

**信号 1：账号级"家庭锚点 IP"**
主账号在电视端首次播放时，Netflix 会把该会话的公网 IP 与地理位置（ASN、城市级 GeoIP）记为"Household Anchor"。这个锚点不是永久锁死的，它会随着主设备长期、稳定地使用而缓慢漂移（类似指数移动平均）。

**信号 2：设备指纹图（Device Graph）**
每台设备有独立的 ESN（设备序列号），TV 端还带 DRM 等级、设备型号、固件版本、语言与分辨率协商能力。Netflix 记录的是"哪些 ESN 曾与锚点 IP 同现"，这就是所谓的可信设备集。

**信号 3：局域网探测（SSID / BSSID）**
这是很多人忽略的一环。Android TV 与部分移动端在验证流程中会读取当前 Wi-Fi 的 SSID/BSSID，用于确认"设备确实连在家庭局域网上"。TV 端提示"你的设备似乎不在 Netflix 家庭中"，很大概率就是因为这一步的局域网指纹与锚点不符。

**信号 4：验证周期与漫游容忍**
移动端（手机/平板）被定义为"可漫游设备"，只要每 31 天回一次家庭网络播放一次内容，就不会被踢。TV 端（尤其是智能电视、Apple TV、Fire TV）则被视为"固定设备"，没有漫游豁免，必须走临时验证码或同户网络。

**信号 5：网络可信度评分**
出口 IP 的 ASN 类型直接影响判定。数据中心 ASN（如各类云厂商）与住宅 ISP ASN 在风控模型里的权重完全不同。共享型机场节点的 IP 上往往挂着成百上千个 Netflix 会话，会被打上"共享出口"的标记——这既可能帮你蒙混过关（因为海量用户产生噪声），也可能因触发异常行为检测而被要求重新验证。

> 关键推论：**要让异地 TV 端稳定通过同户验证，真正要凑齐的是"出口 IP 一致性 + 住宅/企业级 ASN + 低抖动链路"。** 单靠一个共享节点，成功率是概率事件，不是工程方案。

## 四、细分人群与场景选型

**场景 A：留学生 / 出差党，只想让国内的家人继续用**
最优解是网络层同出口。把主账号的"家庭"定义在你稳定使用的那一侧（比如海外住处），然后在国内路由器上做透明代理，让家人的电视机顶盒从你的出口出网。代价是家人的所有流量都会绕一圈，网页体验下降，建议用分流规则只把 Netflix 域名走专线。

**场景 B：纯粹的家庭组异地合租（几个朋友分摊）**
这类场景 TV 端冲突最大。推荐组合拳：一人持有主账号并在 TV 端完成一次"家庭确认"，其余人在自己设备上使用**额外成员席位**，或者接受每 14 天一次的临时验证码续期。硬凑同出口会导致所有人带宽互相挤占，4K 播放时码率断崖。

**场景 C：4K/HDR 重度影迷 + 多设备**
优先选 IEPL 专线，重点看晚高峰抖动而非峰值带宽。4K 流媒体对**抖动**的敏感度远高于对带宽的敏感度，`15.6 Mbps` 的稳定码率比 `100 Mbps` 的忽高忽低体验好得多。

**场景 D：技术型自建党**
自建 WireGuard 统一出口，落地选住宅 IP 更好的地区（如日本、美国西海岸的家宽 VPS 或独立 IP 资源），并在出口做 DNS 强制劫持，避免 DNS 泄漏暴露真实位置。

更多分场景的网络方案对比，可参考站内 [场景化选型总览](/scenario/) 与 [专线技术原理详解](/tech/)。

## 五、分客户端实操与深度避坑

### 5.1 电视端（最严苛）

TV 端没有代理设置项，必须**在路由器层做透明代理**。三种主流做法：

- **软路由主路由方案**：OpenWrt / iStoreOS 直接接��网关，全局或分流代理。稳定性最好，部署成本最高。
- **旁路由方案**：主路由 DHCP 把网关指向旁路由。优点是改动小，缺点是部分客户端不遵守网关下发的 DNS，需要额外做 DNS 强制重定向。
- **代理网关硬件**：即插即用，适合非技术用户，但分流规则可控性差。

**避坑要点：**
- 关闭电视/盒子的"自动时区"，手动锁定为目标地区时区。时区与 IP 的地理位置错配是常见的验证触发点。
- 关闭 IPv6。多数代理方案只接管 IPv4，IPv6 会直接裸奔出去，造成出口 IP 不一致——这是 TV 端验证失败的头号原因。
- 关闭电视的"Wi-Fi 自动切换"与省电模式，避免设备在验证瞬间掉线到另一个网络。

### 5.2 移动端（最宽容）

手机/平板属于漫游设备，策略是"每 31 天回一次家"。实操上：让主账号手机每个月在家庭网络环境（或统一出口）下完整播放一集内容即可续命。注意**必须是完整播放**，只打开 App 不算。

### 5.3 桌面浏览器端

桌面端风控最松，但有 DNS 泄漏检测。浏览器建议开启 DoH，同时确保代理为全局模式或规则中包含 `netflix.com`、`nflxvideo.net`、`nflximg.net`、`fast.com` 四个域名族。少配一个 `nflxvideo.net`，就会出现"能打开首页但播不了"的经典症状。

各平台的分步配置教程，见 [全平台配置教程合集](/tutorial/)。

## 六、抓包排障诊断手册

排障逻辑：**先证出口，再证路径，最后证应用层。**

**第一步：确认出口 IP 是否一致**

```
curl -sS https://ipinfo.io/json | jq -r '.ip, .org, .country, .region'
```

在每一台需要"同户"的设备上分别跑（或通过该设备的网关跑）。如果 `org` 字段显示的是云厂商 ASN（如 `AS-XXX Cloud`），说明你用的是数据中心 IP，同户验证的通过率会被打折。

**第二步：确认链路质量与抖动**

```
mtr -rwzbc 100 nflxvideo.net
```

重点看三列：`Loss%`、`Avg`、`StDev`。判读标准如下：

| 指标 | 健康值 | 预警值 | 危险值 |
| --- | --- | --- | --- |
| 端到端丢包 | `0%` | `0.1-0.5%` | `> 1%` |
| 平均 RTT | `< 40ms` | `40-100ms` | `> 100ms` |
| 抖动（StDev） | `< 5ms` | `5-15ms` | `> 15ms` |
| 跨境跳数 | `≤ 8` | `9-14` | `> 14` |
| TLS 握手耗时 | `< 120ms` | `120-300ms` | `> 300ms` |

**第三步：验证应用层可达性**

```
curl -sS -o /dev/null -w "code=%{http_code} dns=%{time_namelookup}s conn=%{time_connect}s tls=%{time_appconnect}s total=%{time_total}s\n" https://www.netflix.com/title/80057281
```

`time_namelookup` 超过 `0.5s` 说明 DNS 走了远端解析，很容易造成 CDN 调度到错误区域；`time_appconnect - time_connect` 是 TLS 握手耗时，��线这条一般在 `80-160ms`，隧道方案经常超过 `300ms`。

**第四步：TCP 层连通性（无 curl 环境）**

```
tcping -t 5 www.netflix.com 443
```

连续五次全通则链路无阻断；若出现 `timeout` 交替，多半是代理出口存在会话竞争或 NAT 表溢出。

**第五步：确认 DNS 无泄漏**

```
dig +short @1.1.1.1 netflix.com
dig +short @8.8.8.8 netflix.com
```

两个解析结果的 CDN 边缘 IP 若落在完全不同的国家/地区，说明你的 DNS 分流规则有漏，实际观看会走错 CDN，表现就是"能进站、加载慢、频繁降档"。

## 八、常见问题 FAQ

**Q1：为什么手机能看，电视端一直提示"不在 Netflix 家庭中"？**
因为 TV 端没有漫游豁免，且会更严格地读取局域网指纹。解决路径只有两条：走临时访问代码，或让 TV 端的出口 IP 与主设备保持一致（含 IPv6 关闭、DNS 强制劫持）。

**Q2：临时访问代码多久要重新获取一次？**
官方口径约为 14 天有效期，实际因地区和客户端版本略有浮动。建议在失效前 2-3 天主动续期，别等到播放中断再操作，因为中断瞬间的验证更容易触发二次风控。

**Q3：同一个节点上多个人看奈飞，会互相影响吗？**
会。同一出口 IP 上活跃 Netflix 会话越多，行为特征越"像商业共享"，被要求重新验证的频率越高。3-5 台是相对安全的区间。

**Q4：换了家庭位置之后，原来的设备全部失效了怎么办？**
这是正常现象。更换家庭锚点后，所有不在新锚点网络下的设备都需要重新验证。所以更换前务必确认新网络是你长期稳定的主网络。

**Q5：用机场节点为什么有时候能过、有时候过不了？**
因为同户判定是加权模型，不是布尔值。节点 IP 池轮换、出口 ASN、当时的并发会话数都会影响结果。工程化方案必须做到出口 IP 可预期、可复现。

**Q6：额外成员席位值得开吗？**
如果你有 2-3 个固定异地用户，且不想折腾网络，额外成员是最省心的方案——独立密码、独立推荐流、不受同户判定影响。代价是月费上升，且部分地区未开放。

**Q7：4K 播放总是降到 1080p，是节点问题还是账号问题？**
先排除账号套餐等级（需 Premium），然后用 `mtr` 看抖动。抖动 `> 15ms` 时 Netflix 的 ABR 算法会保守降档。这也是为什么专线方案在 4K 场景下优势明显。

## 十、结语
